# RagFlow 技术架构设计

> 基于 `cmd/`、`internal/` 代码梳理，从服务进程、分层架构、核心引擎、数据模型、关键流程等维度描述技术实现。

---

## 1. 服务进程架构

RagFlow 采用**多进程模式**，单一二进制 `ragflow_server` 通过命令行参数启动不同角色：

```bash
ragflow_server --api          # API 服务（对外 HTTP）
ragflow_server --admin        # 管理后台服务
ragflow_server --ingestor     # 摄取服务（文档解析与索引）
ragflow_server --syncer       # 同步服务（外部数据源拉取）
ragflow_server --deepdoc      # DeepDoc 推理服务（OCR/版面分析）
ragflow_server --migrate      # 数据库迁移
```

### 1.1 启动流程

入口在 `cmd/ragflow_server.go`：

1. **参数解析**：`parseArgsFrom` 解析 `--api/--admin/--ingestor/--syncer/--deepdoc` 等模式
2. **配置加载**：`server.Init(configPath)` 通过 Viper 加载 `conf/service_conf.yaml` + 环境变量
3. **数据库初始化**：`dao.InitDB()` 连接 MySQL/PostgreSQL，执行 GORM 迁移
4. **引擎初始化**：`engine.InitDocEngine()` 按配置创建文档引擎；`engine.InitMessageQueue()` 连接 NATS
5. **模式分发**：调用对应 `server/<mode>.Run()`

### 1.2 各模式职责

| 模式 | 职责 | 关键代码 |
|------|------|---------|
| API | 对外 HTTP API、Agent 运行时、通道接入 | `server/api/server.go` |
| Admin | 管理后台接口、用户管理 | `server/admin/server.go` |
| Ingestor | 文档摄取管线、知识编译 | `server/ingestor/server.go`, `ingestion/service/` |
| Syncer | 外部数据源定时同步 | `server/syncer/server.go`, `syncer/` |
| DeepDoc | OCR 与版面分析推理（CGO） | `server/deepdoc/server.go`, `deepdoc/native/` |

API 与 Ingestor 可在进程内注册 DeepDoc 后端，无需独立进程。

## 2. 分层架构

```
┌─────────────────────────────────────────────────────┐
│                    前端 (web/)                       │
│            React + TypeScript + Vite                 │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP / WebSocket / SSE
┌──────────────────────▼──────────────────────────────┐
│              接入层 (internal/router)                │
│         Gin Engine + 路由注册 + 中间件                │
├─────────────────────────────────────────────────────┤
│             处理层 (internal/handler)                │
│     HTTP Handler / 请求校验 / 响应格式化              │
├─────────────────────────────────────────────────────┤
│              服务层 (internal/service)               │
│         业务逻辑 / 领域服务 / 模型工厂                 │
├─────────────────────────────────────────────────────┤
│            数据访问层 (internal/dao)                 │
│            GORM DAO / 原生 SQL                       │
├─────────────────────────────────────────────────────┤
│              实体层 (internal/entity)                │
│         GORM 模型 / 枚举 / 类型定义                   │
└─────────────────────────────────────────────────────┘
```

### 2.1 接入层

- **Gin Web 框架**：`router/router.go` 注册所有路由
- **路由分组**：
  - 无需认证：`/api/v1/system/ping`、登录注册、OAuth 回调、公开 Workflow 运行
  - Beta Token 认证：`/api/v1/searchbots`、`/api/v1/chatbots`、`/api/v1/mcp`
  - 用户 Session 认证：`/api/v1/*` 下大部分受保护接口
- **中间件**：认证中间件（`AuthMiddleware`）、请求日志（`common.GinLogger`）、CORS

### 2.2 处理层

`internal/handler/` 下每个业务域对应一个 Handler，职责：
- 解析请求参数
- 调用 Service 层
- 统一错误处理（`error.go`）
- 构造响应

例如 `ChatHandler`、`DatasetsHandler`、`DocumentHandler`、`AgentHandler` 等。

### 2.3 服务层

`internal/service/` 承载核心业务逻辑，按子域组织：
- `dataset/`：知识库 CRUD、搜索
- `document/`：文档上传、解析、状态
- `file/`：文件存储、文件夹、版本提交
- `chunk/`：chunk 管理、向量操作
- `nlp/`：检索、重排、同义词、导航
- `graph/`：知识图谱检索与打分
- `nav/`：知识库导航服务
- `wikisearch/`：编译知识搜索

### 2.4 数据访问层

`internal/dao/` 使用 GORM 封装数据库操作：
- 每个实体对应一个 DAO（如 `KnowledgebaseDAO`、`DocumentDAO`、`ChatDAO`）
- 支持 MySQL 与 PostgreSQL
- 迁移逻辑在 `migration.go`，含索引迁移、列迁移

### 2.5 实体层

`internal/entity/` 定义 GORM 模型：
- `BaseModel`：通用时间字段（`create_time`、`update_time`）
- 业务实体：`Knowledgebase`、`Document`、`Chat`、`ChatSession`、`Tenant`、`User`、`UserCanvas` 等
- JSON 类型：`JSONMap`、`JSONSlice` 存储灵活配置

## 3. 核心引擎

### 3.1 文档引擎（Doc Engine）

`internal/engine/engine.go` 定义 `DocEngine` 接口，统一向量+全文检索能力：

```go
type DocEngine interface {
    // Chunk 存储
    CreateChunkStore / InsertChunks / UpdateChunks / DeleteChunks / Search / GetChunk
    // 元数据存储
    CreateMetadataStore / InsertMetadata / SearchMetadata
    // 文档索引（技能搜索）
    IndexDocument / DeleteDocument / BulkIndex
    // 工具方法
    GetFields / GetAggregation / GetHighlight / RunSQL / KNNScores
}
```

**支持的后端：**

| 引擎 | 目录 | 特点 |
|------|------|------|
| Elasticsearch | `engine/elasticsearch/` | 成熟方案，向量+全文 |
| Infinity | `engine/infinity/` | 国产向量数据库 |
| OceanBase / SeekDB | `engine/oceanbase/` | 关系型+向量扩展 |
| SereneDB | `engine/serenedb/` | 时序+向量 |
| Vastbase | `engine/vastbase/` | PostgreSQL 系 |

全局单例通过 `engine.Get()` 获取，启动时 `InitDocEngine` 按配置创建。

### 3.2 消息队列（Message Queue）

`internal/engine/nats/` 基于 NATS JetStream：

```go
type MessageQueue interface {
    InitConsumer(subject string) error
    PublishTask(subject string, payload []byte) error
    PullMessages(ctx, messageCount int) ([]TaskHandle, error)
    // 知识编译专用
    InitKnowledgeCompileStream / PublishKnowledgeCompile
    AcquireKnowledgeCompileLease / HeartbeatKnowledgeCompileLease
}
```

**用途：**
- 摄取任务分发（`ingestion_tasks` subject）
- 知识编译任务调度
- 分布式锁与租约（Lease）

### 3.3 存储引擎（Storage Engine）

`internal/storage/` 抽象对象存储：

| 类型 | 实现 |
|------|------|
| MinIO | `minio.go` |
| AWS S3 | `s3.go` |
| 阿里云 OSS | `oss.go` |
| Google GCS | `gcs.go` |
| Azure | - |

存储原始文档、解析中间产物、图片等二进制数据。

### 3.4 缓存引擎

基于 Kvrocks（Redis 兼容），用于：
- Agent 运行状态（CheckpointStore、RunTracker）
- 会话缓存
- 分布式锁

## 4. Agent 运行时架构

### 4.1 整体结构

```
UserCanvas (DSL)
    │
    ▼
Canvas.Compile()  ──→  Eino Workflow
    │
    ▼
Scheduler 调度执行
    │
    ├── Component.Invoke()  ──→  各组件实现
    │       │
    │       ├── LLM 组件 ──→ ModelFactory ──→ 模型驱动
    │       ├── Retrieval 组件 ──→ 检索适配器
    │       ├── Tool 组件 ──→ 工具注册表
    │       └── ...
    │
    ▼
CanvasState（运行时状态）
```

### 4.2 关键包

| 包 | 职责 |
|----|------|
| `agent/canvas/` | DSL 解析、编译、调度、状态 |
| `agent/component/` | 画布节点组件实现 |
| `agent/runtime/` | 运行时核心：组件注册表、状态、模板 |
| `agent/tool/` | 工具系统与注册表 |
| `agent/sandbox/` | 代码执行沙箱 |
| `agent/audio/` | TTS 语音合成 |
| `harness/` | 通用 Agent 执行框架（ReAct、Workflow、Session） |
| `agentic_rag/` | 智能推理 Agent（ReAct + 知识库工具） |

### 4.3 组件注册表

`agent/runtime/registry.go` 的 `DefaultRegistry` 管理所有组件：
- 按 Category 分类：`CategoryAgent`、`CategoryIngestion`、`CategoryShared`
- 注册接口：`Register(name, category, factory, metadata)`
- 查找：`Lookup(name)` 返回工厂函数

### 4.4 Eino 框架集成

基于 [CloudWeGo Eino](https://github.com/cloudwego/eino) 框架：
- `compose.Workflow`：画布编译目标
- `components/tool`：工具调用
- `schema`：消息、工具调用数据结构
- `adk`：Agent 开发套件

## 5. 摄取管线架构

### 5.1 Ingestor 运行模型

```
NATS Consumer (Pull)
    │
    ▼
Ingestor.dispatchLoop()
    │
    ├── Worker Pool（worker_dispatcher）
    │       │
    │       ▼
    │   PipelineExecutor.Execute()
    │       │
    │       ├── 加载 Pipeline DSL
    │       ├── 编译 Canvas → Workflow
    │       ├── 执行 Workflow
    │       ├── 后处理：chunk 规范化、索引写入
    │       └── 持久化结果
    │
    └── Heartbeat（续约消息 ACK 截止时间）
```

### 5.2 Pipeline DSL

`internal/ingestion/pipeline/pipeline.go`：

- DSL 以 JSON 描述管线，含组件节点与连线
- 内置模板在 `pipeline/template/`：general、book、paper、laws、qa、table、picture、audio、email 等
- `NewPipelineFromDSL` 解析 DSL，`Run` 执行

### 5.3 摄取组件

`internal/ingestion/component/` 实现管线各阶段：

| 组件 | 文件 | 职责 |
|------|------|------|
| Parser | `parser.go` | 文档解析分发 |
| Chunker | `chunker/` | 分块（token/delim/title/table/qa/page/one） |
| Tokenizer | `tokenizer.go` | Token 统计 |
| Extractor | `extractor.go` | 实体/关系抽取 |
| Vision | `vision_*.go` | 视觉增强（图片描述、OCR） |
| KnowledgeCompiler | `knowledge_compiler/` | 知识编译（tree/wiki/mindmap/structure） |

### 5.4 分词器

`internal/tokenizer/` + `internal/binding/cpp/`：
- 基于 C++ 实现的分词器（re2、pcre2、stemmer、darts 双数组 Trie）
- CGO 绑定供 Go 调用
- 支持中英文分词、同义词、NER

## 6. 文档解析架构

`internal/parser/parser/` 实现各格式解析器，统一输出 `ParseResult`：

```
文件输入 → 文件类型检测 → GetParser(fileType) → ParseResult（含 DocItem 列表）
```

### 6.1 解析器矩阵

| 格式 | 解析器 | 后端 |
|------|--------|------|
| PDF | `pdf_parser_*.go` | MinerU / PaddleOCR / Docling / OpenDataLoader / SOMark / TCADP |
| DOCX | `docx_parser.go` | 原生解析 + CGO |
| DOC | `doc_parser.go` | office_oxide |
| XLSX | `xlsx_parser.go` | 原生 |
| XLS | `xls_parser.go` | office_oxide |
| PPTX | `pptx_parser.go` | 原生 |
| PPT | `ppt_parser.go` | office_oxide |
| HTML | `html_parser.go` | goquery |
| Markdown | `markdown_parser.go` | goldmark |
| Email | `email_parser.go` | go-message |
| EPUB | `epub_parser.go` | go-epub |
| JSON | `json_parser.go` | 原生 |
| Audio | `audio_parser.go` | ASR 模型 |
| Picture | `picture_parser.go` | OCR + VLM |
| CSV | `csv_parser.go` | encoding/csv |

### 6.2 解析结果

`DocItem` 是统一的文档元素表示：
- 类型：text、title、table、image、list、equation 等
- 含位置信息、层级关系、原始内容

## 7. 模型驱动架构

### 7.1 模型类型体系

`internal/entity/models/` 实现 80+ 提供商驱动，统一接口：

```
ModelDriver (基础接口)
    ├── ChatModel      → Chat / Completion / Stream
    ├── EmbeddingModel → Embed
    ├── RerankModel    → Rerank
    ├── ASRModel       → Transcribe
    ├── TTSModel       → Speech
    └── ImageModel     → Generate / Understand
```

### 7.2 模型工厂

`internal/service/model_factory.go` 的 `ModelFactory`：

1. 解析 `modelRef`（如 `tenant-xxx/openai/gpt-4`）
2. 查询租户模型配置（provider → instance → model）
3. 权限校验
4. 构造具体模型实例（含 API Key、端点、超时）

### 7.3 模型配置

- `conf/models/*.json`：各提供商的模型清单与默认配置
- `conf/all_models.json`：全量模型索引
- `entity/llm_factories.go`：提供商工厂映射

## 10. 关键技术流程

### 10.1 文档摄取流程

```
1. API 接收上传 → 存储到 Storage Engine → 创建 Document 记录
2. 发布 NATS 消息到 ingestion_tasks
3. Ingestor PullMessage → Worker 处理
4. PipelineExecutor:
   a. 加载 Pipeline DSL（按 parser_id 选择模板）
   b. 编译 Canvas → Eino Workflow
   c. 执行 Workflow:
      - Parser 组件：解析文档 → DocItem 列表
      - Chunker 组件：分块 → Chunk 列表
      - Embedder 组件：生成向量
      - IndexWriter：写入 Doc Engine
   d. 知识编译（tree/wiki/mindmap/structure）
5. 更新 Document 状态与进度
```

### 10.2 RAG 问答流程

```
1. 用户问题 → ChatSessionService.Completions
2. ChatPipelineService.AsyncChat:
   a. 问题理解：关键词提取、元数据过滤
   b. 多路检索:
      - 向量检索（KNN）
      - 关键词检索（BM25）
      - 知识图谱检索
      - Web 搜索（可选）
   c. 重排序（Rerank 模型）
   d. 上下文构建：拼接检索结果到 Prompt
   e. LLM 流式生成（ChatModel.Stream）
   f. 引用装饰：关联答案引用到源 chunk
3. SSE 流式返回给前端
```

### 10.3 Agent 执行流程

```
1. 触发画布运行 → AgentService.Run
2. 加载 UserCanvas.DSL → Canvas 结构
3. Canvas.Compile() → Eino Workflow
4. Scheduler 调度:
   a. 拓扑排序确定执行顺序
   b. 逐个 Component.Invoke(ctx, db, inputs)
   c. 变量在 Components 间传递（CanvasState）
   d. 支持 Loop、Parallel、Switch 控制流
5. 工具调用通过 agent/tool 注册表分发
6. 运行记录持久化到 AgentRun
7. 返回 End 节点输出
```
