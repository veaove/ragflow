# RagFlow 业务模块设计

> 基于代码库 `internal/` Go 实现梳理，覆盖用户体系、知识库、摄取、检索、对话、Agent、通道、MCP、连接器等核心业务域。

---

## 1. 总体业务视图

RagFlow 是一个面向企业的检索增强生成（RAG）平台，核心业务闭环为：

```
数据接入 → 知识加工 → 检索增强 → 智能问答 → 多端触达
```

围绕该闭环，平台划分为以下业务域：

| 业务域 | 核心职责 | 关键代码入口 |
|--------|---------|-------------|
| 用户与租户 | 账号、组织、模型配额、权限 | `internal/service/user.go`, `tenant.go`, `permission/` |
| 知识库管理 | 数据集 CRUD、元数据、标签、同义词 | `internal/service/dataset/` |
| 文档管理 | 上传、解析、分块、版本提交 | `internal/service/document/`, `file/` |
| 摄取管线 | 解析→分块→嵌入→索引→知识编译 | `internal/ingestion/` |
| 检索服务 | 混合检索、重排、过滤、导航 | `internal/service/nlp/`, `search.go` |
| 对话问答 | RAG 问答、会话、引用、语音 | `internal/service/chat_pipeline.go`, `chat_session.go` |
| 智能体 | Canvas 画布、组件、工具、沙箱 | `internal/agent/`, `internal/harness/` |
| MCP 集成 | MCP 服务器、工具、对外暴露 | `internal/mcp/`, `internal/service/mcp.go` |
| 外部通道 | 钉钉、飞书、企微、Telegram 等 | `internal/channels/` |
| 连接器同步 | 外部数据源拉取与增量同步 | `internal/syncer/`, `internal/service/connector.go` |
| 模型管理 | 提供商、实例、模型类型、API Key | `internal/service/model_*.go`, `entity/models/` |
| 记忆系统 | 对话记忆、记忆提取与检索 | `internal/service/memory*.go` |
| 质量检查 | 质检规则、实时命中、高亮 | `internal/service/qc_*.go` |
| 分析统计 | 咨询日志、报表、系统监控 | `internal/service/analytics_service.go`, `stats.go` |

## 2. 用户与租户管理

### 2.1 多租户体系

RagFlow 采用 **租户（Tenant）+ 用户（User）** 双层模型，一个用户可属于多个租户。

**核心实体：**
- `Tenant`（`entity/tenant.go`）：组织主体，持有默认模型配置（LLM、Embedding、Rerank、ASR、OCR、TTS）及积分（Credit）
- `User`（`entity/user.go`）：用户账号，支持邮箱/SSO 登录
- `UserTenant`（`entity/user_tenant.go`）：用户与租户的多对多关系，含角色（admin/member）

**关键业务能力：**
- 用户注册、登录、登出、忘记密码（OTP 验证码）
- 租户创建、成员邀请/添加/移除
- 租户级默认模型选择（`entity/tenant_model.go`、`tenant_llm.go`）
- API Token 管理（`entity/api_token.go`），支持 Beta Token、App API Key

### 2.2 权限体系

基于 `internal/permission/` 的资源-动作模型：

```
Subject(UserID, TenantID) → Resource(Kind, ID) → Action(read/write/enable)
```

- **资源类型**：Dataset、Canvas、AgentSession、Memory、File、SearchApp、Chat、ChatChannel、Connector、ModelProvider、MCPServer、SkillSpace 等
- **权限策略**：Community 版与 Enterprise 版通过 `policy_ce.go` / `policy_ee.go` 分离
- **数据隔离**：所有业务查询按 `tenant_id` 过滤，实现租户级数据隔离

## 3. 知识库管理

### 3.1 数据集（Dataset）

知识库的顶层容器，对应 `entity/dataset.go` 的 `Knowledgebase` 实体。

**核心属性：**
- 名称、描述、语言（影响分词器和全文索引）
- Embedding 模型、向量相似度权重
- 权限（me / team）
- 元数据配置（`metadata_config`）
- 解析器配置集合

**业务能力：**
- 创建/编辑/删除数据集
- 数据集标签聚合（`datasets/tags/aggregation`）
- 知识库图谱（`datasets/:id/graph`）
- 元数据字段配置与批量更新
- 知识库导航树（Navigation）

### 3.2 同义词管理

数据集级别的词汇别名体系（`entity/synonym.go`、`service/synonym.go`）：
- 同义词组的 CRUD 与批量导入
- 查询时通过 `nlp.QueryBuilder` 进行关键词扩展
- 与内置分词器词库（`rag/res/synonym.json`）协同

### 3.3 知识库变更集（Change Set）

类 Git 的 staged-edit 工作流（`entity/kb_change_set.go`、`service/kb_change_set.go`）：
- 创建变更集 → 编辑 chunk → 检索对比（retrieval-compare）→ 相似问生成 → 发布/丢弃
- 支持变更前后的检索效果对比

## 4. 文档管理

### 4.1 文档实体

`entity/document.go` 的 `Document` 实体记录文档全生命周期：
- 所属知识库、解析器类型、解析配置
- 文件类型、大小、token 数、chunk 数
- 处理进度（progress）、进度消息
- 内容哈希（content_hash）用于幂等去重
- 状态机：未开始 → 运行中 → 完成/失败/取消

### 4.2 文档解析器类型

在 `entity/dataset.go` 中定义 `ParserType`，覆盖：
- `general` 通用、`naive` 朴素、`one` 整体
- `paper` 论文、`book` 图书、`laws` 法律、`manual` 手册
- `presentation` 演示、`table` 表格、`qa` 问答对
- `picture` 图片、`audio` 音频、`email` 邮件
- `knowledge_graph` 知识图谱

### 4.3 文件管理

`internal/service/file/` 提供：
- 文件上传（分片、秒传、断点续传）
- 文件夹结构（`file_folder.go`）
- 文件版本提交（`file_commit.go`，类似 Git commit）
- 文件与数据集关联（link-to-datasets）

## 5. 摄取管线（Ingestion Pipeline）

摄取是 RagFlow 最核心的数据加工链路，由独立的 **Ingestor** 服务进程承载。

### 5.1 整体流程

```
文档上传 → NATS 任务分发 → Pipeline 执行 → Chunk 索引 → 知识编译
```

**关键组件：**
- `ingestion/service/ingestion_service.go`：Ingestor 主控，管理 worker pool、心跳、租约
- `ingestion/pipeline/pipeline.go`：从 DSL 构造并执行摄取管线
- `ingestion/task/pipeline_executor.go`：单个文档的管线执行器
- `ingestion/component/`：各阶段组件实现

### 5.2 管线阶段

**解析阶段（Parser）**
- `ingestion/component/parser.go`：根据文件类型分发到具体解析器
- `parser/parser/`：PDF、DOCX、XLSX、HTML、Markdown、PPTX、Email、Audio、Picture、EPUB、JSON、Text 等解析器
- PDF 支持多种后端：MinerU、PaddleOCR、Docling、OpenDataLoader、SOMark、TCADP

**分块阶段（Chunker）**
- `ingestion/component/chunker/`：核心分块逻辑
  - `token.go`：基于 token 数的智能分块（默认）
  - `delim.go`：基于分隔符分块
  - `title.go`：按标题层级分块
  - `table.go`：表格分块
  - `qa.go`：问答对分块
  - `page.go`：按页分块
  - `one.go`：整体分块
- 支持 overlap（重叠）、父子 chunk、table context

**嵌入阶段（Embedder）**
- `ingestion/task/embedder.go`：调用租户配置的 Embedding 模型生成向量
- 支持批量嵌入、限流、重试

**索引阶段（Index Writer）**
- `ingestion/task/chunk_index_writer.go`：将 chunk 写入文档引擎（ES/Infinity/OceanBase 等）

### 5.3 知识编译器（Knowledge Compiler）

对已索引的 chunk 进行高阶知识加工，产出结构化知识产品：

| 编译类型 | 目录 | 产出 |
|---------|------|------|
| Tree | `knowledge_compiler/tree/` | 层次化知识树（RAPTOR 摘要、分水岭算法） |
| Wiki | `knowledge_compiler/wiki/` | Wiki 页面（主题规划、摘要、增量更新） |
| Mindmap | `knowledge_compiler/mindmap/` | 思维导图 |
| Structure | `knowledge_compiler/structure/` | 知识图谱（实体、关系、证据链） |

调度由 `ingestion/knowledge_compile/service.go` 管理，通过 NATS 消息驱动。

## 6. 检索服务

### 6.1 混合检索

`internal/service/nlp/retrieval.go` 的 `RetrievalService` 实现多策略融合检索：

1. **向量检索**：通过 Embedding 模型计算查询向量，KNN 召回
2. **关键词检索**：基于分词器的全文检索（BM25）
3. **混合排序**：`vector_similarity_weight` 控制向量与关键词的权重融合

### 6.2 检索增强

- **重排序（Rerank）**：`nlp/reranker.go`，调用租户的 Rerank 模型对候选 chunk 精排
- **元数据过滤**：`service/metadata_filter.go`，支持按文档元数据条件过滤
- **同义词扩展**：`nlp/synonym.go`，查询关键词同义词替换
- **TOC/子 chunk**：支持按目录结构和父子 chunk 导航
- **知识库导航**：`service/nav/`，基于向量聚类的导航树
- **知识图谱检索**：`service/graph/`，图谱遍历与打分

### 6.3 文档引擎抽象

`engine.DocEngine` 接口统一了多种检索后端：
- Elasticsearch
- Infinity
- OceanBase / SeekDB
- SereneDB
- Vastbase

## 7. 对话与问答

### 7.1 对话实体

- `Chat`（`entity/chat.go`，表 `dialog`）：对话配置，含 LLM、提示词、知识库列表、检索参数
- `ChatSession`（`entity/chat.go`，表 `conversation`）：会话，含消息历史

### 7.2 RAG 问答流水线

`internal/service/chat_pipeline.go` 的 `ChatPipelineService` 是核心引擎：

```
用户问题 → 检索增强 → Prompt 构建 → LLM 生成 → 引用装饰 → 流式返回
```

**关键步骤：**
1. **查询理解**：提取关键词、元数据过滤条件
2. **多路检索**：SQL 检索、向量检索、Web 搜索、KG 检索
3. **重排序**：对多路结果融合排序
4. **上下文构建**：拼接检索结果到 Prompt
5. **LLM 生成**：支持流式输出、推理内容（reasoning）分离
6. **引用装饰**：`service/citation.go`，将答案中的引用标记关联到源 chunk
7. **相关问题推荐**：`service/related_question.go`

### 7.3 对话能力

- 多轮对话与会话管理
- 思维导图生成（mindmap）
- 语音合成（TTS）与语音转文字（ASR）
- OpenAI 兼容 API（`/api/v1/openai/:chat_id/chat/completions`）
- 消息反馈（点赞/踩）

## 8. 智能体（Agent）

### 8.1 Canvas 画布

`internal/agent/canvas/` 是 Agent 的可视化编排运行时：

- **DSL 表示**：`Canvas` 结构含 components（节点）、path（边）、history、memory、retrieval、globals
- **编译**：`compile.go` 将 DSL 编译为 Eino Workflow
- **调度**：`scheduler.go` 管理节点执行顺序、循环、并行
- **状态**：`state.go` 维护运行时上下文、变量、错误

画布支持 4 种形态（`entity/canvas.go`）：
- `agent_canvas`：传统 Agent
- `chatflow_canvas`：对话流
- `workflow_canvas`：工作流
- `dataflow_canvas`：数据流（摄取管线）

### 8.2 组件体系

`internal/agent/component/` 实现画布节点，每个组件实现 `Component` 接口（`Name`、`Invoke`、`Stream`、`Inputs`、`Outputs`）：

| 组件 | 职责 |
|------|------|
| Begin | 流程入口，接收用户输入 |
| End | 流程出口，返回结果 |
| LLM | 调用大语言模型 |
| Retrieval | 知识库检索 |
| Answer | 生成最终回答 |
| Switch | 条件分支 |
| Loop | 循环执行 |
| Parallel | 并行执行 |
| Message | 流式消息输出 |
| Tool | 工具调用 |
| CodeExec | 代码执行 |
| Browser | 浏览器操作 |
| Invoke | 调用其他画布 |
| VariableAssigner | 变量赋值 |
| TemplateTransform | 模板转换 |
| StringTransform | 字符串变换 |
| ListOperations | 列表操作 |
| DataOperations | 数据操作 |
| Categorize | 分类 |
| Fillup / UserFillup | 表单填充 |
| MemorySave | 保存记忆 |

### 8.3 工具系统

`internal/agent/tool/` 提供 Agent 可调用的工具集，通过 `registry.go` 注册：

- **搜索类**：Google、DuckDuckGo、Tavily、SearXNG、Wikipedia、PubMed、ArXiv
- **金融类**：AkShare、Tushare、Yahoo Finance、Jin10、Wencai
- **知识检索**：Hybrid Search、Vector Search、BM25 Search、Wiki Query
- **代码执行**：CodeExec（沙箱环境）
- **数据库**：ExecuteSQL
- **爬虫**：Crawler、Web Crawler
- **邮件**：Email
- **翻译**：DeepL
- **GitHub**：代码仓库操作
- **MCP 工具**：通过 MCP 协议调用外部工具

### 8.4 沙箱环境

`internal/agent/sandbox/` 提供代码执行隔离环境：
- E2B 云沙箱
- 本地沙箱
- SSH 远程沙箱
- 阿里云沙箱

`internal/agentic_rag/` 实现基于 ReAct 范式的智能体：

- 知识库引用（`citations.go`）

## 17. 业务流程总览

### 17.1 知识库构建流程

```
用户创建数据集 → 上传文档 → 触发摄取任务
    → Ingestor 消费 NATS 消息
    → 解析文档（PDF/DOCX/...）
    → 分块（token/title/table/...）
    → 嵌入向量
    → 写入文档引擎
    → 知识编译（tree/wiki/mindmap/structure）
    → 文档状态标记为完成
```

### 17.2 问答流程

```
用户发起对话 → 加载对话配置
    → 问题理解（关键词提取、元数据过滤）
    → 多路检索（向量+关键词+KG+Web）
    → 重排序
    → 构建 Prompt（含检索上下文）
    → LLM 流式生成
    → 引用装饰
    → 返回答案与引用
```

### 17.3 Agent 执行流程

```
用户触发画布运行 → 加载 DSL
    → 编译为 Workflow
    → 从 Begin 节点开始
    → 按依赖顺序执行组件
    → 工具调用（搜索/代码/数据库/...）
    → 状态与变量传递
    → End 节点输出结果
    → 运行记录持久化
```
