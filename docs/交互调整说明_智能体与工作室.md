## 一、现状问题诊断

当前把 Chatflow / Workflow / 管道 / 算子并排放进原生「创建智能体」弹窗，产生四个问题：

| # | 问题 | 现象 | 根因 |
|---|---|---|---|
| 1 | i18n key 直接暴露 | 卡片上写着 `flow.flow.chatflow`、`flow.flow.workflow` | 枚举值直接当文案渲染，缺少 i18n 映射表 |
| 2 | 文案竖排换行 | 「工作流」「数据管道」每行只放 2 个字 | 5 个卡片挤在固定宽度里，中文标签被压到换行 |
| 3 | 语义边界混乱 | 智能体、对话工作流、无对话工作流、数据管道、编译算子 并列 | 「智能体类型」这个问句答不了「Chatflow 是什么」 |
| 4 | 能力承诺不一致 | 「编译算子」置灰但没有解释 | 没有状态说明，用户不知道是未开放还是不可用 |

同时「创建智能体」这个标题与它实际承载的 5 种类型已经不符。

---

## 二、调整方案

**原则：原生智能体入口不动，新增能力独立成模块。**

```
改造前                                  改造后
┌──────────────┐                        ┌──────────────┐
│ 首页          │                        │ 首页          │
│ 知识库        │                        │ 知识库        │
│ 聊天          │                        │ 聊天          │
│ 搜索          │                        │ 搜索          │
│ 智能体 ●      │                        │ 智能体 ●      │  ← 原生，弹窗仍是
│ 记忆          │                        │ 工作室 ★新增  │     智能体流程 / Ingestion
│ 文件管理      │                        │ 记忆          │
└──────────────┘                        │ 文件管理      │
                                         └──────────────┘
创建智能体弹窗（5 类，卡片挤）
  工作流 / flow.flow.chatflow
  / flow.flow.workflow / 数据管道 / 编译算子

                                         创建智能体弹窗（2 类，与原生一致）
                                           智能体流程 / Ingestion pipeline

                                         工作室弹窗（2 类）
                                           Chatflow（对话式工作流）
                                           Workflow（无对话工作流）
```

## 三、改动清单

| 对象 | 改造前 | 改造后 |
|---|---|---|
| 侧边栏 | 智能体（内含 5 种类型） | 智能体（不变）+ **工作室（新增，带「新增」标记）** |
| 智能体列表 | Agent、Chatflow、Workflow 混排 | 只放 Agent 与模板；Chatflow/Workflow 迁至工作室 |
| 创建智能体弹窗 | 5 个卡片，含未翻译 key 与置灰项 | **2 个卡片：智能体流程 / Ingestion pipeline**，与原生一致 |
| 工作室列表 | — | 类型 Tab（全部 / Workflow / Chatflow）+ 类型说明卡 + 空态 |
| 工作室创建弹窗 | — | Chatflow / Workflow 两张大卡，各带**行为差异说明**与**适用场景**；含名称、图标、描述、起步模板 |
| 归属提示 | 无 | 工作室弹窗底部提示「Agent 与数据管道请到智能体模块」 |
| 顶部创建 | 智能体只有一个 `+` 图标按钮；工作室类型卡不可点 | **智能体**：`+` 改成「创建应用 ▾」拆分按钮，主按钮直接开弹窗，箭头出下拉；**工作室**：两张类型卡变成创建入口，hover 出现「创建对话流 → / 创建任务流 →」，点击直接打开弹窗并**预选对应类型** |
| 视图切换 | 无 | 两个页面都加「卡片 / 表格」分段开关；表格视图列：<br>智能体＝名称·类型·标签·状态·上次保存·操作<br>工作室＝名称·类型·状态·版本·最近运行·更新时间·操作<br>视图偏好存 localStorage，刷新后保持 |

### 3.1 顶部创建的两种做法对比

| 做法 | 优点 | 缺点 | 本期采用 |
|---|---|---|---|
| 只保留右上角一个「创建应用」按钮 | 干净 | 类型多时用户要进弹窗才知道有什么 | |
| 类型卡可直接点 | 一眼看清有哪两种，点哪张建哪种 | 卡片区占一行 | ✅ 工作室 |
| 拆分按钮（主按钮 + 下拉） | 主流程一步到位，低频操作收进下拉 | 需要两个按钮位 | ✅ 智能体 |

**为什么智能体用拆分按钮、工作室用类型卡**：智能体只有「智能体流程 / 数据管道」两类且入口已存在多年，
用户对「从哪创建」已形成习惯，不需要额外占一行；工作室是新增模块，用户还不知道能建什么，
把类型做成可点的卡片本身就是最好的引导。

### 3.2 视图切换的取舍

- **默认卡片**：卡片能展示描述与图标，识别成本低；表格适合「已有很多应用、需要横向比对状态/版本/时间」的场景。
- **偏好持久化**：存 `localStorage`，两个页面共用一个偏好，切换一次全局生效。

### 3.3 搜索与分页

两个页面都补齐，规则完全一致：

| 能力 | 规则 |
|---|---|
| 搜索 | 按名称模糊匹配，输入即筛；带 `×` 一键清空；空结果显示「没有匹配「xxx」的应用」+ 清空按钮 |
| 搜索范围 | 只匹配名称，不匹配描述——保持可预期，避免搜出描述里偶然出现的词 |
| 分页 | 默认 12 条/页，可选 8/12/24/48；卡片与表格**共用同一份分页状态**，切换视图不丢页码 |
| 页码 | 页数 ≤7 时全显示；超过则首尾 + 当前页 ±1，中间用省略号 |
| 联动 | 搜索或切换类型时**重置到第 1 页**；翻页超出范围自动收敛 |
| 计数 | Tab 上的数量显示的是**该类型的总数**（不随搜索变化），筛选结果数单独显示在搜索框右侧 |
| 空数据 | 卡片与表格都隐藏，分页按钮不渲染，只留文案 |

**为什么计数要分两处**：Tab 上的「任务流 10」回答「我有多少个任务流」，搜索框旁的「筛选出 2 个」回答
「我现在看到几个」。如果 Tab 数字跟着搜索变，用户会以为数据丢了。

## 四、两个弹窗的设计要点

### 4.1 创建智能体（原生，不动）

- 卡片从 5 个减到 2 个，宽度回到原生比例，中文不再竖排。
- 没有未解释的置灰项。
- 标题与内容一致。

### 4.2 创建应用（工作室）

**大卡片要回答三个问题，而不是只给名字：**

| 问题 | Chatflow 的答案 | Workflow 的答案 |
|---|---|---|
| 它是什么 | 对话式工作流 | 无对话工作流 |
| 图长什么样 | 开始 → 检索/工具 → 回答 | 开始 → 处理 → 结束 |
| 输出是什么 | 流式消息 + 引用 + 会话变量 | 结构化 JSON（结束节点定义） |
| 适合谁 | 智能客服、知识问答、多轮引导 | 定时批处理、数据加工、系统集成 |

另外三点：

1. **类型不可改**：创建前用一句话说明「类型决定可用节点、是否有会话、发布契约，创建后不可更改」。
2. **起步模板随类型联动**：Chatflow 默认「知识库问答」，Workflow 默认「结构化抽取」。
3. **边界兜底**：弹窗底部固定提示，避免用户在工作室里找 Agent。

## 五、归属规则（建议写进实现）

| 想做的事 | 去哪 |
|---|---|
| 多轮对话、工具调用、子智能体 | 智能体 → 智能体流程 |
| 文档解析入库 | 智能体 → Ingestion pipeline |
| 面向用户的对话式应用（有会话、有记忆） | 工作室 → Chatflow |
| 面向系统的数据加工、批处理、集成 | 工作室 → Workflow |
| 看所有运行记录 | 工作室 → 运行日志 |

## 六、已定 decisions（2026-10-20 确认）

### 6.1 类型数量：弹窗 4 个，不是 5 个

排查发现**原生就是 3 个类型**，不是 2 个：

| 来源 | FlowType | 卡片文案 | 说明 |
|---|---|---|---|
| 原生 | `Agent` | 智能体流程 | `agent_canvas` |
| 原生 | `Flow` | 数据管道 | `dataflow_canvas`（Ingestion pipeline） |
| 原生 | `Compiler` | 编译算子 | 选中后跳转编译模板页，**不创建应用** |
| 新增 | `Chatflow` | 对话流（Chatflow） | `chatflow_canvas` |
| 新增 | `Workflow` | 任务流（Workflow） | `workflow_canvas` |

3 + 2 = 5，其中「编译算子」既不是创建应用、也和另外四个不同源。

**已定**：把「编译算子」移出创建弹窗，改成列表页 `+` 下拉里的独立入口（带分隔线），
空状态卡片里也补一个入口。移出后弹窗正好是 4 个：2 个原生 + 2 个新增。

### 6.2 命名去冲突

原来 Agent 显示「工作流」、新增 Workflow 显示「Workflow（任务式）」，两个卡片字面撞车。

**已定命名**：

| 类型 | 中文名 | 英文/标识 |
|---|---|---|
| Agent | 智能体流程 | Agent canvas |
| Chatflow | 对话流 | Chatflow |
| Workflow | 任务流 | Workflow |
| 数据管道 | 数据管道 | Ingestion pipeline |
| 编译算子 | 编译算子 | Compilation operator |

i18n key 一并正名，避免「key 名和文案不一致」继续累积：
`flow.tabList.workflow` → `flow.tabList.agentCanvas`，`flow.workflow` → `flow.taskFlow`。

### 6.3 附带修掉的 i18n bug

渲染处是 `t(\`flow.${config.labelKey}\`)`（`create-agent-form.tsx:86`），会自动补 `flow.` 前缀。
之前新增的两项把 labelKey 写成了 `flow.chatflow` / `flow.workflow`，最终渲染成
`flow.flow.chatflow` / `flow.flow.workflow` 直接暴露在界面上。
词典里 `flow.chatflow` / `flow.workflow` 本来就存在，labelKey 去掉多余前缀即可。

**约定**：labelKey 一律写「不带命名空间前缀的相对 key」，前缀由渲染处统一补。

## 七、仍待确认

1. **Chatflow / Workflow 是否进一步独立成「工作室」模块？** 当前实现仍与智能体共用一个创建弹窗（4 个卡片）。
   若按本文第二节的完整方案走，弹窗只留 2 个原生项，新增两项移到工作室独立入口。需确认是否本期做。
2. **「工作室」命名**：也可叫「应用」「编排」「自动化」，取决于客户对对话流/任务流的认知。
3. **Agent 是否也要进工作室**：Dify 是三类都放 Studio 下；当前按「智能体保留不动」处理。
4. **空态与占位**：首次进入工作室若没有任何应用，应直接给「空白画布 / 从模板开始」两个入口。
