## 一、总体设计

### 1.1 核心挑战：两条链路两套表

这是本详设要解决的头号问题。对话数据散落在两套表里：

| 维度 | 链路 1（聊天 Chat Pipeline） | 链路 2（对话流/工作流 Agent 运行时） |
|---|---|---|
| 会话表 | `conversation`（entity.ChatSession） | `api_4_conversation`（entity.API4Conversation） |
| 消息表 | `conversation_message` | `api_4_conversation_message` |
| 客户 id | `user_id`（size 255） | `user_id` + `exp_user_id` |
| 会话耗时 | ❌ 无 | ✅ `duration`（float） |
| 轮次 | 需 count | ✅ `round` |
| token | ❌ 无 | ✅ `tokens` + `agent_run` |
| 消息级评价 | ✅ `thumb_up`(bool) + `feedback` | ✅ 同（内嵌 ConversationMessageFields） |
| 会话级点赞 | ❌ | ✅ `thumb_up`(int) |

**好消息**：两条链路的消息表都内嵌了 `ConversationMessageFields`
（`internal/entity/conversation_history.go`），字段结构一致（`role`/`content`/`thumb_up`/`feedback`/`created_at`）。

**结论**：不需要改数据模型去「统一」两套表（迁移风险大、收益低），而是**在服务层做统一访问抽象**，
把两套表的数据映射到同一个 `ConsultationLogItem` 结构。

### 1.2 分层

```
Handler（analytics.go）
   │
Service（analytics_service.go）  ← 统一访问层，屏蔽两表差异
   │        │
   ├─ 咨询日志查询：ChatLogQuery + CanvasLogQuery → 合并
   │        │
   └─ 报表聚合：StatsQuery → 指标
   │
DAO（conversation / api_4_conversation / agent_run）
```

### 1.3 数据延迟：T+1，不建实时链路

PRD 定的是 T+1。MVP 直接用**实时聚合查询**（数据量可控 + 时间范围必选 + 索引支撑），
不做预计算汇总表。数据量增长（会话 > 100 万）后，演进到预计算（见 §7）。

## 三、统一访问层设计

### 3.1 统一结构

```go
// internal/entity/analytics.go
type ConsultationLogItem struct {
    Chain        string    // "chat" | "canvas"
    SessionID    string
    CustomerID   string    // user_id
    AppID        string    // dialog_id（两表同名字段）
    AppName      string
    StartTime    time.Time
    Rounds       int       // 轮次
    Rating       string    // "good" | "bad" | "none"
    Feedback     string    // 最新一条文字反馈
    DurationMS   int       // 响应耗时（链路1=首包，链路2=总耗时）
    FirstQuestion string   // 首问摘要
}

type ConsultationDetail struct {
    SessionID  string
    CustomerID string
    AppName    string
    Turns      []Turn
}

type Turn struct {
    Position   int
    Role       string    // user / assistant
    Content    string
    ThumbUp    *bool
    Feedback   string
    DurationMS int       // assistant 才有
    References []string  // 引用 chunk 摘要
}
```

### 3.2 查询实现（Go 层合并，不用 SQL UNION）

两表字段语义有差异（链路 1 无 duration/round，链路 2 有），SQL UNION 反而别扭。
**分别查询，Go 层合并排序分页**：

```go
func (s *AnalyticsService) ListConsultations(ctx, filter) ([]ConsultationLogItem, int64, error) {
    var items []ConsultationLogItem

    // 链路 1：conversation + 消息聚合
    chatItems, _ := s.listChatLogs(ctx, filter)      // count rounds / 首问 / 评价
    // 链路 2：api_4_conversation（duration/round 直接取）
    canvasItems, _ := s.listCanvasLogs(ctx, filter)

    items = append(items, chatItems...)
    items = append(items, canvasItems...)

    // 统一按 StartTime 倒序，再分页
    sort.SliceStable(items, func(i, j int) bool { return items[i].StartTime.After(items[j].StartTime) })
    total := int64(len(items))
    return paginate(items, filter.Page, filter.Size), total, nil
}
```

### 3.3 链路 1 查询（补聚合）

链路 1 的 `conversation` 无 round/duration，需要从消息表聚合：

```sql
SELECT
  c.id, c.user_id, c.dialog_id, c.create_time,
  COUNT(m.conversation_id) AS rounds,
  MAX(CASE WHEN m.role='assistant' AND m.duration_ms>0 THEN m.duration_ms END) AS duration_ms,
  (SELECT content FROM conversation_message
     WHERE conversation_id=c.id AND role='user'
     ORDER BY position ASC LIMIT 1) AS first_question
FROM conversation c
LEFT JOIN conversation_message m ON m.conversation_id = c.id
WHERE c.tenant_id = ? AND c.create_time BETWEEN ? AND ?
GROUP BY c.id
ORDER BY c.create_time DESC
```

评价聚合（好评/差评/未评）单独一条查询或子查询，取该会话内 assistant 消息的最新 thumb_up。

### 3.4 链路 2 查询（直取）

```sql
SELECT
  a.id, a.user_id, a.dialog_id, a.create_time,
  a.round AS rounds, a.duration, a.thumb_up
FROM api_4_conversation a
WHERE a.tenant_id = ? AND a.create_time BETWEEN ? AND ?
ORDER BY a.create_time DESC
```

> 注意：`api_4_conversation` 的 `thumb_up` 是 int（会话级），与链路 1 的消息级 bool 口径不同。
> 统一评价口径以**消息级**为准（两表消息都内嵌 `ThumbUp bool`），会话级 int 仅作参考不参与好评率。

### 3.5 详情查询

会话详情展开完整对话流，从对应链路的消息表按 `position` 升序读取：

```go
func (s *AnalyticsService) GetConsultationDetail(ctx, sessionID, chain) (*ConsultationDetail, error) {
    switch chain {
    case "chat":
        msgs := s.msgDAO.ListByConversation(sessionID)          // conversation_message
    case "canvas":
        msgs := s.apiMsgDAO.ListByConversation(sessionID)       // api_4_conversation_message
    }
    // 组装 Turn，附引用（conversation_reference / api_4_conversation_reference）
}
```

## 四、埋点设计

### 4.1 链路 1：首包延迟（本次必做）

**位置**：`internal/service/chat_pipeline.go` 的 `send()`（第 1147 行）与消息落库处。

**实现**：

```go
// AsyncChat 内，进入 LLM 前
reqStart := time.Now()

// 新增：会话级首包计时器，挂在 AsyncChat 的局部作用域
var firstAnswerAt time.Time

// send() 内，首个非空 answer delta
if firstAnswerAt.IsZero() && result.Answer != "" {
    firstAnswerAt = time.Now()
}

// 消息落库时（assistant 消息）
durationMS := 0
if !firstAnswerAt.IsZero() {
    durationMS = int(firstAnswerAt.Sub(reqStart).Milliseconds())
}
// 写入 conversation_message.duration_ms
```

**关键点**：

| # | 细节 | 处理 |
|---|---|---|
| 1 | 只对 `role=assistant` 消息有意义 | user 消息 duration_ms 恒 0 |
| 2 | 流式落库时机 | duration_ms 需在消息**最终落库**时写入，此时首包早已发出，用局部变量传递 |
| 3 | 存量消息 | duration_ms=0，统计时 `WHERE duration_ms>0` 过滤 |
| 4 | 失败/空响应 | firstAnswerAt 仍为零值，duration_ms 写 0，标记无响应 |

**落库位置**：需定位链路 1 写 `conversation_message` 的 DAO 调用，把 `durationMS` 传进去。
若落库逻辑封装较深，可在 `AsyncChatResult` 增加内部字段 `FirstTokenAt time.Time`（不序列化），
随最终结果带出。

### 4.2 链路 2：首包延迟（V1.1，可选）

链路 2 已有 `duration`（总耗时），若需统一「首包延迟」口径，在 `agent_run` 补
`first_token_ms`，在 `RunAgent` 事件循环的首个 `message` 事件处计时。
**V1.0 先不补**，报表对链路 2 用总耗时并明确标注口径。

## 五、报表聚合

### 5.1 指标 SQL（近 N 天，按应用可选）

```sql
-- 咨询量（会话数）
SELECT COUNT(*) FROM (
  SELECT id FROM conversation WHERE tenant_id=? AND create_time BETWEEN ? AND ?
  UNION ALL
  SELECT id FROM api_4_conversation WHERE tenant_id=? AND create_time BETWEEN ? AND ?
) t;

-- 咨询客户数（去重，跨两表）
SELECT COUNT(DISTINCT user_id) FROM (
  SELECT user_id FROM conversation WHERE ...
  UNION
  SELECT user_id FROM api_4_conversation WHERE ...
) t;
```

> 客户数去重必须跨两表 UNION 后再 DISTINCT——同一个 user_id 可能既在聊天又在对话流咨询过。

```sql
-- 好评率（消息级，跨两表）
SELECT
  SUM(CASE WHEN thumb_up=1 THEN 1 ELSE 0 END) / NULLIF(SUM(CASE WHEN thumb_up IS NOT NULL THEN 1 ELSE 0 END), 0)
FROM (
  SELECT thumb_up FROM conversation_message WHERE role='assistant' AND ...
  UNION ALL
  SELECT thumb_up FROM api_4_conversation_message WHERE role='assistant' AND ...
) t;

-- 成功率（链路2 专用，链路1 无 status）
SELECT SUM(status='succeeded') / COUNT(*) FROM agent_run WHERE ...;
```

### 5.2 指标口径映射

| 指标 | 实现 |
|---|---|
| 咨询量 | 两表会话数相加 |
| 客户数 | 两表 user_id 去重 |
| 响应速度 | 链路 1 `avg(duration_ms where >0)`；链路 2 `avg(duration)`；分链路返回，前端分链路标注 |
| 好评率 | 两表消息级 thumb_up 合并算 |
| 成功率 | 仅 agent_run（链路 2）；链路 1 无，显示「—」 |
| 平均轮次 | 链路 1 消息 count 平均；链路 2 `avg(round)` |
| token | 链路 2 `agent_run` 求和；链路 1 无 |

### 5.3 趋势

按日聚合，`GROUP BY DATE(create_time)`，返回 7/30 个点的数组，前端画图。
复用 5.1 的 SQL 加 `GROUP BY` 即可，无需预计算。

### 5.4 性能保障

| 项 | 措施 |
|---|---|
| 时间范围必选 | 强制，默认近 7 天，上限 90 天 |
| 索引 | `conversation(tenant_id, create_time)`、`api_4_conversation(tenant_id, create_time)`、消息表 `(conversation_id, position)` |
| 全表扫防护 | 导出限 10 万行；超限分批 |
| 演进 | 会话 >100 万时引入 T+1 预计算汇总表（§7） |

## 九、测试方案

### 9.1 单元测试

| 用例 | 断言 |
|---|---|
| 两链路合并 | 构造 chat + canvas 各 N 条，合并后按时间倒序、总数正确 |

### 9.2 集成测试

| 场景 | 断言 |
|---|---|
| 链路 1 对话产生咨询日志 | 聊天后能在咨询日志查到，chain=chat，含首问摘要 |
| 链路 2 对话产生咨询日志 | 对话流后能查到，chain=canvas，duration 取 api_4_conversation |
| 详情对话流 | 展开后每轮 role/content/评价/耗时正确 |
| 评价联动 | 用户在聊天页点 👍 后，咨询日志评价列变「好评」 |
| 跨租户隔离 | 访问他人数据 404 |
| 导出 | CSV 行数与列表一致，敏感字段脱敏 |

| 场景 | 通过标准 |
|---|---|

## 十、风险

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 两链路字段语义差异导致口径混乱 | 4 | 4 | 统一结构体显式标注 chain；报表分链路返回；PRD 口径逐条对齐 |
| R2 | 「准确率」代理口径被误用 | 4 | 4 | 界面明示「好评率（近似准确率）」；V2 人工标注 |
| R3 | 大表实时聚合拖慢库 | 3 | 3 | 时间范围必选 + 索引 + 导出限流；V2 预计算 |
| R4 | 链路 1 埋点位置遗漏非流式路径 | 2 | 3 | 覆盖 stream 与 non-stream 两分支；集成测试双路径 |
| R5 | user_id 语义不清导致客户数失真 | 3 | 3 | 待确认 Q1；确认前报表标注口径 |
