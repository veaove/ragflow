## 一、背景与目标

### 1.1 背景

RAGFlow 现有画布只有**一种应用形态** `agent_canvas`：对话式与任务式靠 Begin 节点的 `mode`（conversational / task / Webhook）在**前端**区分，后端执行链路完全一致。这带来四个具体问题：

1. **做不了真正的 Workflow**。没有 End 输出节点，末端隐式取「第一个非空输出」，无法定义稳定的 API 响应结构；无法做无对话的批处理、定时任务、系统间集成。
2. **Chatflow 不成立**。没有 Answer 节点与流式回答语义，没有会话变量（现在 `env.*` 同时承担环境变量与会话变量），多轮记忆只能靠会话 DSL 副本，无法按 Conversation 持久化与回读。
3. **发布契约单一**。只有 Agent run 一种接口，Workflow 与 Chatflow 没有各自的请求/响应契约，也没有每应用 API Key 与限流。
4. **运行不可排障**。节点执行记录只存在实时 SSE 里，刷新即丢；版本只能看不能回滚。

与此同时，RAGFlow 的底层并不弱：React Flow 画布、40 个 Agent 面板算子、Go 执行引擎、循环/并行/中断恢复、变量池、知识检索与引用溯源都已具备。真正缺的是**形态、契约与可观测**，不是重写引擎。

### 1.2 目标

| 目标 | 说明 | 衡量方式 |
|---|---|---|
| 两种形态独立 | Workflow 与 Chatflow 成为独立应用类型，各自有节点限制、输入输出契约、发布 API | 创建时可选类型；发布前按形态校验；API 路径分流 |
| 核心节点补齐 | End、Answer、独立 LLM、参数提取、模板转换可用 | 5 个节点在面板可添加、可配置、可试运行 |
| 变量双轨 | 环境变量只读、会话变量按 Conversation 持久化 | 环境变量不可被赋值节点写入；会话变量跨轮可读 |
| 变更可回滚 | 发布生成不可变快照，支持恢复到草稿 | 任意历史版本可恢复，恢复不直接影响线上 |
| 运行可追溯 | 每次运行有 run_id，节点执行记录持久化 | 刷新页面后仍能查看节点 IO、耗时、错误 |
| 发布可集成 | Workflow / Chatflow 各有运行 API，每应用独立 Key | 第三方可用 curl 调通；Key 可轮换、可限流 |

### 1.3 非目标（本期不做）

- **不移植 Dify 的 graphon 运行时**。Dify 的节点执行已外置为 `graphon==0.7.0`，本 PRD 只做能力对齐，不做代码移植。
- **不做 Dify DSL 直接导入**。节点类型与字段映射层工作量大，本期只支持 RAGFlow 自有 DSL 导入导出。
- **不做定时触发器、插件事件触发器**。本期只保留 Webhook 触发（现有能力）。
- **不做多人实时协作、评论、CRDT**。
- **不做插件市场、自定义节点 SDK**。节点仍为编译期注册。
- **不做 Agent v2 运行时**。保留现有 Agent 能力。

> **假设（可推翻）**：现有 `agent_canvas` 应用全部按 `app_mode=agent` 处理，不做自动迁移为 Chatflow。若客户希望存量对话式应用直接转为 Chatflow，需单独评估提示词与节点差异。

## 二、名词与术语

| 术语 | 定义 |
|---|---|
| Workflow | 无对话的工作流应用，`Start → ... → End`，输出结构化 JSON |
| Chatflow | 对话式工作流应用，`Start → ... → Answer`，输出流式消息并绑定会话 |
| Agent | 现有智能体形态，自主规划、工具调用、子智能体，继续保留 |
| Start / Begin | 入口节点，声明输入字段；Chatflow 额外注入 `sys.query` 与会话变量 |
| End | 出口节点，声明输出字段；只有 Workflow 可用 |
| Answer | 回答节点，流式输出并携带引用；只有 Chatflow 可用 |
| 变量池 | 运行时保存各节点输出的结构，按节点 ID + 参数路径寻址 |
| 系统变量 | `sys.*`，由运行时注入，如 `sys.query`、`sys.user_id`、`sys.files` |
| 环境变量 | `env.*`，应用级配置，发布时快照，运行时只读 |
| 会话变量 | `conversation.*`，按 Conversation 持久化，可读可写，不跨会话 |
| 节点输出变量 | `{node_id@param.path}`，引用上游节点输出 |
| 版本快照 | 发布时生成的不可变 DSL 副本，带版本号与发布人 |
| Run | 一次运行实例，含输入、输出、状态、耗时、token |
| NodeExecution | 一次运行中某个节点的执行记录，含 inputs / process / outputs / error |
| DSL | 应用的图定义（节点、边、配置、变量）序列化结果 |

### 3.3 约束

- 必须在现有 React Flow 画布与 Go `internal/agent` 引擎上增量改造，不引入新运行时。

- 发布必须原子化：全部成功或全部回滚，不允许部分生效。
- 代码节点沿用现有沙箱后端，不引入 Dify sandbox。

## 四、方案对比与选型说明

### 4.1 三种可选路径

| 方案 | 实现成本 | 开发复杂度 | 用户体验 | 风险 | 上线时间 | 综合评价 |
|---|---|---|---|---|---|---|
| A. 复用现有引擎，新增 `app_mode` + 补节点 | 中 | 中 | 好：画布与现有体验一致 | 中：需改编译/运行分流 | 中 | **推荐** |
| B. 移植 Dify graphon + 独立运行时 | 高 | 高 | 中：交互与现有不一致 | 高：双运行时、双数据模型 | 慢 | 不推荐 |
| C. 只做前端包装，后端不改 | 低 | 低 | 差：Workflow 无法真正运行 | 高：无法发布 API | 快 | 不可行 |

### 4.2 推荐结论

**推荐方案 A**，理由：

1. RAGFlow 已有 40 个 Agent 算子、变量池、循环/并行、中断恢复，缺的只是 5 个节点与形态契约，改造成本远低于重写。
2. Dify 的节点执行已在 `graphon` 包内，移植等于引入第二套运行时与依赖，与 RAGFlow「Go 单实现」的方向冲突。
3. 方案 A 可以保证现有 Agent 应用零改动，风险可控。
4. 方案 C 无法提供稳定的 API 契约，不满足「把 Workflow 做进来」的核心诉求。

### 4.3 演进路径

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| V1.0 | 形态 + 5 节点 + 变量双轨 + 运行记录 + 版本回滚 + 双 API | 本期 |
| V1.1 | 子工作流、HTTP 补全、失败分支、变量检查器增强 | 客户出现「工作流复用」「第三方系统集成」诉求 |
| V2.0 | 定时/插件触发、单步断点、版本 diff、标注回流 | 客户出现「定时任务」「效果评测」诉求 |
| 远期 | Dify DSL 兼容、多人协作、插件市场 | 有存量 Dify 迁移或生态诉求时单独立项 |

## 五、用户角色与使用场景

### 5.1 角色

| 角色 | 职责 | 典型诉求 |
|---|---|---|
| 应用开发者（业务运营 / 算法） | 搭图、配节点、调提示词、发布 | 快速把业务流程变成可运行应用 |
| 应用使用者（客服 / 业务人员） | 用 WebApp 或 API 运行应用 | 稳定、可追溯、出错能定位 |
| 系统管理员 | 权限、密钥、审计、配额 | 可治理、可审计、不越权 |
| 集成方（第三方系统） | 通过 API 调用 Workflow/Chatflow | 契约清晰、鉴权简单、错误码明确 |

### 5.2 用户故事

**US-01 搭一个 Workflow**
作为应用开发者，我想要从空白画布拖出「开始 → 知识检索 → 大模型 → 结束」，以便把「每日净值播报生成」做成可被定时系统调用的接口。
- Given 我创建了 Workflow 应用，When 我拖入 4 个节点并连线，Then 画布校验通过，结束节点可配置输出字段。
- Given 我点击试运行，Then 底部面板展示每个节点的输入输出与耗时。

**US-02 搭一个 Chatflow**
作为应用开发者，我想要搭「开始 → 知识检索 → 大模型 → 回答」，并把本轮主题写入会话变量，以便下一轮能接上上下文。
- Given 我创建了 Chatflow，When 我添加回答节点，Then 回答节点支持流式输出与引用。
- Given 我在调试预览里连续问两个问题，Then 第二轮能读到第一轮写入的会话变量。

**US-03 发布并调用**
作为集成方，我想要拿到 Workflow 的接口地址与独立 API Key，以便在我的系统里调用。
- Given 应用已发布，When 我打开发布面板，Then 能看到 endpoint、API Key、curl 示例。
- Given 我用错误 Key 调用，Then 返回 401 且不泄露应用信息。

**US-04 回滚**
作为应用开发者，我想要把线上版本回滚到上一版，以便发布出错时快速恢复。
- Given 线上是 v3，When 我在版本历史里对 v2 点「恢复」，Then v2 内容写回草稿，线上仍是 v3。
- Given 我确认发布草稿，Then 线上变为新的 v4，内容与 v2 一致。

**US-05 排障**
作为应用使用者，我想要看到某次运行为什么失败，以便定位是模型超时还是变量为空。
- Given 一次运行失败，When 我打开运行详情，Then 能看到失败节点、错误信息、该节点输入。

**US-06 权限隔离**
作为管理员，我想要限制运营只能编辑自己负责的应用，以便避免误改生产应用。
- Given 运营 A 只有应用 X 的编辑权限，When 他打开应用 Y，Then 只能查看不能编辑。

## 六、功能需求

> 编号规则：`FR-模块-序号`。状态词统一：**必须（shall）** / **应该（should）** / **可以（may）** / **禁止（must not）**。

### FR-01 应用形态

| 编号 | 需求 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-01-01 | 创建三种应用 | 创建时必须选择 Workflow / Chatflow / Agent；类型创建后禁止修改 | Given 选择 Workflow，Then 进入 Workflow 画布，节点面板不含 Answer；Given 选择 Chatflow，Then 节点面板不含 End |
| FR-01-02 | 形态级节点限制 | Chatflow 禁止 End 与触发器；Workflow 禁止 Answer；Start 与 Trigger 二选一 | Given 在 Workflow 中尝试添加 Answer，Then 该节点不可见或置灰并提示原因 |
| FR-01-03 | 应用列表 | 必须展示名称、类型、状态、版本、最近运行、更新时间；支持按类型/状态筛选与搜索 | Given 筛选 Chatflow，Then 只展示 Chatflow 应用 |
| FR-01-04 | 应用设置 | 必须支持名称、图标、描述、权限；Chatflow 额外支持开场白与建议问题 | Given 修改开场白并发布，Then WebApp 显示新开场白 |
| FR-01-05 | 应用归档 | 已发布应用可以归档，归档后不可运行但保留历史 | Given 归档应用，Then 列表中默认隐藏，API 返回「应用已归档」 |

### FR-02 画布与编排

| 编号 | 需求 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-02-01 | 节点面板 | 必须按分类展示可添加节点，支持搜索；新增节点必须标注「增量」 | Given 打开面板，Then 看到入口出口/模型/知识/逻辑/数据/集成/人机协同分组 |
| FR-02-02 | 拖拽与连线 | 必须支持拖入、连线、删除、撤销重做；禁止非法上下游 | Given 从 End 反向连到 Start，Then 连线被拒绝并提示 |
| FR-02-03 | 右键菜单 | 画布与节点必须支持右键添加、删除、复制 | Given 右键节点，Then 出现删除/复制/查看日志 |
| FR-02-04 | 容器节点 | Iteration / Loop 必须支持子图与进出点 | Given 拖入 Iteration，Then 自动生成 start 与 exit 子节点 |
| FR-02-05 | 画布校验 | 发布前必须校验：唯一 Start、形态允许的出口、无孤立节点、变量引用可达、必填配置完整 | Given 存在孤立节点，Then 校验失败并定位到该节点 |
| FR-02-06 | 自动布局 | 应该支持一键整理布局 | Given 点击自动布局，Then 节点按拓扑分层排列 |

### FR-03 节点能力

| 编号 | 需求 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-03-01 | End 节点 | Workflow 必须且只能有一个可达 End；必须声明输出字段与类型；输出字段构成 API 响应体 | Given 未配置任何输出字段，Then 发布被阻止并提示 |
| FR-03-02 | Answer 节点 | Chatflow 必须至少有一个可达 Answer；必须支持流式、引用、Markdown 开关；内容可为变量 | Given 回答内容引用 `{llm@answer}`，Then 运行时流式输出该变量 |
| FR-03-03 | LLM 节点（前端补齐） | 后端 `component/llm.go` 已实现，本期必须补齐前端表单并纳入 Workflow/Chatflow 节点面板；支持模型、温度、TopP、系统/用户提示词、输出变量、结构化输出开关 | Given 在 Workflow 画布添加 LLM 节点并配置 JSON Schema，Then 运行时输出按 Schema 校验 |
| FR-03-04 | 参数提取节点 | 必须支持字段列表、类型、必填、描述；输出结构化对象；低置信字段必须标注 | Given 输入文本缺少必填字段，Then 该字段为空并标注「未提取到」 |
| FR-03-05 | 模板转换节点 | 必须支持 Jinja 语法与变量插入；输出字符串 | Given 模板含 `{{ name }}`，Then 运行时替换为变量值 |
| FR-03-06 | 知识检索节点 | 复用现有检索；必须支持知识库、TopK、阈值、引用元数据开关 | Given 开启引用，Then 输出包含 doc_id、chunk_id、原文片段 |
| FR-03-07 | 逻辑节点 | 条件分支、迭代、循环、变量聚合、变量赋值、列表操作复用现有能力 | Given 条件分支配置两个分支，Then 只走命中的分支 |

### FR-11 AI 功能六模块专项（LLM / 参数提取 / 问题分类）

| 模块 | 本需求的具体要求 |
|---|---|
| 任务定义 | 谁：应用开发者编排、业务用户运行；何时：应用运行时；基于什么：上游变量 + 提示词 + 知识检索结果；做什么：生成文本、结构化抽取、分类；帮到哪一步：**生成候选内容或结构化结果，不代替人工决策**；人工确认点由应用自身决定 |
| 输入契约 | 输入必须来自显式变量引用；缺失必填变量时节点失败并提示变量名；超长输入必须按配置截断并标注「已截断」；知识检索结果必须携带来源，冲突时以高相似度且较新的结果优先，并在输出中保留来源 |
| 输出契约 | 必须声明输出变量名与类型；结构化输出必须给 JSON Schema 并运行时校验；禁止输出未定义字段；引用必须以 `doc_id + chunk_id + 原文片段` 形式返回，可溯源 |
| 质量标准与验收样本 | 建立 200 条评测集，覆盖正常、缺失字段、多义、超长、无检索结果、拒答；文本节点人工评审可用率 ≥80%；结构化抽取字段准确率 ≥85%；分类准确率 ≥85%；引用可溯源率 100%；格式合规率 ≥99% |
| 异常降级与人工接管 | 模型超时/限流：按节点重试策略重试，仍失败走异常策略（终止/默认值/失败分支）；输出不符合 Schema：重试 1 次后失败并返回原始输出；检索无结果：明示「未找到依据」，禁止编造；低置信抽取：字段留空并标注，不猜测 |
| 行为约束三层 | **Always do**：Schema 校验、引用溯源、超长截断标注；**Ask first**：参数提取低置信字段先给草稿，由下游或人工确认；**Never do**：不得绕过权限读写数据、不得编造引用、不得把密钥写入提示词或日志 |
| 反馈与版本闭环 | 每次运行记录模型版本、提示词版本、知识库版本、节点配置版本，支持按版本复现与对比；本期提供「运行结果 → 版本」的可追溯链路，标注「可用/不可用」与数据集回流列入 V2.0 |

## 八、业务流程与状态流转

### 8.1 主流程

```
创建应用（选形态）
   │
   ▼
编排画布（节点 + 连线 + 变量）
   │
   ▼
试运行（整图 / 单节点 / Chatflow 预览）
   │  ├─ 失败 ──► 看运行面板定位 ──► 修改 ──► 重新试运行
   │  └─ 成功
   ▼
发布校验（形态 + 出口 + 变量 + 密钥）
   │  ├─ 不通过 ──► 定位修复
   │  └─ 通过
   ▼
生成版本快照（vN） ──► 线上生效
   │
   ▼
调用（API / WebApp / 嵌入）──► 运行记录 ──► 排障 / 回滚
```

### 8.2 状态机

**应用状态**

| 状态 | 触发 | 允许操作 |
|---|---|---|
| `draft` | 创建后 | 编辑、试运行、发布、删除 |
| `published` | 发布成功 | 编辑（生成新草稿）、试运行、回滚、归档 |
| `archived` | 归档 | 查看、恢复；禁止运行与发布 |

**运行状态**

| 状态 | 说明 | 终态 |
|---|---|---|
| `queued` | 排队中 | 否 |
| `running` | 执行中 | 否 |
| `succeeded` | 成功 | 是 |
| `failed` | 失败 | 是 |
| `stopped` | 用户停止 | 是 |
| `partial` | 部分成功（Iteration 中部分失败） | 是 |

**节点执行状态**

| 状态 | 说明 |
|---|---|
| `waiting` | 等待上游 |
| `running` | 执行中 |
| `succeeded` | 成功 |
| `failed` | 失败 |
| `skipped` | 未走到的分支 |
| `retrying` | 重试中 |

**发布状态**

| 状态 | 说明 |
|---|---|
| `validating` | 校验中 |
| `publishing` | 写入快照 |
| `succeeded` | 成功 |
| `failed_rolled_back` | 失败并回滚 |

### 8.3 发布冲突与回滚

- 发布前逐条比对「草稿基线版本」与线上版本；不一致说明期间有人发布过，必须提示冲突并要求基于最新版本重新发布。
- 发布失败必须回滚到发布前快照，线上不受影响。
- 回滚 = 把历史版本内容写回草稿 + 走一次正常发布；回滚本身也生成新版本，保留审计。

## 十、权限与安全

### 10.1 权限矩阵

| 操作 | 创建者 | 应用成员（编辑） | 应用成员（只读） | 租户管理员 | 其他租户 |
|---|---|---|---|---|---|
| 查看应用 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 编辑画布 | ✅ | ✅ | ❌ | ✅ | ❌ |
| 试运行 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 发布 / 回滚 | ✅ | ✅ | ❌ | ✅ | ❌ |
| 管理 API Key | ✅ | ❌ | ❌ | ✅ | ❌ |
| 查看运行日志 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 删除 / 归档 | ✅ | ❌ | ❌ | ✅ | ❌ |

### 10.2 安全规则

- 所有接口校验 `tenant_id` + `app_id` 归属；越权与不存在统一返回 404，防跨租户探测。
- API Key 只存哈希，明文仅在创建时展示一次；支持禁用与轮换。
- 环境变量中的 `secret` 类型加密存储，导出 DSL 时剔除，日志中掩码。
- 代码节点必须在沙箱执行，限制网络与文件系统；HTTP 节点必须做 SSRF 防护（禁止访问内网与元数据地址）。
- 发布、回滚、删除、Key 重置必须二次确认。
- 审计日志保留 ≥180 天，包含操作人、时间、对象、前后值。

## 十一、异常处理清单

| 场景 | 处理 | 用户提示 |
|---|---|---|
| Workflow 缺少 End | 阻止发布 | 「Workflow 必须配置结束节点」 |
| Chatflow 缺少 Answer | 阻止发布 | 「Chatflow 至少需要一个可达的回答节点」 |
| 添加形态禁止的节点 | 隐藏或置灰 | 「当前形态不支持该节点」 |
| 存在孤立节点 | 阻止发布并定位 | 「节点 X 未连接」 |
| 变量引用已删除节点 | 阻止发布并高亮 | 「变量引用失效：{node@var}」 |
| 环境变量被赋值节点写入 | 阻止保存 | 「环境变量只读，请使用会话变量」 |
| 会话变量在 Workflow 中使用 | 选择器不展示 | 「Workflow 不支持会话变量」 |
| 变量为空导致节点失败 | 节点失败，记录变量名 | 「必填变量 X 为空」 |
| LLM 超时 | 按重试策略重试，仍失败走异常策略 | 「模型调用超时」 |
| LLM 输出不符合 Schema | 重试 1 次后失败，返回原始输出 | 「输出不符合预期结构」 |
| 检索无结果 | 继续执行，明示无依据 | 「未检索到相关依据」 |
| 代码节点执行超时 | 终止沙箱，节点失败 | 「代码执行超时」 |
| HTTP 节点访问内网 | 拒绝请求 | 「目标地址不被允许」 |
| 并发编辑冲突 | 后保存者收到冲突 | 「应用已被他人修改，请刷新后重试」 |
| 发布时线上已被他人发布 | 拒绝并提示基于最新版本 | 「线上版本已变更，请重新发布」 |
| 发布中途失败 | 回滚到发布前快照 | 「发布失败，已回滚，线上未受影响」 |
| API Key 无效/禁用 | 返回 401/403 | 「API Key 无效或已禁用」 |
| 超过 RPM | 返回 429 | 「请求过于频繁，请稍后重试」 |
| 应用已归档 | 拒绝运行 | 「应用已归档，无法运行」 |
| 会话已过期 | 新建会话或返回 404 | 「会话不存在或已过期」 |
| 网络中断 | 保留草稿，提示重试 | 「网络异常，修改未保存」 |
| 权限不足 | 阻止操作 | 「无权限执行该操作」 |
| 模型配额不足 | 节点失败，提示配额 | 「模型配额不足，请联系管理员」 |

### 13.2 待确认

1. **应用形态是否保留 Agent 第三类？** 本 PRD 假设保留；若客户要求合并，需重新评估迁移。
2. **Chatflow 是否强制 Answer？** 本 PRD 要求发布时至少一个可达 Answer。
3. **Workflow 是否强制 End？** 本 PRD 要求必须；否则无法定义输出契约。
4. **会话变量是否跨会话共享？** 本 PRD 假设不共享；跨会话共享另做「应用变量」。
5. **async 是否接受延后到 V1.1？** 本 PRD 已决策：V1.0 只做 blocking/streaming，避免假异步接口；若客户强需求，需增加 NATS worker 工作包。
6. **HITL 公开 API 是否接受 V1.0 阻止发布？** 本 PRD 已决策：含 UserFillUp 的 Workflow 在 V1.0 不允许发布为公开 API；V1.1 提供 resume。
7. **运行记录与审计的保留期？** 运行记录默认 90 天可配；审计独立保留 ≥180 天。
8. **API Key 消耗谁的模型配额？** 本 PRD 假设归画布 owner；若需归 Key 创建者，需在 `app_api_key` 增加 quota 维度。
9. **是否允许代码节点访问外网？** 本 PRD 假设默认禁止，白名单可配。
10. **是否兼容 Dify DSL？** 本 PRD 不做；若客户有存量迁移需求，需单独立项。
