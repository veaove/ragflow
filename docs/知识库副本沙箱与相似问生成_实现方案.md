> 状态：待评审
> 编写日期：2026-10-19
> 适用项目：RAGFlow（Go 后端 + React 前端）

## 一、结论先行：三个改变方案的技术事实

### 1.1 相似问不需要重算 embedding（利好，显著降低副本成本）

已验证 embedding 的输入文本来自 `concatFields(ck, c.param.Fields)`
（`internal/ingestion/component/tokenizer.go:473`），即配置的 embedding 字段，
**不包含 `question_kwd`**。

同时 `internal/service/chunk/chunk.go:1166-1177` 的更新逻辑是：

```go
if req.Questions != nil {
    // 只覆盖 question_kwd，不触碰向量
    d["question_kwd"] = filteredQuestions
}
```

**因此：副本创建时可直接复用源 chunk 的向量，不需要调用 embedding 模型。**
这让副本方案的成本从「重新解析 + 全量 embedding」降到「元数据复制」。

### 1.2 相似问对检索的影响权重已很高（决定功能价值）

| 环节 | 权重 | 位置 |
|---|---|---|
| 全文检索（BM25） | `question_tks^20` | `internal/service/nlp/query_builder.go:86-94` |
| Rerank | `question_tks` 重复 6 次参与 tsim | `internal/service/nlp/reranker.go:975-990` |

改相似问对召回排序的影响是**可测量的**，这正是沙箱存在的意义。

### 1.3 近义词功能已全栈实现，但用户访问不到（最低成本的交付）

后端 entity / dao / service / handler / router 五层齐全
（`internal/{entity,dao,service,handler}/synonym.go`，含租户校验、按库作用域、缓存失效），
前端有 473 行完整页面 `web/src/pages/synonym-management/index.tsx`，
服务层 6 个 API 全实现 —— **但 `routes.tsx` 未注册路由，全仓库无任何文件 import 它**。

**加一条路由即可上线**，建议作为 P0 先行交付。

## 二、P0 前置修复（不做则后续功能无法验证）

### 2.1 检索结果需返回相似问字段（阻塞性）

**问题**：`internal/service/nlp/retrieval.go:301-398` 构造 resultChunk 时未取
`question_kwd`，导致 `internal/service/dataset/search.go:353` 的
`"question_kwd": "questions"` 键名映射成为死代码。

**后果**：测试时看到某 chunk 被召回，**无法判断是哪条相似问命中的**，
归因分析无从谈起 —— 副本对比也就失去意义。

**改动**：
- `retrieval.go` 的 resultChunk 构造中加入 `question_kwd`
- `retrieval.go:734-745` 的 src 投影列表中加入 `question_kwd`

### 2.2 同义词管理页面注册路由

`web/src/routes.tsx` 新增一条，参照现有写法：

```tsx
{
  path: `${Routes.DatasetBase}/synonym-management/:id`,
  Component: () => import('@/pages/synonym-management'),
}
```

注意该页面组件签名是 `SynonymManagement({ datasetId })`，
需确认路由层如何传入 `datasetId`（参考 `dataset/testing` 的处理方式）。

## 三、功能一：知识库副本 + 审核发布

### 3.1 目标流程

```
生产知识库 KB
    │ ① 创建副本（复用向量，不重算 embedding）
    ▼
副本 KB-DRAFT（草稿态，生产检索不受影响）
    │ ② 调整相似问 / 近义词 / 检索参数
    ▼
    │ ③ 双栏对比测试（检索层 + 问答层）
    ▼
    │ ④ 审核：展示相似问 diff，人工确认
    ▼
   审核通过 ──→ ⑤ 合并回生产 chunk（批量更新 question_kwd）
   审核拒绝 ──→ ⑤ 副本销毁，生产数据完全未动
```

### 3.2 数据模型改动

`Knowledgebase` 表（`internal/entity/dataset.go`）新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `source_kb_id` | varchar | 来源生产库 ID，空表示正常库 |
| `is_draft` | bool | 是否草稿副本 |
| `draft_status` | enum | `pending` / `approved` / `rejected` |
| `draft_diff` | JSON | 相对生产库的改动摘要（chunk_id → 相似问前后值） |
| `base_config` | JSON | 副本创建时的生产库检索配置快照 |

复用已有设计参考：`internal/entity/evaluation.go:65` 的
`EvaluationRun.ConfigSnapshot` 已预留了同类字段。

### 3.3 核心接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/datasets/{kb_id}/drafts` | 创建副本（复制 chunk 元数据 + 复用向量） |
| GET | `/datasets/{id}/drafts/{draft_id}/diff` | 获取相似问 diff |
| POST | `/datasets/{id}/drafts/{draft_id}/publish` | 审核通过，合并回生产 |
| POST | `/datasets/{id}/drafts/{draft_id}/discard` | 废弃副本 |
| GET | `/datasets/{id}/drafts` | 副本列表 |

**发布时的合并动作**：批量调用现有 chunk 更新接口写回 `question_kwd`。
该接口已支持只改相似问不动向量（见 1.1）。

### 3.4 关键风险与对策

| 风险 | 对策 |
|---|---|
| 副本与生产检索结果不一致（配置漂移） | `base_config` 快照 + 对比时锁定同一组检索参数 |
| 副本占存储 | 向量复用不重复计算，元数据增量小；提供副本清理 |
| 生产库在副本期间被他人修改 | publish 时校验源 chunk 的相似问是否仍与 `draft_diff` 的基线一致，不一致则拒绝并提示重新 diff |
| 误把草稿库当生产用 | 列表页明确标记「草稿」；草稿库不出现在 Agent 绑定选择器里 |

## 四、功能二：智能生成相似问 + 相近知识点检测

### 4.1 智能生成相似问

**已有能力**：解析阶段自动生成已实现
（`internal/ingestion/component/extractor.go:840-891` `runAutoQuestions`，
prompt 在 `:172`），由解析配置 `parser_config.auto_questions` 控制数量。

**需补充**：对**已有 chunk** 批量重新生成。

```
入口：知识库设置 → 相似问管理 → 「批量生成」
流程：
  1. 选中目标 chunk（可按文档/状态筛选）
  2. 调 LLM 批量生成（沿用 runAutoQuestions 的 prompt）
  3. 展示生成结果，人工勾选采纳
  4. 采纳的写入 —— 建议默认写入副本而非生产，与功能一闭环
```

**批量生成的工程要点**：
- LLM 调用需限流与断点续跑（chunk 量可能上千）
- 建议复用同义词模块的差异化更新范式
  （`internal/service/synonym.go:66-74` 的 `*[]SynonymWordInput` 指针语义：
  nil=不修改、空数组=清空）

### 4.2 相近知识点检测（入库标记 + 检索实时提示）

#### (a) 入库/管理时批量扫描

**原理**：基于 chunk 已有向量做两两余弦相似度，超阈值判定为疑似冗余。

```
新增接口：
  POST /datasets/{id}/near-duplicates/scan     触发扫描
  GET  /datasets/{id}/near-duplicates          拉取结果列表

返回：
  [{ chunk_a, chunk_b, similarity, doc_a, doc_b, content_a, content_b, status }]
  status: pending（未处理）/ resolved（已确认可共存）
```

**阈值**：建议 0.9 起步，需按实际语料调优。注意分块策略影响 —— 短 chunk 之间
天然更容易高相似。

**处理动作**：合并 / 改写其一 / 标记「允许共存」。

#### (b) 检索时实时提示干扰

在 `/retrieval` 检索结果与问答链路中加入提示：

> 此 query 同时命中了 3 个高度相似的知识点（相似度 0.91~0.95），可能是重复内容，
> 建议合并后再上线。

**实现位置**：前端 `web/src/pages/dataset/testing/testing-result.tsx`
已有三档打分展示（`:15-19`），可直接基于已返回的
`similarity` 做 top-k 内部两两比对，无需新增后端接口。

### 4.3 两者的语义分工（避免功能重叠）

沿用项目既有约定（`docs/demo_huaxia/相似问与别名表实现方案.md:210-221`）：

| | 相似问 | 同义词 |
|---|---|---|
| 挂载对象 | 知识点（chunk） | 词 |
| 作用 | 整句改写，覆盖「换个说法问」 | 实体归一，覆盖「同义表述」 |
| 检索影响 | 全文 ^20 + rerank ×6 | query 侧 token 扩展 |

两者已同时接入检索（`query_builder.go:389/491/545`），可叠加使用。

## 六、分期建议

| 阶段 | 内容 | 预估 | 依赖 |
|---|---|---|---|
| **P0** | 检索返回 question_kwd；同义词页注册路由 | 1~2 天 | 无 |
| **P1** | 副本创建/废弃/发布 + 相似问 diff 审核 | 1~2 周 | P0 |
| **P2** | 双栏对比测试启用（检索层 + 问答层） | 3~5 天 | P1 |
| **P3** | 已有 chunk 批量生成相似问 | 3~5 天 | P1（写入副本） |
| **P4** | 相近知识点扫描 + 检索时干扰提示 | 3~5 天 | P0 |

**建议先做 P0**：成本最低（1~2 天），且「同义词页面可访问」本身就是用户
可感知的交付；同时 `question_kwd` 返回是后面所有归因分析的前提。

  `snapshot|clone|copy` 仅命中 License 注释），本方案的副本能力需从零开发

  直接引用已有向量
- **配置漂移**：副本创建后若生产库被他人修改，发布冲突如何裁决，需产品决策
- 回答「检索层 + 问答层都要」—— 问答层的沙箱还需考虑会话历史是否隔离
