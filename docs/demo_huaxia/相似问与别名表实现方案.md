> 对应需求清单两项：
> 1. 每个标准问可维护多个相似问，支持相似问的管理（新增/修改/删除）

## 二、相似问：已开箱即用，无需开发

### 2.1 底层原理

相似问存放在 chunk 的 `question_kwd` 字段。检索时这些词**直接参与分词与关键词匹配**，
所以客户说「工资想理财去哪买」也能命中标准问「基金怎么买」。

代码链路：
- 写入：`internal/service/chunk/chunk.go:1167-1177`（`Update` 时整体覆盖 `question_kwd`）
- 读取：`internal/service/chunk/chunk.go:962-963`（`questions` 别名 ↔ `question_kwd` 互转）
- 索引：`internal/service/dataset/embedding.go:274` `QuestionKeywords` 参与 embedding
- 引擎字段映射：`internal/engine/infinity/chunk.go:2757`（粗排）、`:2961`（细排 ft_questions）

### 2.2 增删改如何实现（重要）

RAGFlow 的相似问**没有独立的增删改接口**，而是通过 chunk 更新接口的**差异化覆盖语义**实现：

```go
// internal/service/chunk/chunk.go:1166
if req.Questions != nil {              // 指针：区分「未传」与「传空数组」
    filteredQuestions := []string{}
    for _, q := range req.Questions {  // 自动 trim + 过滤空串
        q = strings.TrimSpace(q)
        if q != "" {
            filteredQuestions = append(filteredQuestions, q)
        }
    }
    d["question_kwd"] = filteredQuestions   // 整体覆盖
}
```

由 `req.Questions` 是**指针**（`[]string` 而非 `[]string` 的值）可推导出三种操作语义：

| 前端操作 | 请求体 | 服务端行为 | 结果 |
|---|---|---|---|
| **新增**一个相似问 | `questions: [已有..., "新问法"]` | 过滤空串后整体覆盖 | 追加成功 |
| **修改**某条 | `questions: [改后..., 其他不变...]` | 整体覆盖 | 更新成功 |
| **删除**某条 | `questions: [剩余...]`（去掉该条） | 整体覆盖 | 删除成功 |
| （清空全部） | `questions: []` | 覆盖为空数组 | 全部清除 |

> **推论依据**：字段为指针类型，`nil` 表示「不修改」，空数组表示「清空」。
> 新增/修改/删除本质都是「读取当前列表 → 增删改元素 → 整体回传」，
> 前端交互层负责维护列表状态，服务端无需感知具体是哪一种操作。

### 2.3 前端界面（已存在）

- 分块编辑弹窗：`web/src/pages/chunk/parsed-result/add-knowledge/components/knowledge-chunk/components/chunk-creating-modal/index.tsx`
- 字段声明：`web/src/pages/agent/form/extractor-form/schema.ts`（含 `questions`）
- 提取器侧配置：`web/src/components/auto-keywords-form-field.tsx`

### 2.4 客户操作演示

1. 知识库 → 基金FAQ库 → 文档 → 基金怎么买 → 点开分块 → 「相似问」输入框
2. 粘贴 `工资发下来想理财，在哪买基金`，回车
3. 到「检索测试」页输入 `刚发的工资想理财，在哪能买基金`
4. 命中「基金怎么买」→ 演示成功

## 三、词汇别名表：需开发（工作量小）

### 3.1 现状核实

**机制已存在**：`internal/service/nlp/synonym.go` 的 `Synonym` 类型。

```go
// synonym.go:79
path := filepath.Join(s.resPath, "synonym.json")   // 读本地文件
```

**已接入检索链路**（三处调用，均在查询构造阶段做关键词扩展）：
- `internal/service/nlp/query_builder.go:344`
- `internal/service/nlp/query_builder.go:446`（主路径，`syns := qb.synonym.Lookup(segment, 8)`）
- `internal/service/nlp/query_builder.go:500`

扩展结果追加进 `keywords`（上限 32），参与后续检索打分。

### 3.2 三个必须提前说明的现状问题

**问题一：词典是通用词库，不是金融领域**
```
internal/rag/res/synonym.json  共 10502 条
样例：'阿为特' -> 873693        '骑士乳业' -> 832786
```
全是「对账单/验证码」这类通用词，**没有任何基金、金融术语**。

**问题二：实时加载被注释掉了**
```go
// synonym.go:121-150  load() 全部注释
// 含注释掉的 Redis key "kevin_synonyms"
```
`s.load()` 目前是空实现（同步版本直接用文件内容）。

**问题三：无任何管理界面**
`internal/router/router.go` 中**没有 synonyms 相关的路由**，
`GetDictionary()` 只有定义、无调用方（即无对外读取接口）。

### 3.3 结论

**当前状态 = 「配了也不会生效」**：改词典必须改服务器文件 + 重启服务，
无管理界面，且现有词库对基金场景无用。

这正是甲方要求「维护基金领域及华夏专属领域词汇别名表」必须开发的原因——
不是 RAGFlow 缺能力，而是**缺管理台与金融词库**。

### 3.4 实现方案

**Step 1｜数据模型**（新增2 张表）

```sql
CREATE TABLE synonym_group (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id   VARCHAR(64)  NOT NULL,     -- 租户隔离
  kb_id       VARCHAR(64)  NOT NULL,     -- 绑定知识库（基金通用词可挂公共库）
  name        VARCHAR(128) NOT NULL,     -- 词组名，如「华夏基金产品别名」
  domain      VARCHAR(32)  NOT NULL,     -- fund(基金通用) / hx(华夏专属)
  remark      VARCHAR(512),
  created_at  DATETIME,
  updated_at  DATETIME,
  UNIQUE KEY uk_tenant_kb_name (tenant_id, kb_id, name)
);

CREATE TABLE synonym_word (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  group_id    BIGINT NOT NULL,
  word        VARCHAR(128) NOT NULL,-- 词条（全称/简称/别名均可为词条）
  is_primary  TINYINT DEFAULT 0,            -- 是否主词（检索扩展时保留权重）
  created_at  DATETIME,
  KEY idx_group (group_id)
);
```

**Step 2｜后端 CRUD 接口**（仿现有 chunk 风格，路径 `internal/router/router.go`）

```
GET    /api/v1/datasets/:dataset_id/synonym_groups          列表（含词条数）
POST   /api/v1/datasets/:dataset_id/synonym_groups          建词组
PUT    /api/v1/synonym_groups/:group_id                     改词组（含增删改词条）
DELETE /api/v1/synonym_groups/:group_id                     删词组
POST   /api/v1/synonym_groups/import                        Excel/CSV 批量导入
```

**Step 3｜接入检索（关键：必须改，否则配了不生效）**

改造 `synonym.go`，让它从DB 加载而非文件：

```go
    // 写入 s.dictionary：word -> 同组其他词
}

// 3) 保留原 synonym.json 作为兜底底座（通用词），DB 词表叠加在上层
```

**Step 4｜缓存与实时性**

- 加token 级失效：词表变更时 `DELETE /api/v1/tenants/synonym_cache/:tenant_id`
- `Synonym` 结构体已内建`loadTm` 时间戳与原子操作，可直接复用做定时/惰性刷新
- 刷新粒度建议按租户，避免全量重载

**Step 5｜前端管理界面**

- 右侧词条表格，支持行内增删改 + 批量导入
- 复用现有 `ui/table.tsx` + `RAGFlowPagination`，与本次知识库列表改造风格一致

## 四、两套机制如何配合（避免客户混淆）

| 维度 | 相似问（question_kwd） | 词汇别名表（synonym） |
|---|---|---|
| 粒度 | **挂在具体知识点**上 | **全局/知识库级**，按词匹配 |
| 作用范围 | 只增强该chunk 的召回 | 增强所有含该词的 query |
| 典型用途 | 整句口语化改写：「工资理财去哪买」 | 实体/术语归一：「50ETF」→「华夏上证50ETF」 |
| 是否需开发 | 否 | 是 |

**推荐用法**：
- 相似问 → 挂在 FAQ 知识点上，覆盖**整句**表达差异
- 别名词表 → 覆盖**专有名词、简称、产品名**的归一化

建议在合同中明确词表由甲方提供并确认。

1. 在管理页新增词组「华夏产品别名」，录入 `50ETF → 华夏上证50ETF`

3. 修改词条为`50 → 华夏上证50ETF`，重新检索立即生效（无需重启服务）
4. 删除该词条后再次检索，命中数下降
5. 相似问新增/删除后，检索测试结果相应变化，且**无需重新上传文档**
