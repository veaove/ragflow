## 一、总体设计

### 1.1 两条执行链路，两个挂点

系统有**两条完全独立的对话执行链路**，质检必须分别挂点，只挂一条会漏掉一半入口。

#### 链路 1：Chat Pipeline（`AsyncChat`）

| 调用方 | 位置 | 入口 |
|---|---|---|
| 主聊天会话 | `chat_session.go:1280` | 聊天页 |
| 外部 bot | `bot_completion.go:435` | `ChatbotCompletion` |
| OpenAI 兼容 | `openai_chat.go:344` | `/v1/chat/completions` |
| chatbots 分享页 | `use-send-shared-message` → `/chatbots/:id/completions` → `ChatbotCompletion` → `AsyncChat` | 分享/嵌入 |

出口：`AsyncChatResult.Answer`（文本增量）。

#### 链路 2：Agent Canvas Runtime（`RunAgent`）

| 调用方 | 位置 | 入口 |
|---|---|---|
| Chatflow 公开 API | `app_run.go:99` `ChatFlow` → `RunAgentAsApp` → `RunAgent` | `/chatflows/:canvas_id/chat` |
| Workflow 公开 API | `app_run.go:56` `RunWorkflow` → `RunAgentAsApp` → `RunAgent` | `/workflows/:canvas_id/run` |
| agentbots 分享页 | `bot.go:138` → `bot.go:162` `RunAgent` | `/agentbots/:id/completions` |
| 编辑器调试运行 | `/agents/:canvas_id/run` → `RunAgent` | 画布试运行 |
| Webhook 触发 | `agent_webhook.go` → `RunAgent` | 外部触发 |

出口：`<-chan canvas.RunEvent`（结构化事件）。

> **v1.0 勘误**：初版设计只挂了链路 1，并误称「3 个调用方全覆盖」。
> chatflow / workflow 走 `RunAgentAsApp`，与 `AsyncChat` 无关——那是链路 2 的入口。
> 若只按初版实现，**所有 chatflow 与 workflow 的会话都不会被质检**。

#### 收敛策略

| 链路 | 收敛点 | 挂点位置 |
|---|---|---|
| 链路 1 | `AsyncChat`（`chat_pipeline.go:207`） | `send()` 内，第 1119 行 |
| 链路 2 | `RunAgent`（`agent.go:1485`） | 事件 channel 包装处 |

**两处挂点，调用方零改动。**

### 1.2 双通道

```
链路 1  send(result)  ← chat_pipeline.go:1119
链路 2  RunEvent 出口 ← agent.go:1485 RunAgent 的 return chan
   │
   ├─ 同步：qc.Inspect(文本)
   │     ├─ 未命中 → 原样 emit
   │     ├─ 命中提示/警告 → 原样 emit + 异步事件
   │     └─ 命中阻断 → 替换文本为替代话术 + 异步事件
   │
   └─ 异步：NATS publish QcHitEvent
         └─ 质检服务消费 → 写 qc_hit → WebSocket 推送面板
```

### 1.3 三条硬性原则

1. **质检异常不得影响聊天**：所有质检调用包在 `recover()` + error 忽略内
2. **阻断漏过率必须为 0**：阻断判定必须基于权威全文（`fullAnswer`），不能只基于 delta
3. **旁路可降级**：NATS 不可用时仅丢失实时推送，记录改走同步落库

## 二、匹配引擎设计

### 2.1 为什么不能只匹配 delta

流式输出可能把关键词拆开：

```
delta1 = "这只产品是稳"
delta2 = "赚的，保本保收益"
```

只匹配 delta1 漏「稳赚」，只匹配 delta2 漏「保本」前的上下文。
**必须以 `fullAnswer` 为权威文本做匹配。**

### 2.2 增量匹配（避免每 delta 全量重扫）

```go
// internal/service/qc_matcher.go
type StreamMatcher struct {
    full      strings.Builder // 累积全文
    scanned   int             // 已扫描长度
    fired     map[string]bool // ruleID → 本会话是否已命中（去重）
    compiled  *CompiledRules  // 预编译规则集
}

// Inspect 在每次 delta 后调用，返回本次新产生的命中
func (m *StreamMatcher) Inspect(delta string, scope string) []Hit
```

流程：

1. `full.WriteString(delta)`
2. 取未扫描区间 `text := full.String()[m.scanned:]`
3. 对 `text` 跑预编译匹配器，得到 `(ruleID, start, end)` 列表（start 为全文绝对位置）
4. 过滤：`m.fired[ruleID]` 为 true 的跳过（同会话同规则只报一次）
5. 推进 `m.scanned = full.Len()`
6. 返回新命中

**跨 delta 正确性**：因为扫描区间从上次结束位置开始，且 `full` 保留全部文本，
「稳」+「赚」会在第二个 delta 的未扫描区间「稳赚的，保本保收益」中被完整匹配到。

**去重语义**：同一会话同一规则只报一次（PRD FR-02-03）。若产品后续要求「每次出现都报」，
把 `fired` 改为记录已报位置集合即可。

### 2.3 快速路径（性能关键）

绝大多数 delta 不命中。先做一次廉价预判：

```go
// 预编译时收集所有关键词的首字符集合
firstBytes map[byte]bool

func (m *StreamMatcher) maybeHit(text string) bool {
    for i := 0; i < len(text); i++ {
        if m.firstBytes[text[i]] { return true }
    }
    return false
}
```

`Inspect` 入口先跑 `maybeHit`，返回 false 直接返回 nil。
对纯中文文本需按 rune 取首字符（中文首字节不可靠），实现时用 `[]rune` 转换后判定。

### 2.4 三种匹配模式的编译

| 模式 | 编译产物 | 说明 |
|---|---|---|
| 包含 | 关键词集合 + 首字符索引 | 短文本直接 `strings.Index` 循环；长文本用简化 AC 自动机 |
| 全词 | `\b(词1\|词2)\b` 正则 | 需转义正则元字符 |
| 正则 | 用户正则，编译校验 | 保存时校验，非法拒绝 |

**200 条规则 × 50 词 = 10000 词**的规模下：

- 方案 A：Go `regexp` 并联 10000 个交替分支 —— **不可用**，回溯灾难
- 方案 B：`strings.Contains` 循环 10000 次 —— 短文本（delta 通常 <100 字）可接受，长文本慢
- 方案 C：简化 AC 自动机（自建 ~150 行）—— 一次性 O(文本长度)，**推荐**
- 方案 D：引入 `github.com/ahocorasick` —— 性能最好，但新增第三方依赖

**V1.0 选 B + 快速路径**（实现最简单，delta 场景够用），**V1.1 换 C**。
理由：delta 平均长度小，快速路径已过滤掉绝大多数调用；先用真实压测数据决定是否值得上 AC。

### 2.5 规则加载与缓存

```
租户规则变更（CRUD/启停）
   └─→ 写 MySQL
   └─→ 删 Redis 缓存 qc:rules:{tenant_id}
   └─→ 广播 NATS qc.rule.invalidated {app_type, app_id}

会话开始
   ├─ 链路 1（AsyncChat）：app_type='chat'，app_id=chat.ID
   └─ 链路 2（RunAgent）：app_type='canvas'，app_id=canvasID
   └─→ 查 Redis qc:rules:{app_type}:{app_id}
         ├─ 命中 → 反序列化 → 编译匹配器
         └─ 未命中 → 查 MySQL → 写 Redis（TTL 300s）→ 编译

会话进行中
   └─→ 收到 qc.rule.invalidated 且 app 匹配 → 重新加载并编译
```

**编译一次，整个会话复用**。匹配器无锁（单会话单 goroutine 访问）。

## 三、数据模型

### 3.1 DDL

```sql
CREATE TABLE qc_rule (
  id             VARCHAR(32)  NOT NULL PRIMARY KEY,
  tenant_id      VARCHAR(64)  NOT NULL,
  app_type       VARCHAR(16)  NOT NULL,           -- 'chat'（聊天应用）/ 'canvas'（对话流/工作流）
  app_id         VARCHAR(64)  NOT NULL,           -- chat_id 或 canvas_id
  name           VARCHAR(50)  NOT NULL,
  keywords       JSON         NOT NULL,          -- ["保本","稳赚"]
  match_mode     VARCHAR(16)  NOT NULL DEFAULT 'contains',  -- contains / whole_word / regex
  scope          VARCHAR(16)  NOT NULL DEFAULT 'ai_answer', -- ai_answer / user_input / both
  severity       VARCHAR(16)  NOT NULL DEFAULT 'warn',      -- info / warn / block
  action         VARCHAR(24)  NOT NULL DEFAULT 'log_and_alert', -- log / log_and_alert / block_and_alert
  prompt_message VARCHAR(500) NOT NULL,
  enabled        TINYINT      NOT NULL DEFAULT 1,
  created_by     VARCHAR(64),
  create_time    DATETIME(3)  NOT NULL,
  update_time    DATETIME(3)  NOT NULL,
  KEY idx_qc_rule_tenant (tenant_id, enabled),
  KEY idx_qc_rule_app (app_type, app_id, enabled)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE qc_hit (
  id             VARCHAR(32)  NOT NULL PRIMARY KEY,
  tenant_id      VARCHAR(64)  NOT NULL,
  rule_id        VARCHAR(32)  NOT NULL,
  rule_name      VARCHAR(50)  NOT NULL,           -- 规则快照，防规则改名后不可读
  session_id     VARCHAR(64)  NOT NULL,
  chat_id        VARCHAR(32)  NOT NULL,
  app_type       VARCHAR(16)  NOT NULL,           -- 与规则的 app_type 对应
  app_id         VARCHAR(64)  NOT NULL,           -- 用于按应用筛选命中记录
  scope          VARCHAR(16)  NOT NULL,
  severity       VARCHAR(16)  NOT NULL,
  matched_text   VARCHAR(200) NOT NULL,           -- 命中片段（已脱敏）
  context_before VARCHAR(100),                    -- 前 50 字
  context_after  VARCHAR(100),                    -- 后 50 字
  action_taken   VARCHAR(24)  NOT NULL,
  create_time    DATETIME(3)  NOT NULL,
  KEY idx_qc_hit_tenant_time (tenant_id, create_time),
  KEY idx_qc_hit_rule (rule_id),
  KEY idx_qc_hit_session (session_id),
  KEY idx_qc_hit_app (app_type, app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3.2 设计说明

| 决策 | 理由 |
|---|---|
| `rule_name` 冗余存 | 规则可改名/删除，历史记录必须仍可读 |
| `keywords` 用 JSON | 变长列表，避免子表 join；50 个词的 JSON 序列化开销可忽略 |
| `matched_text` 限 200 字 | 只存命中片段，不存全文，降低敏感数据暴露面 |
| `context_before/after` 各 100 | 足够质检员判断语境，又不记录完整对话 |
| 不加 `app_id` | V1.0 租户级全局；V2.0 加 `app_id` 时需补索引 |

### 3.3 存量迁移

纯新增两张表，**无存量数据迁移**。回滚 = 关闭 `qc.enabled`，表可留可删。

**改动 3：`send()` 内插入判定**（第 1119 行）

```go
send := func(result AsyncChatResult) {
    if qc != nil && !result.Final && result.Answer != "" {
        hits := qc.InspectAnswer(result.Answer)   // 基于 fullAnswer 增量匹配
        for _, h := range hits {
            result.QcEvent = &QcEvent{...}
            qc.PublishAsync(h)                     // NATS，失败仅告警
        }
        if v := qc.BlockVerdict(); v != nil {
            // 阻断：本 delta 不返回用户
            if !qc.replacementSent {
                qc.replacementSent = true
                result.Answer = v.Replacement       // 替代话术
                result.QcEvent = &QcEvent{Blocked: true, ...}
            } else {
                return                               // 已发过替代话术，丢弃后续 delta
            }
        }
    }
    emit(result)
}
```

**关键细节**：

| # | 细节 | 处理 |
|---|---|---|
| 1 | `fullAnswer` 在 `send` 外层累积，`InspectAnswer` 读的是它，不是 `result.Answer` | 保证跨 delta 匹配正确 |
| 2 | 阻断后只发一次替代话术 | `replacementSent` 标记 |
| 3 | 用户输入质检 | 在 `AsyncChat` 入口对 `requestMsg` 最后一条 user 消息调 `InspectUserInput` |
| 4 | 异常隔离 | `initQc`/`InspectAnswer`/`PublishAsync` 全部内部 `recover()`，返回零值不 panic |
| 5 | `Final` 消息不质检 | 最后一次是汇总事件，不含新文本 |

### 4.3 链路 2 挂点：`agent.go` 改动

链路 2 出口是 `canvas.RunEvent` 结构化事件，不是文本增量。四个关键差异：

#### 差异 1：文本要从事件里提取

`RunEvent` 的类型（`internal/agent/canvas/`）：

| 事件类型 | 是否含文本 | 质检处理 |
|---|---|---|
| `message` | ✅ 增量文本（chatflow 的回答） | **主质检点** |
| `message_end` | ❌ 汇总事件 | 不质检 |
| `node_finished` | ✅ outputs 里（workflow 的 End 输出） | **workflow 主质检点** |
| `workflow_started` / `workflow_finished` | ❌ | 不质检 |

```go
// agent.go RunAgent 出口包装
func (s *AgentService) wrapQc(events <-chan canvas.RunEvent, qc *QcSession) <-chan canvas.RunEvent {
    out := make(chan canvas.RunEvent, 32)
    go func() {
        defer close(out)
        for ev := range events {
            if qc != nil {
                switch ev.Type {
                case "message":
                    if txt := extractMessageText(ev); txt != "" {
                        if v := qc.InspectText(txt, ScopeAIAnswer); v != nil {
                            if v.Blocked {
                                ev.Data = replaceMessageText(ev, v.Replacement)
                                emitQcEvent(out, v)
                            } else {
                                emitQcEvent(out, v)
                            }
                        }
                    }
                case "node_finished":
                    if txt := extractEndOutput(ev); txt != "" {
                        qc.InspectText(txt, ScopeAIAnswer)   // workflow 只记录，不阻断
                    }
                }
            }
            out <- ev
        }
    }()
    return out
}
```

#### 差异 2：workflow 不阻断，只记录

Workflow 的输出是结构化 JSON，供下游系统消费。拦截会导致调用方拿到不符合契约的数据，破坏集成。

**决策**：Workflow 的质检**只记录 + 告警，不阻断**。阻断仅对 Chatflow 的 `message` 事件生效。
理由：chatflow 面向人，可以替换话术；workflow 面向系统，替换会破坏数据契约。

#### 差异 3：tenant 解析不同

规则按 **app** 维度加载（`app_type` + `app_id`），不再按 tenant 全量加载——
因为规则绑定到了应用，加载集合天然缩小。

- 链路 1：`app_type='chat'`，`app_id=chat.ID`；权限校验仍用登录用户 `userID`
- 链路 2：`app_type='canvas'`，`app_id=canvasID`；权限校验用 `canvasRow.UserID`（API Key 调用时无用户）

```go
// 链路 2 初始化质检时，tenant 必须是画布 owner，不是调用方
tenant := canvasRow.UserID
qc, err := s.initQcForTenant(ctx, tenant)
```

若误用调用方身份，API Key 调用场景下会加载不到规则（或加载到错误的租户规则）。

#### 差异 4：调试运行默认不质检

编辑器试运行（`/agents/:canvas_id/run`）是开发者调试，质检拦截会干扰排障。

**决策**：调试运行（`trigger_type=debug`）**只记录，不阻断、不告警**。
生产触发（`api` / `webapp` / `embed` / `webhook`）才走完整动作。

通过 `AppRunRequest.TriggerType` 区分；调试入口该字段为 `debug`。

### 4.5 异步通道

```go
// NATS subject: qc.hit.{tenant_id}
type QcHitEvent struct {
    HitID         string `json:"hit_id"`
    TenantID      string `json:"tenant_id"`
    RuleID        string `json:"rule_id"`
    RuleName      string `json:"rule_name"`
    SessionID     string `json:"session_id"`
    ChatID        string `json:"chat_id"`
    Scope         string `json:"scope"`
    Severity      string `json:"severity"`
    MatchedText   string `json:"matched_text"`
    ContextBefore string `json:"context_before"`
    ContextAfter  string `json:"context_after"`
    PromptMessage string `json:"prompt_message"`
    ActionTaken   string `json:"action_taken"`
    Timestamp     int64  `json:"timestamp"`
}
```

消费侧（`qc_service.go`）：

```
收到 QcHitEvent
  ├─ 脱敏（matched_text / context）
  ├─ 写 qc_hit（同步落库，保证不丢）
  └─ WebSocket 广播给该租户在线质检面板
```

**为什么不把落库也放异步**：命中记录是合规证据，不能因消费失败丢失。
NATS 仅作为「从聊天进程到质检服务」的传输，落库动作在消费侧同步执行。

**NATS 不可用降级**：`PublishAsync` 失败时改为同步写 `qc_hit`（不发推送），
保证记录不丢，只损失实时性。

## 五、接口设计

### 5.1 规则管理

```
GET    /api/v1/qc/rules?page=&size=&keyword=&scope=&severity=&enabled=
POST   /api/v1/qc/rules
GET    /api/v1/qc/rules/:id
PUT    /api/v1/qc/rules/:id
DELETE /api/v1/qc/rules/:id
POST   /api/v1/qc/rules/:id/toggle
POST   /api/v1/qc/rules/test          # 规则测试，不落库
```

**POST /api/v1/qc/rules 请求**：

```json
{
  "name": "禁止承诺收益",
  "keywords": ["保本", "稳赚", "零风险"],
  "match_mode": "contains",
  "scope": "ai_answer",
  "severity": "block",
  "action": "block_and_alert",
  "prompt_message": "基金投资均存在风险，历史业绩不代表未来表现...",
  "enabled": true
}
```

**响应**：`{ "code": 0, "data": { "id": "qr_xxx", ... } }`

**校验规则**：

| 字段 | 规则 |
|---|---|
| name | 必填，≤50 字，同租户内唯一 |
| keywords | 必填，1~50 个，非空字符串，去重 |
| match_mode | 枚举 `contains` / `whole_word` / `regex` |
| scope | 枚举 `ai_answer` / `user_input` / `both` |
| severity | 枚举 `info` / `warn` / `block` |
| action | 枚举 `log` / `log_and_alert` / `block_and_alert` |
| prompt_message | 必填，≤500 字 |
| 规则总数 | 同租户 ≤200 |

**severity 与 action 一致性**：`block` 严重级必须配 `block_and_alert`；
`info`/`warn` 不允许配 `block_and_alert`（否则语义冲突）。服务端强校验。

**必须与后端匹配逻辑一致**，否则测试结果失真。抽取共享的「关键词→正则」函数，

| 严重级 | 表现 |
|---|---|
| info | 不提示（只落库） |
| warn | 右下角轻提示（3s 自动消失） |
| block | `answer` 字段已是替代话术，前端正常渲染；额外在气泡上方显示「该回答已被质检拦截」条 |

前端只负责展示 `QcEvent.Blocked` 标记。这样避免前后端两套拦截逻辑不一致。

## 七、测试方案

### 7.1 单元测试

| 用例 | 断言 |
|---|---|
| 关键词跨 delta | 「稳」+「赚」两个 delta 后能命中「稳赚」 |
| 增量扫描不重复 | 同一文本两次 `Inspect` 不产生重复命中 |
| 同会话同规则去重 | 一段话出现两次「保本」只报 1 次 |
| 包含模式 | 「保本保收益」命中「保本」 |
| 全词模式 | 「保本息」不命中「保本」；「保本。」命中「保本」 |
| 正则模式 | `保本.{0,4}收益` 匹配「保本高收益」 |
| 正则非法 | 保存被拒 |
| 快速路径 | 无首字符命中时 `Inspect` 返回 nil 且不进入全量匹配 |
| 脱敏 | 手机号/身份证/银行卡在 `matched_text` 中被掩码 |
| 上下文截断 | 超过 50 字被截断 |

### 7.2 集成测试

**链路 1（Chat Pipeline）**

| 场景 | 断言 |
|---|---|
| 主会话入口命中 | 聊天页对话命中产生记录 |
| 外部 bot 入口命中 | `ChatbotCompletion` 命中产生记录 |
| OpenAI 兼容入口命中 | `/v1/chat/completions` 命中产生记录 |
| chatbots 分享页命中 | 分享/嵌入页对话命中产生记录 |
| 阻断生效 | 命中 block 规则时响应 `answer` 为替代话术 |
| 用户输入命中 | 记录 `scope=user_input`，且对话正常继续 |

**链路 2（Agent Canvas Runtime）**

| 场景 | 断言 |
|---|---|
| Chatflow 公开 API 命中 | `/chatflows/:id/chat` 命中产生记录 |
| Chatflow 阻断生效 | `message` 事件文本被替换为替代话术 |
| Workflow 公开 API 命中 | `/workflows/:id/run` 的 End 输出命中产生记录 |
| Workflow **不**被阻断 | End 输出原文不变（只记录），调用方契约不被破坏 |
| agentbots 分享页命中 | `/agentbots/:id/completions` 命中产生记录 |
| API Key 调用的 tenant | 记录 `tenant_id` = 画布 owner，不是调用方 |
| 调试运行不阻断 | `trigger_type=debug` 时命中只记录，回答原文返回 |

**通用**

| 场景 | 断言 |
|---|---|
| 质检服务故障 | 停掉质检依赖后两条链路均正常返回 |
| NATS 故障 | 记录仍落库，仅无实时推送 |
| 规则热更新 | 会话进行中修改规则，下一条消息按新规则匹配 |

### 7.3 专项测试：阻断漏过率 = 0

构造 100 条含阻断关键词的变体（含跨 delta 拆分、同音字、插入符号），**两条链路各跑一遍**，逐条断言：
**没有任何一条原文出现在返回给用户/调用方的文本中**。

此专项不过，不予上线。

### 7.4 压测

| 场景 | 通过标准 |
|---|---|
| 200 条规则 × 50 词，100 并发对话 | 首包延迟增量 P95 ≤30ms |
| 单 delta 匹配（100 字文本） | P99 ≤2ms |
| 命中推送 | P95 ≤2s |

### 10.1 上线前必须确认的三件事

| # | 事项 | 原因 |
