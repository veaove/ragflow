## 〇、总体结论

原方案的出发点是好的：识别出「重建索引才能测」这个假设过强，并提出影子检索。对**同义词**这一半完全成立。

但**相似问这一半的模拟方式是错的**，且错得不容易发现——我用来演示的原型数据本身就包含一个物理上不可能的结果。这个错误会让用户基于虚假的「新增召回」做出发布决策，比原来的降级方案危害更大。

以下按严重程度排列。

---

## 一、P0-1：相似问的模拟方式不等价（方案级错误）

### 1.1 事实：相似问走的是词法通道，权重 20 倍

`internal/agentic_rag/bm25_service.go:33` 的注释写明了 BM25 通道的字段权重：

```
title_tks^2, title_sm_tks^2, important_*, question_tks^20, content_ltks^2, content_sm_ltks
```

`chunk_question` 表的检索投影是 `chunk.question_kwd`（`internal/dao/chunk_question.go:27-29` 注释：
"the legacy chunk.question_kwd array remains the retrieval-facing projection"），
即相似问以 `question_tks` 字段、**20 倍权重**参与 BM25 打分。

> 待确认：Go 侧未发现独立的 question 向量索引，向量通道是否也纳入 question 需与引擎侧确认。
> 这不影响下面的论证——词法通道一定存在且权重最高。

### 1.2 真实机制 vs 我的方案

真实机制：**用户 query Q 的 token** 命中 chunk 的 `question_tks` 字段，获得 20 倍加权。
即贡献量取决于 `overlap(tokens(Q), tokens(Q'))`。

我的方案：把新增相似问 Q' 当 query 去检索，得到 `BM25(Q', chunk)`，
即「这个 chunk 有多匹配 Q'」。

**两者不是一回事。**

### 1.3 反例

| 场景 | 值 |
|---|---|
| 用户 query | `你好` |
| 新增相似问 Q'（挂在 NAV chunk 上） | `净值怎么查` |
| 真实贡献 | `overlap(你好, 净值怎么查) = 0` → **零贡献** |
| 我的方案 | `retrieve("净值怎么查")` → NAV chunk 高分 → 报「新增召回」 |

**结论：我的方案会产生假阳性**，让用户以为发布后能召回 NAV chunk，实际不能。

### 1.4 我的原型里就有这个错误

原型「完整对比」态的差异明细写着：

> 得分变化 ｜ #3 基金净值在哪里查 · 0.464 → 0.489 ｜ Δ +0.025（相似问「净值怎么查」命中）

而测试问题输入框里填的是 `你好`。
`overlap("你好", "净值怎么查") = 0`，这条得分变化**不可能发生**。

演示数据暴露了方案错误——这不算坏事，但它证明这个方案在实现前就会开始骗人。

### 1.5 正确做法

对每条新增相似问 Q'，计算它与原始 query 的词项重叠：

```
overlap(Q, Q') = Σ_{t ∈ tokens(Q) ∩ tokens(Q')} tf(Q,t) × idf(t) × 20
```

- `overlap = 0` → 该相似问对本次查询**零影响**，直接判定，无需任何检索
- `overlap > 0` → 按 20 倍权重折算成 BM25 增量，叠加到所属 chunk 的 lexical 分，
  再走既有的 `w × vector + (1-w) × lexical` 融合公式

这样做的好处：

| 维度 | 原方案（Q' 当 query） | 修正后（overlap） |
|---|---|---|
| 正确性 | ❌ 假阳性 | ✅ 与真实机制同向 |
| 成本 | N+1 次检索 | 0 次额外检索，仅分词 + 查 idf |
| 模型依赖 | 需要 embedding/rerank | 纯词法，**rerank 缺失也能测** |
| 可解释性 | 差（用户看不懂为什么） | 好（可列出命中的词项） |

**修正后，原方案为解决问题而引入的复杂性全部消失**：
影子 query 上限、抽样、10s 超时、并行检索、rerank 依赖——都不需要了。

## 二、P0-2：未声明「删除相似问」不在范围

`GetChangeSetDiff`（`internal/service/kb_change_set.go:320-340`）的语义是：

```go
after := append([]string{}, before...)
for _, a := range add {
    if !seen[a] { after = append(after, a); seen[a] = true }
}
```

即 **`after = before + pending additions`，变更集不支持删除相似问**。

设计文档通篇讲「新增」，但没有把这个前提写出来。评审时一定被问「删相似问能测吗」，
而答案是「当前变更集模型不支持删除」——这是产品边界，不是技术遗漏，必须显式声明。

**修订**：在「二、核心判断」加一节「范围声明：变更集仅支持新增相似问与同义词（`after = before + additions`），
删除需走单独的下架流程，不在本功能范围」。

## 三、P1：影响结论可信度的四个问题

### P1-1 `avg_score_delta` 口径不可比

baseline 5 条、candidate 6 条，两个均值来自不同集合，直接相减没有意义。

**修订**：改为两个口径，都报：
- `avg_delta_on_common`：**交集 chunk** 上的平均分变化（真实相关性变化）
- `topk_size_delta`：命中间数变化（覆盖面变化）

原型的「平均分变化 +0.021」应标注为「交集口径」。

### P1-2 排序变化重复计数

新增一条插到 #1，原有 5 条全部后移一位 → 记为 5 个「排序变化」，实际只有 1 个真实变化。

**修订**：拆成两个指标：
- `reordered_on_common`：**交集内**位次发生真实变化的条数
- `displaced`：因新增/丢失导致的结构性位移条数（ informational，不计入"变化"）

### P1-3 `removed.reason = below_threshold` 不可计算

chunk 被阈值滤掉时，我们拿不到它的分数，无法区分「得分跌到阈值下」和「没被召回」。

**修订**：reason 只保留两个可判定的值：
- `pushed_out_of_topk`：得分未变（或变化小于 ε），但被新增结果挤出
- `not_recalled`：影子检索中该 chunk 未被任何路径召回

需要 `below_threshold` 的话，得把候选集扩大到 `top_k + buffer` 再判，列为 P2。

### P1-4 状态机缺 `stale`

用户改 TopK / 阈值后，旧结果仍然显示且指标卡仍有数字，容易拿旧结论做决策。

**修订**：加 `stale` 状态——参数变更后结果区加半透明遮罩 + 「参数已变更，重新测试」按钮，
指标卡数字降级为灰色。或直接自动重跑（参数变更成本低，建议自动）。

## 四、P1：原型的三个问题

### P1-5 `queries_issued` 不可见

设计响应里有 `queries_issued`，但原型没展示。用户看不到这次对比覆盖了哪些查询路径，
就无法判断「我测的这个问题到底有没有测到变更集上」。

**修订**：在双栏上方加一行「本次对比覆盖：你好（原 query）· 你好呀（新增相似问，词项重叠 1/2）」。
overlap = 0 的相似问也要列出来并标注「无词项重叠，不参与」——这本身就是最有价值的反馈：
它告诉用户「你加的这条相似问，对这类问题没用」。

### P1-6 双栏行位对不齐，语义混乱

原型里 baseline 5 条、candidate 5 条 + 1 个虚框。
那条「丢失召回」的 chunk 在原配置是 #5，虚框却排在右栏最后，位置语义说不通。

**修订**：虚框应放在**新配置中它本该出现的位置**（按 candidate 分数排序后它落在哪就放哪），
或者在右栏末尾单列「未进入 Top-K」区并注明原名次。

### P1-7 demo 数据自相矛盾

见 1.4。除那条不可能的得分变化外，「排序 ↑1」标注也有问题：
#1 从 0.457 变 0.512、名次从 #1 变 #2，分数涨了但名次降了——因为新来了个 0.461 的插在中间？
不对，0.512 > 0.461，它应该还是 #1。demo 的数字没有自洽。

**修订**：按 overlap 机制重新构造一组自洽的 demo：
- query「你好」，新增相似问「你好呀 / 您好」（overlap 高）→ 问候 chunk 得分上升、名次上升
- 新增相似问「净值怎么查」（overlap=0）→ 明确标注「无词项重叠，不参与对比」
- 无同义词变更 → query 不扩写

## 六、修订后的方案要点

1. **同义词**：query 扩写（精确模拟，不变）
2. **相似问**：改为 `overlap(Q, Q')` 判定
   - overlap = 0 → 明确告知「该相似问对本查询无影响」，不参与打分
   - overlap > 0 → 按 `question_tks^20` 折算 BM25 增量，叠加后走既有融合公式
3. **范围声明**：变更集仅支持新增；删除不在范围
4. **指标口径**：新增召回 / 丢失召回 / 交集位次变化 / 交集平均分变化 / 覆盖说明
5. **删掉的复杂性**：影子 query 上限、抽样、N+1 检索、10s 超时、rerank 硬依赖
6. **保留的诚实性设计**：不静默降级、不假装精确、removed 必须给 reason

修正后这个功能从「需要一次额外检索实验」变成「一次纯词法计算」，
实现量、延迟、失败面都显著下降，而结论反而更准。

---

## 七、待确认

1. **向量通道是否纳入 question？** 决定 overlap 公式是否要并上余弦路径。需与引擎侧确认。
2. **`question_tks^20` 的 20 是全局常量还是可配？** 若可配，折算公式要读配置。
3. **同义词扩写后是多路取 max 还是加权和？** 决定 candidate 分数的聚合方式，需读现有实现确认。
4. **变更集是否计划支持删除相似问？** 若支持，本功能需补删除的模拟（去掉该 question 的匹配点）。
