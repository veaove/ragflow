## 一、范围与前提（全部有代码依据）

自评 P0-1 推翻了原方案「把新增相似问当 query 检索」的做法。重新核对代码后，得到三个硬事实：

### 1.1 变更集只支持新增

`internal/service/kb_change_set.go:328-336`：

```go
after := append([]string{}, before...)
for _, a := range add {
    if !seen[a] { after = append(after, a); seen[a] = true }
}
```

**本设计只处理「新增相似问 / 新增同义词」。删除不在变更集模型内，不在范围。**

### 1.2 同义词作用于 query 字符串，权重 = 原 token 权重 / 4

`internal/service/nlp/query_builder.go:389-399`：

```go
tkSyns := qb.synonym.LookupScoped(ctx, tenantID, datasetID, tk, 8)
for _, syn := range tkSyns {
    synParts = append(synParts, fmt.Sprintf(`"%s"^%.4f`, syn, tw.w/4.0))
}
```

同义词在**构造 query 字符串时**展开，每个 token 最多 8 个同义词，权重为原权重的 1/4。
→ **换字典就能精确模拟，与引擎无关。**

### 1.3 相似问通过 `question_tks` 进入 `tsim`，且不进入 reranker 的 doc 文本

`internal/service/nlp/reranker.go:138-146`：

```go
contentLtks := extractContentTokens(chunk, cfield)
titleTks := extractTitleTokens(chunk)
importantKwd := extractImportantKeywords(chunk)
questionTks := extractQuestionTokens(chunk)     // ← question_tks
tks := append(tks, contentLtks...)
tks = append(tks, titleTks...)
tks = append(tks, importantKwd...)
tks = append(tks, questionTks...)               // ← 进入 insTw
```

`reranker.go:566-572`：`extractNaturalText` 只取 `content_with_weight`，**不含 question 文本**。
`reranker.go:198`（融合公式）：`sim[i] = tkWeight*tsim[i] + vtWeight*modelSim[i]`。

**结论**：新增相似问只改变该 chunk 的 `insTw`（从而改变 `tsim`），不改变 `modelSim`。
→ **有 rerank 时，相似问的影响可在应用层精确注入。**

### 1.4 能力矩阵

| 变更类型 | 注入点 | 有 rerank | 无 rerank |
|---|---|---|---|
| 同义词 / 专有词 | query 字符串（`query_builder.go:399`） | ✅ 精确 | ✅ **精确**（query 字符串与引擎无关） |
| 相似问 | chunk 的 `insTw`（`reranker.go:146`） | ✅ 精确 | ❌ 引擎内 `question_tks^20` 融合，不可注入 |

> 自评里「rerank 缺失也能测」的结论**只对同义词成立**，相似问不行。此处按代码事实修正。

## 二、方案：双 hook 影子检索

不再「多跑 N 次检索」，而是**一次带注入的检索**：给现有检索链路开两个可选注入点，candidate 与 baseline 走完全相同的融合公式，差异只来自注入。

```
                        ┌─────────────────────────────────────────┐
                        │  nlp.RetrievalRequest                   │
                        │  + SynonymOverride  map[string][]string │  ← hook 1（query 侧）
                        │  + ExtraChunkTokens map[string][]string │  ← hook 2（chunk 侧）
                        └─────────────────────────────────────────┘
                                        │
        ┌───────────────────────────────┴───────────────────────────────┐
        │                                                               │
   baseline（无注入）                                          candidate（注入）
   - 字典 = live                                            - 字典 = live + pending 同义词
   - insTw = chunk 原 token                                  - insTw += 新增相似问 token
        │                                                               │
        └───────────────────────────────┬───────────────────────────────┘
                                        │
                                同一套 scoreSearchResult / RerankByModel
                                同一套阈值 / TopK / 权重
                                        │
                                      diff 计算
```

### 2.1 hook 1：`SynonymOverride`

**位置**：`query_builder.go:391` 的 `LookupScoped` 调用处。

```go
// RetrievalRequest 新增字段
SynonymOverride map[string][]string `json:"-"` // 测试用，不序列化

// query_builder.go:391 附近
tkSyns := qb.synonym.LookupScoped(ctx, tenantID, datasetID, tk, 8)
if override, ok := req.SynonymOverride[tk]; ok {
    tkSyns = override   // 注入优先，其余 token 仍走原字典
}
```

**语义**：只覆盖命中的 token，未命中的 token 仍查 live 字典。这样 candidate 字典 = live ∪ pending，与变更集语义一致。

**线程安全**：`GetQueryBuilder()` 是包级单例，`LookupScoped` 内部有 per-dataset 缓存。
`SynonymOverride` 挂在 `RetrievalRequest` 上（请求级），不碰单例状态，无并发问题。

### 2.2 hook 2：`ExtraChunkTokens`

**位置**：`reranker.go:146` 的 `insTw` 拼接处。

```go
tks = append(tks, questionTks...)
if extra, ok := req.ExtraChunkTokens[chunkID]; ok {
    tks = append(tks, extra...)   // 注入新增相似问的 token
}
insTw = append(insTw, tks)
```

**语义**：给指定 chunk 追加 token，等效于该 chunk 的 `question_tks` 多了这些词。
因为 `tsim = TokenSimilarity(keywords, insTw)`，追加后 `tsim` 自然反映新增相似问的影响。

**token 化**：新增相似问是自然语言，需过同一套分词：
`qb.Question(Q', "qa", 0.6, language)` 拿 token，或直接 `extractQuestionTokens` 的逆操作。
**必须与索引侧同 tokenizer**，否则权重不一致（见风险 R2）。

### 2.3 无 rerank 时的降级

`scoreSearchResult`（`retrieval.go:484`）在无 rerank 时走引擎融合（ES/Infinity/OceanBase），
`question_tks^20` 在引擎内部生效，应用层拿不到也改不了。

→ **无 rerank 时：同义词可精确模拟，相似问不可模拟。**
前端必须把这个能力差异讲清楚（见 6.2），不能给一个假的对比结果。

## 三、接口设计

### 3.1 端点

`POST /api/v1/datasets/:dataset_id/change-sets/:change_set_id/retrieval-compare`

挂到现有 `ChangeSetHandler`（`internal/handler/kb_change_set.go:58`），复用其权限模型。

**请求**：

```go
type RetrievalCompareRequest struct {
    service.RetrievalTestRequest            // question / top_k / similarity_threshold /
                                            // vector_similarity_weight / doc_ids ...
    ShadowSimilarQuestions bool `json:"shadow_similar_questions"` // 默认 true
}
```

**响应**：

```go
type RetrievalCompareResponse struct {
    Baseline  CompareSide            `json:"baseline"`
    Candidate CompareSide            `json:"candidate"`
    Diff      CompareDiff            `json:"diff"`
    Capability CompareCapability     `json:"capability"`
}

type CompareSide struct {
    Hits      []CompareHit `json:"hits"`
    TookMs    int64        `json:"took_ms"`
    Total     int64        `json:"total"`
}

type CompareHit struct {
    ChunkID    string  `json:"chunk_id"`
    DocKeyword string  `json:"doc_keyword"`
    Content    string  `json:"content"`
    Similarity float64 `json:"similarity"`
    Rank       int     `json:"rank"`
}

type CompareCapability struct {
    SynonymSimulated    bool     `json:"synonym_simulated"`     // 恒 true
    SimilarQSimulated   bool     `json:"similar_q_simulated"`   // = 有 rerank
    UnsolvedReasons     []string `json:"unsolved_reasons"`      // 如 ["no_rerank_model"]
    AffectedChunkCount  int      `json:"affected_chunk_count"`  // 有新增相似问的 chunk 数
    SkippedSimilarCount int      `json:"skipped_similar_count"` // 与 query 无词项重叠而被跳过的条数
}
```

### 3.2 diff 结构（按自评 P1 修正口径）

```go
type CompareDiff struct {
    Added           []DiffItem `json:"added"`            // candidate 有、baseline 无
    Removed         []DiffItem `json:"removed"`          // baseline 有、candidate 无
    ReorderedCommon []DiffItem `json:"reordered_common"` // 交集内位次真实变化
    ScoreChanged    []DiffItem `json:"score_changed"`    // 交集内得分变化
    Summary         DiffSummary `json:"summary"`
}

type DiffSummary struct {
    BaselineCount      int     `json:"baseline_count"`
    CandidateCount     int     `json:"candidate_count"`
    AddedCount         int     `json:"added_count"`
    RemovedCount       int     `json:"removed_count"`
    ReorderedCount     int     `json:"reordered_count"`      // 仅交集内
    DisplacedCount     int     `json:"displaced_count"`      // 结构性位移（information only）
    AvgDeltaOnCommon   float64 `json:"avg_delta_on_common"`  // 交集口径
    CommonCount        int     `json:"common_count"`
}
```

**`AvgDeltaOnCommon` 是交集口径**，修复自评 P1-1「baseline 5 条 vs candidate 6 条均值不可比」。
`DisplacedCount` 单独报结构性位移，修复自评 P1-2「新增插队导致全员位移被记成 N 个变化」。

### 3.3 `RemovedItem.Reason` 只保留可判定值

| 值 | 判定 |
|---|---|
| `pushed_out_of_topk` | 该 chunk 在 candidate 中得分未跌（变化 < ε）但名次跌出 TopK |
| `not_recalled` | 该 chunk 在 candidate 中未被任何路径召回 |

去掉 `below_threshold`（自评 P1-3：被阈值滤掉时拿不到分数，无法判定）。

## 四、核心算法

### 4.1 主流程

```
1. 鉴权：checkDatasetAccess(OperationUse) —— 复用 chunk.go:173 的方式
2. 加载变更集 diff：ChangeSetService.GetChangeSetDiff
3. 构造注入：
   - synonymOverride = merge(liveDict, pendingSynonyms)   // 按 token 归并
   - extraChunkTokens = {chunkID: tokens(Q') for each pending similar question}
   - 过滤 overlap(Q, Q') == 0 的相似问 → skippedSimilarCount++，不注入
4. baseline 检索：RetrievalRequest{无注入}
5. candidate 检索：RetrievalRequest{SynonymOverride, ExtraChunkTokens}
6. diff 计算（4.3）
```

### 4.2 为什么第 3 步要过滤 overlap = 0

`TokenSimilarity`（`reranker.go:416`）的输入是 `keywords`（query 分词）与 `insTw`（chunk token）。
若 Q' 与 Q 无共同 token，追加 Q' 的 token 不会改变 `tokenDictSimilarity` 的结果——注入了也不产生差异。

过滤有两个好处：
1. **省事**：不用给无关 chunk 追加 token
2. **有价值的信息**：`skippedSimilarCount` 直接告诉用户「你加的这些相似问，对这个问题没用」，
   这是比 diff 更有用的反馈。

overlap 判定用最廉价的词项交集：

```go
func termOverlap(qTokens, qPrimeTokens []string) []string {
    set := map[string]bool{}
    for _, t := range qTokens { set[t] = true }
    var hit []string
    for _, t := range qPrimeTokens {
        if set[t] { hit = append(hit, t) }
    }
    return hit
}
```

分词统一走 `qb.Question(txt, "qa", 0.6, language)`，与索引侧同源。

### 4.3 diff 计算

```go
b := map[string]CompareHit{}   // chunk_id → hit
c := map[string]CompareHit{}
for _, h := range baseline.Hits  { b[h.ChunkID] = h }
for _, h := range candidate.Hits { c[h.ChunkID] = h }

added   := keys(c) - keys(b)          // 按 c.Rank 升序
removed := keys(b) - keys(c)          // 按 b.Rank 升序，带 reason
common  := keys(b) & keys(c)

reordered := []string{}               // 交集内位次真实变化
for _, k := range common {
    if b[k].Rank != c[k].Rank { reordered = append(reordered, k) }
}

scoreChanged := []string{}
var deltaSum float64
for _, k := range common {
    d := c[k].Similarity - b[k].Similarity
    deltaSum += d
    if math.Abs(d) > 1e-4 { scoreChanged = append(scoreChanged, k) }
}

avgDeltaOnCommon := deltaSum / float64(len(common))   // len(common)==0 时为 0
```

**displaced（结构性位移）** = `added + removed` 造成的名次偏移，只计数不下结论：

```go
displaced := 0
for _, k := range common {
    if b[k].Rank != c[k].Rank {
        // 位次变化量 ≈ 名次差 - (新增/丢失的净影响)
        displaced++
    }
}
// 简化：displaced = |len(common) 中位次变化条数 - reordered 的真实变化数|
```

> 实现时用「位次变化且该 chunk 自身得分未变」判定为结构性位移，其余计为真实位次变化。

## 六、前端设计

### 6.1 结构（沿用原型）

```
变更摘要条（相似问 +N · 同义词 +M · 对比方式）
参数行（问题 / TopK / 阈值 / 测试 / 复制报告）
能力提示条（见 6.2）
六张指标卡（原命中 / 新命中 / 新增 / 丢失 / 交集位次变化 / 交集平均分变化）
双栏结果（原配置 | 新配置，丢失项虚框占位）
差异明细（可折叠）
底部（关闭 / 发布变更集）
```

### 6.2 能力提示条（新增，自评 P1-5 相关）

根据 `capability` 渲染，**四种情况**：

| `similar_q_simulated` | 提示 |
|---|---|
| `true` | 「相似问影响已精确模拟（基于 rerank 分词通道）」 |
| `false` | 「⚠ 未配置 rerank 模型，**相似问变更无法模拟**；同义词变更可精确模拟。配置 rerank 后可获得完整对比。」 |

同时展示 `affected_chunk_count` 与 `skipped_similar_count`：

> 本次变更集为 3 个 chunk 新增相似问；其中 1 条与当前问题无词项重叠，已跳过。

这句话是**比 diff 更有价值的反馈**——它直接告诉用户「你加的这条没用」。

### 6.3 状态机

| 状态 | 表现 |
|---|---|
| `idle` | 双栏空态引导，指标全 `—` |
| `loading` | 指标卡 + 双栏 + 明细三处同时骨架 |
| `done` | 完整对比 |
| `done_no_effect` | diff 全零，指标卡全 0，明细写「无差异」 |
| `partial_capability` | 出结果，但相似问未模拟；指标卡中相似问相关项标 `—`，能力提示条给原因 |
| `stale` | 参数变更后结果区半透明遮罩 + 「参数已变更，重新测试」；或自动重跑（推荐自动，成本低） |
| `error` | 只显示错误与原因，**不退回「只展示原配置」** |

### 6.4 双栏对齐规则（修复自评 P1-6）

虚框放在 candidate 中**按分数排序后它本该落在的位置**，而不是末尾；
若跌出 TopK 之外，在右栏末尾单列「未进入 Top-K」区并注明原名次。

## 八、测试方案

### 8.1 单元测试

| 用例 | 断言 |
|---|---|
| `SynonymOverride` 注入 | candidate query 字符串含 `"syn"^w/4`，且未覆盖的 token 仍查 live |
| `ExtraChunkTokens` 注入 | 注入后 `TokenSimilarity` 结果 > 注入前（用固定 token 集） |
| overlap = 0 过滤 | 无关相似问不进 `ExtraChunkTokens`，`skipped_similar_count` 正确 |
| diff 口径 | 交集平均分只算交集；`reordered` 不含结构性位移 |
| `removed.reason` | 得分未变但名次跌出 → `pushed_out_of_topk`；未被召回 → `not_recalled` |

### 8.2 集成测试（需真实引擎）

| 场景 | 准备 | 期望 |
|---|---|---|
| 同义词新增，有 rerank | 加一组同义词变更 | candidate 与手工构造 query 的结果一致 |
| 相似问新增，有 rerank | 加一条与 query 有词项重叠的相似问 | 该 chunk `tsim` 上升、名次上升 |
| 相似问新增但无重叠 | 加一条无关相似问 | `skipped_similar_count=1`，diff 为空 |
| 相似问新增，无 rerank | 租户不配 rerank | `similar_q_simulated=false`，capability 给出原因，不返回假 diff |
| 无变更影响 | 变更集与 query 完全无关 | `done_no_effect` |

### 8.3 验证「注入是否等价于真实发布」

**这是整个方案的可信度基石**，必须做：

1. 在测试库构造 chunk + 一条新增相似问
2. 跑 compare，记录 candidate 预测
3. **真的发布变更集**
4. 用同一 query 跑线上检索，记录真实结果
5. 断言 candidate 预测与真实结果的 chunk 集合、排序一致（允许浮点误差）

若第 5 步不通过，说明注入点或公式有漏，方案不成立。
**这一步不过，不给上线。**

2. **`qb.Question` 的 `0.6` 阈值**（`reranker.go:117`）是否适用于相似问分词？需与索引侧 ingestion 的分词参数对齐。
3. **是否需要支持「删除相似问」的模拟？** 当前变更集模型不支持，若产品要支持，需先改变更集。
4. **能力提示条的文案是否需要产品确认？** 尤其「未配置 rerank 时相似问不可模拟」这句，涉及对客户的解释口径。
