# 实时质检管理 —— 可行性评估与改造清单

| 项 | 内容 |
|---|---|
| 需求 | 实时质检管理：配置触发实时质检的关键词及对应提示信息 |
| 评估日期 | 2026-10-20 |
| 代码基线 | RAGFlow `ac2044bb` |
| 结论 | **必须改造**。零改造可覆盖约 40% 诉求（关键词分流），无法实现「实时质检管理」（集中配置、实时提示、质检看板、审计） |
| 说明 | 本方案为产品设计参考，具体实施请结合公司合规与法务要求确认 |

## 一、结论先行

| 问题 | 答案 |
|---|---|
| 现有系统能不改造实现吗？ | **不能** |
| 最接近的零改造做法是什么？ | 在 Agent 画布用 `Switch` / `Categorize` 节点做关键词分流 |
| 为什么不够？ | 三个硬伤，见第三节 |
| 改造量大吗？ | **不大**。两条执行链路各有一个收敛点（`AsyncChat` / `RunAgent`），各插一个挂点即可覆盖全部入口 |
| 最小可行版本多大？ | 后端 8 人日 + 前端 8 人日 + 测试 3 人日 = 24 人日（估算，含两条链路） |
| 最容易漏的是什么？ | **链路 2**。chatflow / workflow 走 `RunAgentAsApp`，与聊天页的 `AsyncChat` 是两套独立链路（见 2.1） |
| 规则配在哪？ | **配在聊天应用与对话流的设置页内**（应用级绑定，仅本应用生效），不建独立的「规则管理」模块；质检模块只做全局查看（实时质检 + 命中记录） |

## 二、能力盘点：现有系统有什么

逐项核对了代码，结论如下：

| 需要的能力 | 现状 | 代码位置 | 能否复用 |
|---|---|---|---|
| 实时对话流式链路 | ✅ 有 | `chat_pipeline.go:1119` 的 `send()` 是每个 delta 的统一出口；`fullAnswer` 累积全文 | ✅ **可直接挂点** |
| 统一聊天入口 | ✅ 有 | `AsyncChat` 有 3 个调用方：`chat_session.go:1280`（聊天页）、`bot_completion.go:435`（ChatbotCompletion：外部 bot + chatbots 分享页）、`openai_chat.go:344`（OpenAI 兼容） | ✅ 在 `AsyncChat` 内部插一处，覆盖链路 1 全部入口 |
| agent 画布运行时入口 | ✅ 有 | `RunAgent`（`agent.go:1485`）是链路 2 的收敛点：`app_run.go:99` ChatFlow、`app_run.go:56` RunWorkflow、`bot.go:162` AgentbotCompletion、`/agents/:canvas_id/run` 调试、`agent_webhook.go` | ✅ 在 `RunAgent` 出口插一处，覆盖链路 2 全部入口 |
| 消息队列 | ✅ 有 | NATS（`internal/server/config.go:253`） | ✅ 异步旁路有现成设施 |
| 关键词规则存储 | ❌ 无 | `user-setting` 页只有 chat-channel / compilation-templates / data-source / mcp / profile / setting-api / setting-model / setting-team | ❌ 需新建 |
| 关键词匹配引擎 | ❌ 无 | 全仓无敏感词 / 质检 / 内容审核设施 | ❌ 需新建 |
| 质检提示推送通道 | ❌ 无 | `AsyncChatResult`（`chat_pipeline.go:89-110`）与 `canvas.RunEvent` 均无通用扩展位 | ❌ 两条链路各需加字段或新事件 |
| 质检管理界面 | ❌ 无 | 前端无质检相关页面 | ❌ 需新建 |
| 坐席工作台 | ❌ 无 | RAGFlow 只有用户侧聊天，无坐席侧 | ❌ 需外部系统或新建 |

**关键有利条件**：两条链路各有唯一收敛点（`AsyncChat` / `RunAgent`），各插一个挂点即可，
不需要在 8 个调用方分别改。改造范围从「散点」收敛到「两点」。

### 2.1 ⚠️ 两条执行链路（初版评估遗漏，已补充）

系统有**两条完全独立的对话执行链路**，只挂一条会漏掉一半入口：

```
链路 1  Chat Pipeline（AsyncChat）——面向「聊天」形态
├── 聊天页              chat_session.go:1280
├── 外部 bot            bot_completion.go:435（ChatbotCompletion）
├── OpenAI 兼容         openai_chat.go:344
└── chatbots 分享/嵌入   use-send-shared-message → ChatbotCompletion → AsyncChat

链路 2  Agent Canvas Runtime（RunAgent）——面向「画布」形态
├── chatflows 公开 API   app_run.go:99  ChatFlow → RunAgentAsApp → RunAgent
├── workflows 公开 API   app_run.go:56  RunWorkflow → RunAgentAsApp → RunAgent
├── agentbots 分享/嵌入  bot.go:162    RunAgent
├── 编辑器调试运行       /agents/:canvas_id/run → RunAgent
└── Webhook 触发         agent_webhook.go → RunAgent
```

> **勘误说明**：初版评估只识别出链路 1，并据此得出「一个挂点覆盖全部入口」的结论。
> chatflow / workflow 走 `RunAgentAsApp`，与 `AsyncChat` 无关。
> 若按初版实施，**所有 chatflow 与 workflow 会话都不会被质检**。

### 2.2 两条链路的行为差异（影响产品规则）

| 维度 | 链路 1（聊天） | 链路 2（画布） |
|---|---|---|
| 出口类型 | `AsyncChatResult.Answer` 文本增量 | `canvas.RunEvent` 结构化事件 |
| 质检文本位置 | delta 累积的 `fullAnswer` | chatflow 取 `message` 事件；workflow 取 `node_finished` 的 End outputs |
| 是否可阻断 | ✅ 替换 delta 为替代话术 | **仅 Chatflow 可阻断** |
| Workflow 为何不阻断 | — | 输出是结构化 JSON，供下游系统消费，替换会破坏调用方数据契约 |
| tenant 来源 | 登录用户 `userID` | 画布 owner `canvasRow.UserID`（API Key 调用时无用户） |
| 调试运行 | — | `trigger_type=debug` 时只记录，不阻断不告警 |

## 三、零改造方案评估：为什么不选

### 3.1 唯一接近的零改造做法

用 Agent 画布现有节点拼：

```
开始 → Categorize（LLM 判断是否命中质检词）→ Switch → 分支处理
```

`Categorize`（`internal/agent/component/categorize.go`）和 `Switch` 节点已存在，无需改后端。

### 3.2 三个硬伤

| # | 硬伤 | 说明 |
|---|---|---|
| 1 | **不是集中配置** | 关键词要写死在画布节点里，每个应用一套。客户要的是「质检管理」——统一配、统一看、统一审计 |
| 2 | **不是实时拦截** | `Categorize` 是 LLM 分类，跑在生成之前，只能决定「走哪条分支」，无法在流式输出过程中命中关键词后即时提示 |
| 3 | **没有提示与看板** | 节点分支只能改变回答内容，无法把「命中规则 X，提示信息 Y」推给质检员，也无法产出质检记录与统计 |

### 3.3 判定

零改造方案能解决「关键词分流」（约 40% 诉求），解决不了「实时质检管理」。
且它把配置成本转嫁给每个应用的搭建者，与客户「集中管理」的诉求相反。

**结论：走改造路线。**

## 四、推荐方案：双通道质检

### 4.1 架构

```
                        ┌──────────────────────────────┐
   用户消息 / AI 回答 ──→│  AsyncChat 内的质检挂点      │
                        │  chat_pipeline.go:1119 send()│
                        └──────────┬───────────────────┘
                                   │
              ┌────────────────────┴────────────────────┐
              │ 同步通道（轻量，不阻塞）                  │ 异步通道（NATS，不阻塞）
              │ · 增量关键词匹配 O(n)                   │ · 写质检记录
              │ · block 级：直接拦截该 delta            │ · 实时推送到质检面板
              │ · 命中即打标记                          │ · 聚合统计
              └────────────────────┬───────────────────┘ └──────────┬──────────────────┘
                                   │                               │
                            用户无感知                      质检看板 / 告警
```

### 4.2 为什么双通道

| 通道 | 承载 | 理由 |
|---|---|---|
| 同步 | `block` 级拦截 | 必须在内容到达用户前拦住，只能同步 |
| 异步 | `log` / `alert` 级记录与推送 | 不阻塞聊天主链路；NATS 已有；质检服务故障不影响对话 |

**红线：异步通道失败不得影响聊天。** 质检是旁路，不是主链路的依赖。

### 4.3 匹配位置

| 质检对象 | 挂点 | 说明 |
|---|---|---|
| AI 回答 | `send()` 内，对 delta 与 `fullAnswer` 双重匹配 | delta 做实时拦截，`fullAnswer` 做兜底（防关键词被拆到两个 delta） |
| 用户输入 | `AsyncChat` 入口的消息预处理处 | 命中即记录，用于「用户说了敏感词」的风险识别 |

### 4.4 方案对比

| 方案 | 成本 | 实时性 | 覆盖面 | 风险 | 结论 |
|---|---|---|---|---|---|
| A. 画布节点分流（零改造） | 无 | 差（生成前） | 单应用 | 低 | ❌ 不满足诉求 |
| B. 单通道同步质检 | 低 | 好 | 全入口 | 中（阻塞主链路） | 备选 |
| **C. 双通道（同步拦截 + 异步记录）** | 中 | 好 | 全入口 | 低 | ✅ **推荐** |
| D. 外挂独立网关（所有流量过质检代理） | 高 | 好 | 全流量 | 高（新增单点） | 过度设计 |

## 六、定制功能点

### 6.1 规则配置（FR-01）

| 编号 | 功能 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-01-01 | 关键词多值配置 | 一条规则可配多个关键词，换行或逗号分隔；单规则 ≤50 个词 | Given 输入「保本,稳赚」，Then 保存后两个词都参与匹配 |
| FR-01-02 | 匹配模式 | 支持 `包含`（默认）/ `全词匹配` / `正则` | Given 选正则 `保本.{0,4}收益`，Then 「保本高收益」命中 |
| FR-01-03 | 作用范围 | `AI 回答` / `用户输入` / `两者`，默认 AI 回答 | Given 选「用户输入」，Then AI 回答命中不记录 |
| FR-01-04 | 严重级 | `提示(info)` / `警告(warn)` / `阻断(block)` | Given 选 block，Then 命中时该回答不返回用户 |
| FR-01-05 | 提示信息 | 每条规则可配一段提示文案，质检面板展示 | Given 命中规则 A，Then 面板显示 A 的提示信息 |
| FR-01-06 | 动作 | `记录` / `记录并告警` / `阻断并告警` | Given 选阻断并告警，Then 同时拦截与推送 |
| FR-01-07 | 启停 | 单条规则可启停；停用不参与匹配 | Given 停用规则 A，Then 命中不再记录 |
| FR-01-08 | 规则上限 | 单租户 ≤200 条（可配）；超出提示升级 | Given 已有 200 条，Then 新建被拒并提示 |

### 6.2 实时质检（FR-02）

| 编号 | 功能 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-02-01 | 实时匹配 | AI 回答每个 delta 都过质检；`fullAnswer` 兜底匹配 | Given 关键词「收益」被拆到两个 delta，Then 兜底匹配仍能命中 |
| FR-02-02 | 增量匹配 | 已匹配过的位置不重复报；同一规则同一会话只报一次 | Given 一段话出现两次「保本」，Then 只记 1 条 |
| FR-02-03 | 阻断动作 | `block` 级命中时该 delta 不发给用户；可配置替换为固定话术 | Given 命中 block 规则，Then 用户看到的是替换话术 |
| FR-02-04 | 实时推送 | `告警` 级命中经 NATS 推送到质检面板，延迟 ≤2s | Given 命中 warn 规则，Then 2s 内面板出现该事件 |
| FR-02-05 | 旁路隔离 | 质检服务异常不得影响聊天 | Given 质检服务宕机，Then 聊天正常，只是没有质检记录 |
| FR-02-06 | Chatflow 阻断 | 链路 2 的 Chatflow `message` 事件命中阻断级时替换为提示信息 | Given Chatflow 命中阻断，Then 用户收到替代话术 |
| FR-02-07 | Workflow 不阻断 | 链路 2 的 Workflow End 输出命中只记录 + 告警，不改写输出 | Given Workflow 命中阻断规则，Then 返回给调用方的 JSON 与原文一致 |
| FR-02-08 | 调试运行豁免 | `trigger_type=debug` 时只记录，不阻断不告警 | Given 编辑器试运行命中阻断规则，Then 画布正常显示原文 |
| FR-02-09 | API Key 归属 | 记录 `tenant_id` 为画布 owner，与调用方身份解耦 | Given 用 API Key 调 chatflow，Then 按画布 owner 的规则集质检 |

### 6.3 质检看板与记录（FR-03）

| 编号 | 功能 | 业务规则 | 验收标准 |
|---|---|---|---|
| FR-03-01 | 实时面板 | 展示当前租户进行中会话的命中事件流 | Given 有新命中，Then 面板自动追加 |
| FR-03-02 | 记录查询 | 按时间范围/规则/会话/严重级/动作筛选 | Given 选 block 级，Then 只显示阻断记录 |

| FR-03-05 | 统计 | 按规则统计命中次数、按日趋势 | Given 看统计，Then 数字与明细一致 |

## 九、待澄清（影响范围与排期）

| # | 问题 | 影响 |
|---|---|---|
| Q1 | **质检提示给谁看？** 本方案假设给「质检/运营人员」看（后台面板）。若要给坐席看，RAGFlow 没有坐席工作台，需外部系统对接或新建，工作量 +8~12 人日 | 大 |
| Q2 | **是否需要阻断动作？** 只做「记录+提示」工作量减 2 人日，风险也大幅下降 | 中 |
| Q3 | **质检对象包含用户输入吗？** 本方案默认两者都支持，可配置 | 小 |
| Q4 | **是否需要正则匹配？** 只要「包含」可减 1 人日 | 小 |
| Q5 | **规则是否需要按应用维度隔离？** 本方案默认租户级全局；若需按应用，加 1 人日 | 小 |
| Q6 | **保留期要求？** 涉及合规审计，需法务确认，默认 180 天 | 中 |

## 十、分期建议

| 阶段 | 内容 | 工作量(估算) |
|---|---|---|
| **MVP** | 规则 CRUD（仅包含匹配）+ 同步记录 + 查询页 + 启停 + **两条链路挂点** | 后端 8d + 前端 8d + 测试 3d |
| V1.1 | 实时推送面板 + 阻断动作（含 Chatflow 链路 2 阻断）+ 正则匹配 + 规则测试工具 | +6d |
| V2.0 | 统计看板 + 导出 + 白名单 + 按应用隔离 | +5d |

**MVP 即可交付核心价值**：客户能在聊天/对话流内配置质检关键词、看到命中记录。实时推送与阻断是体验增强，可作为第二期。

> **信息架构说明（v1.1）**：规则配置入口在**聊天应用设置页**与**对话流编辑器设置面板**内（应用级绑定），
> 不建独立的「规则管理」模块；质检模块只保留「实时质检」「命中记录」两个查看页。
> 若后续有跨应用统一管控诉求，再加「租户级默认规则」作为 V1.1 增强。

> **工作量修正**：初版估算后端 6d，漏了链路 2 挂点（B9+B10 = 2.5d）。修正后后端 8d，总计 **24 人日**。
> 链路 2 的挂点即使在 MVP 也**必须做**——否则 chatflow 与 workflow 的会话完全不被质检，
> 而这两个形态正是本次项目的主要交付物。
