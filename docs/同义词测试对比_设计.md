## 一、现状与问题

当前 `TestCompareDialog` 的实现在注释里写得很清楚：

> 完整「新配置」检索需重建受影响 chunk 的 BM25 索引（增量测试沙箱），本阶段采用降级方案（PRD 4.2 允许）：展示 diff + 原配置基准。

落到界面上就是用户看到的样子：

- 弹窗标题写着「原配置 **vs** 新配置」，实际只展示原配置一栏
- 底部用一行小字坦白「本阶段为降级对比：展示原配置检索基准。发布后……可能改变排序并召回新结果」
- **没有任何对比分析**——没有新增召回、没有丢失召回、没有排序变化、没有得分变化

这带来三个直接后果：

1. **测试失去意义**：用户花时间输入问题、点测试，得到的是本来就能看到的结果，对「要不要发布」零帮助。
2. **决策被推给运气**：文案暗示"发布后可能变好也可能变坏"，用户只能盲发。
3. **信任损耗**：标题承诺 vs、内容不给 vs，比不做这个功能更伤。

**结论：这个功能要么做真对比，要么明确降级为「变更摘要预览」。不能停留在中间态。**

---

## 二、核心判断：不需要重建索引也能做真对比

原实现之所以降级，是基于一个假设：相似问/同义词改了就得重建索引才能测。

这个假设对一半：

| 变更类型 | 真实生效方式 | 是否需要重建索引 | 本方案做法 |
|---|---|---|---|
| 同义词 / 专有词 | **query 侧扩写**，把同义词加进检索词 | **不需要** | query 扩写后多跑几次检索，同 chunk 取 max |
| 相似问 | 给 chunk 增加一个 question 匹配点 | 发布后会写入 question 向量索引 | **查询侧近似**：把新增相似问当 query 直接检索 |

**同义词是精确模拟**：同义词表从始至终只作用于 query，不碰索引，扩写后重跑即可完全等价。

**相似问是查询侧近似**：相似问的真实作用是「chunk 多了一个问题向量，用户 query 能匹配上它」。
把它当作 query 去检索，等价于回答「如果用户这么问，能不能命中这个 chunk」——这正是相似问要达到的效果。
两者在检索结果上等价，代价是零索引改动。

> 这个近似必须对用户明示（见 5.3 的「对比方式」标签与说明），不能假装精确。

## 三、方案：影子检索（Shadow Retrieval）

一次测试请求里跑两遍检索，两侧使用**完全相同的 TopK / 阈值 / rerank / 权重**：

```
                        ┌─ 原配置（live）        ─→ baseline hits
query ──┬───────────────┤
        │               └─ query 扩写（live + 变更集同义词） ─┐
        │                                                    ├→ 合并取 max ─→ candidate hits
        └─ 新增相似问（逐条当 query）──────────────────────────┘
```

### 3.1 为什么是「影子」而不是「沙箱」

| 方案 | 成本 | 时效 | 结论 |
|---|---|---|---|
| 增量测试沙箱（重建受影响 chunk 索引） | 高：要建临时索引、隔离生命周期、清理 | 慢：分钟级 | ❌ 为一次测试建索引，投入产出不成比例 |
| 影子检索（应用层补检索） | 低：多跑 N 个 query | 快：百毫秒级 | ✅ 测试场景可接受 |
| 前端模拟 | 无后端成本 | 立即 | ❌ 结果不真实，等于骗人 |

影子检索的额外成本是 N+1 次检索（N = 参与的同义词扩展数 + 新增相似问抽样数），
对一个用户主动点击的测试弹窗完全可接受。

## 四、接口设计

### 4.1 新端点

`POST /api/v1/datasets/:dataset_id/change-sets/:change_set_id/retrieval-compare`

复用现有 `RetrievalTestRequest`（`internal/service/chunk_types.go:27`），扩展字段：

```go
type RetrievalCompareRequest struct {
    RetrievalTestRequest            // question / top_k / similarity_threshold / vector_similarity_weight ...
    MaxShadowQueries int `json:"max_shadow_queries"` // 影子检索 query 上限，默认 8
}
```

### 4.2 响应

```json
{
  "code": 0,
  "data": {
    "baseline": {
      "hits": [{"chunk_id":"c1","doc_keyword":"...","content":"...","similarity":0.457,"rank":1}],
      "took_ms": 120
    },
    "candidate": {
      "hits": [{"chunk_id":"c1","similarity":0.512,"rank":1}],
      "took_ms": 260,
      "queries_issued": ["你好","您好","你好呀"],
      "sampled": false
    },
    "diff": {
      "added":    [{"chunk_id":"c12","similarity":0.461,"rank":3}],
      "removed":  [{"chunk_id":"c5","similarity":0.382,"rank":5,"reason":"pushed_out_of_topk"}],
      "reordered":[{"chunk_id":"c1","before_rank":1,"after_rank":2,"before_score":0.457,"after_score":0.512}],
      "score_changed":[{"chunk_id":"c1","before":0.457,"after":0.512,"delta":0.055}],
      "summary": {
        "baseline_count":5,"candidate_count":6,
        "added_count":1,"removed_count":1,"reordered_count":2,
        "avg_score_delta":0.021
      }
    },
    "config_summary": {
      "similar_questions_added":21,
      "synonyms_added":0,
      "shadow_query_count":3,
      "approximation": "similar_questions_use_query_side_approximation"
    }
  }
}
```

### 4.3 `removed.reason` 取值

| 值 | 含义 |
|---|---|
| `pushed_out_of_topk` | 得分仍在，但被新结果挤出 TopK |
| `below_threshold` | 得分跌到阈值以下 |
| `not_recalled` | 影子检索中该 chunk 未被任何 query 召回 |

这个区分很重要：`pushed_out_of_topk` 是排序竞争变激烈（可能变好），
`below_threshold` 是相关性真的掉了（需要警惕）。

### 4.4 限流与保护

| 项 | 值 | 说明 |
|---|---|---|
| 影子 query 上限 | 8（可配） | 变更集有 500 条新增相似问时，取与 query 最相关的 8 条，`sampled=true` |
| 整体超时 | 10s | 超时返回 `SHADOW_TIMEOUT`，**不返回半截结果** |
| 并发 | 影子 query 并行发起 | 控制 P95 在 500ms 内 |

## 五、前端交互设计

### 5.1 结构

```
┌──────────────────────────────────────────────────────────────┐
│ 测试对比 · 原配置 vs 新配置                    [变更集] [影子检索·不重建索引] │
├──────────────────────────────────────────────────────────────┤
│ 待生效变更：＋相似问 21 条 · 同义词 0 条                       │
│ 测试问题 [你好        ] TopK [5] 阈值 [0.2] [测试] [复制报告]   │
├──────────────────────────────────────────────────────────────┤
│ 原配置命中 5 │ 新配置命中 6 │ 新增 +1 │ 丢失 -1 │ 排序变化 2 │ 平均分 +0.021 │
├───────────────────────────────┬──────────────────────────────┤
│ 原配置 · 已生效       5条·120ms │ 新配置 · 生效配置+变更集  6条·260ms │
│ #1 …0.457                     │ #1 …0.512  [排序↑]          │
│ #2 …0.434                     │ #2 …0.489  [排序↑] Δ+0.025  │
│ #3 …0.464                     │ #3 …0.461  [新增召回]       │
│ #4 …0.398                     │ #4 …0.428  [排序↓]          │
│ #5 …0.382                     │ #5 …0.404  [排名不变]       │
│                               │ #6 …0.382  [丢失召回](虚框) │
├───────────────────────────────┴──────────────────────────────┤
│ ▾ 差异分析明细   新增 1 · 丢失 1 · 排序变化 2 · 得分变化 3     │
│   新增召回  「你好呀」→ #12 客户服务规范(2).txt · 0.461        │
│   丢失召回  #5 开户流程说明.txt · 0.382  被挤出 Top5          │
│   …                                                          │
├──────────────────────────────────────────────────────────────┤
│ 对比结果仅用于发布前评估，不影响线上检索     [关闭] [发布变更集] │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 关键设计决策

**决策 1：六张指标卡置顶，而不是先看列表**
用户第一眼就要知道「这次变更到底有没有影响、影响多大」。新增/丢失/排序变化/平均分变化
四个数字就能定决策，不需要逐条比对。
- 有变化 → 指标卡用色（涨绿跌红，遵循国内约定）
- 全零 → 明确说「新配置对本问题无影响」，避免用户以为自己漏看了

**决策 2：双栏同序展示，不用「合并 diff 视图」**
合并视图（一条 chunk 同时显示 before/after）信息密度高但难读。
双栏同序能让用户直接横向扫「同一名次两边分别是什么」，丢失项在右栏用虚框占位保持行位对齐。

**决策 3：差异明细可折叠，默认展开**
明细是给「想知道为什么」的用户准备的，默认展开但可收起，避免默认状态信息过载。

**决策 4：复制报告**
把指标 + 差异明细拼成 Markdown，方便贴到工单/群里评审。研发内部走查的刚需。

**决策 5：发布按钮留在弹窗内**
测试完直接发布，缩短「测→判→发」链路。但要带二次确认，因为发布会影响线上。

### 5.3 诚实性设计（最重要）

| 原则 | 落地 |
|---|---|
| 不假装精确 | 「对比方式」固定标注 **影子检索 · 不重建索引**，tooltip 说明相似问走查询侧近似 |
| 不静默降级 | 新配置检索失败时**只显示错误与原因**，不退回「只展示原配置」——那会让评估失真 |
| 不夸大结论 | 平均分变化只描述「整体相关性上升/下降」，不给「建议发布/不建议发布」的结论 |
| 参数必须可见 | TopK / 阈值 / 权重展示在界面上，因为对比结论完全依赖它们 |

## 六、状态机

| 状态 | 触发 | 表现 |
|---|---|---|
| `idle` | 打开弹窗 | 双栏空态引导，指标卡全 `—` |
| `loading` | 点击测试 | 指标卡 + 双栏 + 明细**三处同时出骨架**，不能只 loading 一栏 |
| `done` | 两侧都成功 | 完整对比 |
| `done_no_effect` | diff 全零 | 双栏展示，指标卡全 0，明细写「无差异」 |
| `partial_fail` | 原配置成功、新配置失败 | **只显示错误**：原因 + 处置建议；不给 diff；不给发布快捷入口 |
| `shadow_timeout` | 超 10s | 同 partial_fail，原因写超时，提供「减少 TopK 重试」 |
| `sampled` | 新增相似问 > 上限 | 正常出结果，但在 config_summary 标注已抽样，明细说明抽样条数 |

## 七、Diff 算法

```python
b = {hit.chunk_id: (hit.rank, hit.similarity) for hit in baseline.hits}
c = {hit.chunk_id: (hit.rank, hit.similarity) for hit in candidate.hits}

added    = c.keys() - b.keys()          # 按 c 的 rank 升序
removed  = b.keys() - c.keys()          # 按 b 的 rank 升序，带 reason
both     = b.keys() & c.keys()
reordered = [k for k in both if b[k].rank != c[k].rank]
score_changed = [k for k in both if abs(b[k].score - c[k].score) > 1e-4]

avg_score_delta = mean(c[k].score for k in c) - mean(b[k].score for k in b)
```

要点：

1. **key 用 `chunk_id`**，不用内容哈希——同一 chunk 内容不变，id 稳定。
2. **`removed` 必须给 reason**（见 4.3），否则用户无法判断是「排序竞争」还是「相关性下降」。
3. **排序变化和得分变化是两个维度**：得分没变但名次变了（被别人挤下去），和名次没变但得分变了，含义完全不同，都要单独报。
4. **阈值以下的 chunk 不出现在 hits 里**，所以 `below_threshold` 的判定要单独查一次该 chunk 的原始得分。

## 八、埋点与度量

| 事件 | 字段 | 用途 |
|---|---|---|
| `synonym_compare_run` | question_len、top_k、threshold、baseline_count、candidate_count、added/removed/reordered_count、avg_score_delta、took_ms、sampled | 看功能是否被用、对比是否稳定 |
| `synonym_compare_result_view` | 是否展开明细、是否复制报告 | 看信息层次是否合理 |
| `synonym_publish_after_compare` | 从对比弹窗直接发布 | **核心指标：测试是否真的影响决策** |
| `synonym_publish_without_compare` | 未测对比直接发布 | 若该比例远高于前者，说明测试入口或结论不够好用 |

北极星指标：**「测过对比再发布」的比例**。若低于 50%，说明这个功能没有解决真实决策问题，需要回炉而不是继续加功能。

## 九、分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P0** | 影子检索 + 双栏对比 + 六指标卡 + diff 明细 + 诚实失败 | 一个含同义词变更、一个含相似问变更、一个无影响、一个 rerank 缺失，四种场景都能给出可信结论 |
| **P1** | 复制报告（Markdown）、发布后真实效果回补、历史测试记录 | 发布后可用同一问题跑 live 配置，与发布前的 candidate 预测对照，验证近似可信度 |
| **P2** | 批量问题回归（一组标准问题集跑对比，输出汇总指标） | 变更集影响面从「一个问题」扩展到「一类问题」 |

**P1 的「发布后回补」是关键信任建设**：它直接回答「影子检索的预测准不准」，
把近似性从"我们说是近似"变成"我们能验证近似"。

## 十、风险

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 相似问的查询侧近似与真实发布效果有偏差 | 4 | 4 | UI 明示近似；P1 做发布后回补验证；偏差大则在文档给出修正系数 |
| R2 | 多 query 影子检索导致延迟上升 | 3 | 3 | query 上限 8；并行；10s 超时；抽样时提示 |
| R3 | rerank 模型缺失导致无法对比 | 3 | 4 | 诚实失败 + 给出「仅看原配置」的明确取舍说明，不默认降级 |
| R4 | 变更集过大（数百条相似问）时抽样不准 | 3 | 3 | 按与 query 的相关性取 Top8，标注 `sampled` |
| R5 | 用户误以为对比结论等同于线上效果 | 3 | 3 | 底部固定文案「仅用于发布前评估，不影响线上检索」；不做建议性结论 |
| R6 | 阈值以下 chunk 的 reason 判定需要额外一次检索 | 2 | 2 | 仅对 `removed` 项补查，量小 |

## 十一、待确认

1. **影子 query 上限默认 8 是否合适？** 与延迟的权衡需要压测数据校准。
2. **是否允许在弹窗内直接发布？** 当前设计允许（带二次确认）；若客户流程要求审批，需改为跳审批。
3. **相似问近似是否需要在界面上更醒目？** 现在是 tooltip + 标签，可以考虑在首次使用时弹一次说明。
4. **P1 的发布后回补是否需要自动跑？** 自动跑会增加成本，建议手动触发。
5. **历史测试记录保留多久？** 建议与变更集同生命周期，变更集发布/丢弃后一并清理。
