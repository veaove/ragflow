# 实时质检 —— 语义质检技术方案

> 前置文档：`docs/实时质检管理_技术详设.md`（关键词质检已实现并上线）
> 本文只讨论「语义质检」如何加在现有框架上，不重复关键词质检的设计。
> 结论先行：**不新建链路、不新建匹配通道，只扩展 `CompiledRules` 的判定方式**。

---

## 一、结论先行

### 1.1 三种可落地的判定方式

| 方案 | 能识别什么 | 依赖 | 单次延迟（估算） | 成本 | 可解释性 |
|---|---|---|---|---|---|
| **A. 向量相似度**（句子 embedding + 余弦） | 「换一种说法」的同一违规意图，如规则是「保本保收益」，命中文案「稳赚不赔、不会亏」 | 一个 embedding 模型 | 20–80 ms（本地 CPU，批 10–20 句） | 一次性部署，无按次费用 | 高：给出命中句 + 分数 + 最相似的样本句 |
| **B. LLM 裁判**（规则描述 + 文本交给大模型判定） | 需要语义理解 + 常识推理的规则，如「暗示收益确定性」「贬低竞品」 | 一个 chat 模型 | 800–3000 ms | 按 token 计费 | 中：模型给理由，但理由不稳定 |
| **C. 混合**（A 召回 → B 复核） | A 的覆盖率 + B 的准确率 | embedding + chat | A + 仅候选集调 B | 比 B 低一个量级 | 高 |
| **D. Rerank 交叉编码器**（规则描述 vs 句子相关性打分） | 比 A 准（cross-encoder 直接建模两者交互） | 一个 rerank 模型 | 10–30 ms/**对** | 同 A | 中：只给分数不给依据 |

**为什么不用 D**：A 是「一次 embed 句子，再对 N 条规则做 N 次内存点积」，成本与规则数几乎无关；D 是「每句 × 每条规则」各跑一次前向，10 条规则 × 12 句 = 120 次前向，CPU 上累计 1–4 秒，实时质检扛不住。它更适合「人工点一下、等结果」的离线抽检，不是逐条回答的旁路。仓库里 `NewRerankModel` 已存在（`internal/service/model_factory.go`），若后续要做「离线批量复核」可直接复用，不占用在线路径。

### 1.2 本项目的推荐路线

**一期做 A（向量相似度），把 B/C 留成同一套数据结构下的开关。**

三条理由，都基于当前仓库与部署的实际情况：

1. **部署里现在没有任何模型。** 我查了线上库，`llm` 表 0 行、`tenant_llm` 无记录。所以任何依赖外部大模型 API 的方案今天都跑不起来，而向量方案只需要一个 embedding 服务。
2. **本地向量化能力仓库里已经有。** `Dockerfile_tei` 已把 `BAAI/bge-m3`、`bge-small-en-v1.5`、`Qwen3-Embedding-0.6B` 打进镜像，`docker/docker-compose-base.yml` 已有 `tei-cpu` / `tei-gpu` 服务；模型驱动侧有 `OpenAI-API-Compatible`（`internal/entity/models/openai_api_compatible.go`），TEI 的 `/v1/embeddings` 可以直接注册成 embedding 模型。**不需要写任何模型接入代码。**
3. **质检是逐条答案实时跑的。** LLM 裁判每次 1–3 秒、按 token 付费，放在每个回答上都不可接受；向量相似度是纯 CPU、毫秒级、可离线，才配得上「实时」两个字。

### 1.3 语义质检不能替代关键词质检

这点要在产品上说清楚，避免后续做成「有了语义就把关键词关掉」：

- 关键词质检是**确定性**的：命中就一定命中，法务、合规要求的「必须拦截某些词」只能靠它。
- 语义质检是**概率**的：有阈值、有误判，只适合「说得不一样但意思一样」这类长尾。
- 两者是**叠加**关系：一条规则要么配关键词、要么配语义样本，也可以同一规则两者都配（关键词先拦，语义兜底）。

## 二、现状与差距

### 2.1 现有的判定链路（不改）

```
AsyncChat (chat_pipeline.go)                    RunAgent (agent.go)
   └── wrapQcChannel                                └── wrapAgentQcChannel
         └── QcSession                                   └── QcSession
               └── StreamMatcher.Inspect(delta, scope)         （同上）
                     └── CompiledRules.Match(seg, scope)  ← 纯关键词，同步，一次性
                           └── QcHitResult → record → qc_hit + 告警推送
```

关键约束（决定了语义质检的接入形态）：

| 现有事实 | 对语义质检的影响 |
|---|---|
| `CompiledRules.Match` 是**同步纯函数** | 语义判定要发网络/CPU 请求，必须给它加**超时与熔断**，不能让它无限阻塞 SSE |
| `StreamMatcher` 是**单 goroutine**、非并发安全 | 语义状态不能另开 goroutine 直接改它，否则要引入锁或 select 分支 |
| `StreamMatcher.Inspect` 处理的是 **delta** | 向量比较需要**完整句子**，delta 级别没法 embed，必须按句边界攒 |
| `fired map[string]bool` 按规则去重 | 语义命中同样按规则去重，天然复用 |
| 命中后 `Blocked` 会替换整段答案 | 语义拦截沿用它：命中即替换为 `prompt_message` |

### 2.2 差距清单

1. `qc_rule` 没有「判定方式」字段，只有 `match_mode`（contains / whole_word / regex）。
2. 没有存放语义样本句的地方——语义规则的「关键词」实际是**若干条表达同一违规意图的示例句子**。
3. 没有 embedding 调用，也没有样本句的向量缓存（每次质检都 embed 样本句是浪费）。
4. `QcTestMatch` 只做关键词预览，运营无法校准阈值。
5. `qc_hit` 没有分数，事后无法回答「这条为什么算命中」。

## 三、总体设计

### 3.1 一条新分支，不是一条新链路

`CompiledRules` 内部按规则拆成两个判定器，`Match` 对关键词规则照旧、对语义规则走异步判定器：

```
CompiledRules
├── keywordRules []compiledRule          ← 现有，不动
├── semanticRules []semanticRule         ← 新增
│     ├── Rule        *entity.QcRule
│     ├── Examples    []exampleVector    ← 预计算向量，带缓存
│     └── Threshold   float64
└── semanticEngine *SemanticEngine       ← 新增，可选（无模型时为 nil）
```

`SemanticEngine` 只做三件事：**分句 → 向量化 → 比较**。它不感知链路、不感知阻断，只回答「这段文本对这条规则的相似度是多少」。

### 3.2 执行时机：按句边界，而不是按 delta

语义必须拿到完整句子才能判定。所以引入**句边界触发器**：

```
delta 流式到达
   ↓
StreamMatcher.Inspect(delta)            ← 关键词照旧，逐 delta
   ↓
攒进 pending 缓冲；检测到句末标点（。！？；\n ……）
   ↓
语义检查（同步，带 300ms 硬超时）
   ↓ 命中
沿现有 block/warn 通道产出 QcHitResult
```

回答结束时（`message_end` / `Final`）**兜底 flush 一次**，把最后一句没标点的尾巴也检查掉。

这样做的效果：语义拦截**通常发生在流式过程中**，和关键词拦截的体感一致，不会出现「整段答案都看完了才突然被替换」。

**用户输入（`scope=user_input`）不走句边界触发。** `QcSession.InspectUserInput` 拿到的是完整提问，没有 delta，直接在整段上切句判定一次即可——复用同一个 `SemanticEngine`，不需要额外的时序设计。注意现有实现里用户输入只记录不阻断（拦截用户自己的话没有意义），语义分支保持同一语义。

### 3.3 为什么不做全异步

另有两条路，都不选：

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 全异步 + `select` 分支回灌 | 完全不阻塞流 | `wrapQcChannel` / `wrapAgentQcChannel` 要改成双通道 select，`StreamMatcher` 要加锁，两条链路都要动；且异步结果到达时答案可能已经写完，拦截变成「事后替换」 | 不选 |
| 只在回答结束后检查 | 实现最简单 | 用户看完才被替换，体感差；且 `Final` 帧已被前端消费 | 不选 |
| **同步 + 硬超时（本方案）** | 改动局限在 `StreamMatcher` 内部，两条链路零改动 | 每句最多阻塞 300ms | 采用 |

300ms 的上限是兜底值：正常本地 CPU 对一句中文的 embed 在 20–50ms 量级（**待实测确认**），超时按降级处理，见 §9。

## 四、匹配引擎设计

### 4.1 分句规则

```go
// splitSentences 按中英文句末标点切句，保留标点。
// 不引入 NLP 分词库：质检只关心「一句话是否表达同一违规意图」，
// 标点切分足够，且不会因为分词错误导致误判。
func splitSentences(text string) []string
```

- 终止符：`。！？；!?;\n`
- 每句长度上限 200 字符（超长按逗号再切），下限 4 字符（过短不判定，避免「好的」「是的」这类噪声）
- 句子带**句内偏移**，命中后回填到 `qc_hit.matched_text`

### 4.2 相似度计算

```
score(sentence, rule) = max_{e ∈ rule.examples} cos(embed(sentence), e.vector)
```

- 归一化后点积即余弦（embedding 输出先 L2 归一化，缓存也存归一化后的向量）
- **取 max 而不是平均**：一条规则的多条样本句是「同一违规的不同说法」，命中任意一条即为命中，平均会把命中稀释掉
- `cos` 用 `float32` 累加，1024 维一次性约 1μs，可忽略

### 4.3 阈值

按模型尺度分档，**不给统一默认值糊过去**：

| 模型 | 建议初始阈值 | 说明 |
|---|---|---|
| `BAAI/bge-m3`（1024 维） | 0.62 | 多语言、跨域表现好，尺度偏「平」，阈值不能照搬 bge-large |
| `Qwen/Qwen3-Embedding-0.6B`（1024 维，`.env` 当前默认） | 0.65 | 仓库 `TEI_MODEL` 的默认值，中文短句区分度尚可，**以实测校准为准** |
| `BAAI/bge-small-zh-v1.5`（512 维） | 0.68 | 中文短句区分度更高 |
| 其他 | 0.65 | 兜底 |

规则里 `similarity_threshold = 0` 表示「用模型对应的建议值」；运营在测试面板上调出来的值以规则为准。

> 阈值**必须**能按规则单独调，且必须提供校准工具（§8.2）。任何「拍一个 0.8 全租户通用」的做法，上线一周就会被业务反馈成「该拦的不拦、不该拦的乱拦」。

### 4.4 命中聚合与去重

- 逐句判定，**同一规则只报第一次命中**（复用 `StreamMatcher.fired`）
- 报的 `matched_text` 是**第一句越线的原文**，不是整段
- 已检查过的字符位置记 `checkedRunes`，只检查新增部分，不重复 embed

### 4.5 与关键词共存的优先级

同一规则若同时配了关键词和语义样本：**关键词优先**。关键词命中后 `fired[rule] = true`，语义分支看到已 fired 直接跳过，省一次 embed。

## 五、数据模型

### 5.1 `qc_rule` 扩展

```sql
ALTER TABLE `qc_rule`
  ADD COLUMN `match_type` varchar(16) NOT NULL DEFAULT 'keyword'
      COMMENT 'keyword | semantic | hybrid（keyword+semantic）',
  ADD COLUMN `similarity_threshold` double NOT NULL DEFAULT 0
      COMMENT '语义命中阈值，0=用模型建议值',
  ADD COLUMN `semantic_model_id` varchar(128) NOT NULL DEFAULT ''
      COMMENT '语义判定用的 embedding 模型；空=用租户默认';
```

`match_type` 与现有 `match_mode` 是两个维度，不合并：

- `match_type` = 判定方式（关键词 / 语义）
- `match_mode` = 关键词判定方式（包含 / 全词 / 正则）

语义规则不读 `match_mode`，保留字段避免动旧数据。

### 5.2 新表 `qc_rule_example`（语义样本句）

```sql
CREATE TABLE `qc_rule_example` (
  `id`          varchar(32)  NOT NULL,
  `tenant_id`   varchar(64)  NOT NULL,
  `rule_id`     varchar(32)  NOT NULL,
  `text`        varchar(500) NOT NULL COMMENT '样本句原文',
  `embd_id`     varchar(128) NOT NULL DEFAULT '' COMMENT '向量化用的模型，换模型即失效',
  `dim`         int          NOT NULL DEFAULT 0,
  `embedding`   mediumblob   DEFAULT NULL COMMENT 'float32 小端序，已 L2 归一化',
  `create_time` bigint       NOT NULL,
  `update_time` bigint       NOT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_qc_example_rule` (`rule_id`),
  KEY `idx_qc_example_tenant` (`tenant_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：

- **向量存在 MySQL 而不是 Infinity**。样本句数量级是「每条规则 3–20 句 × 租户几十条规则」，最多几千行、几十 MB；为这点数据引入一次向量库查询，延迟更高、还需要向量库可用。载荷在进程内缓存，判定时纯内存比较。
- **`embd_id` 参与缓存有效性**。换 embedding 模型后旧向量维度/语义空间都变了，必须重算：`WHERE embd_id != <当前模型>` 即待重算集合。
- `dim` 单独存，读回来时校验 `len(embedding)/4 == dim`，防止截断的 blob 静默算错分数。
- 为什么单独建表而不是塞进 `qc_rule.keywords` JSON：样本句要独立增删改、每条要带自己的向量与模型版本，JSON 里塞 `{text, vector}` 会让规则表行宽爆炸且无法按样本句索引。

### 5.3 `qc_hit` 扩展（可解释性）

```sql
ALTER TABLE `qc_hit`
  ADD COLUMN `match_type` varchar(16) NOT NULL DEFAULT 'keyword',
  ADD COLUMN `score`      double      NOT NULL DEFAULT 0
      COMMENT '语义置信度；关键词命中为 0',
  ADD COLUMN `matched_example` varchar(200) NOT NULL DEFAULT ''
      COMMENT '最相似的样本句，用于解释为什么算命中';
```

没有这三列，事后复盘只能看到「命中了」，回答不了「凭什么」。

### 5.4 迁移

- `qc_rule` 已在 `internal/dao/database.go` 的 `dataModels` 列表中，新增字段由 `AutoMigrate` 自动补列。
- 新表 `qc_rule_example` **必须**加进 `dataModels`，否则 `--migrate` 不建表（本项目踩过：运行模式不含某实体时新列不会建）。
- 存量规则 `match_type` 默认 `keyword`，行为完全不变，无需数据回填。

### 6.2 核心结构（骨架）

```go
// internal/service/qc_semantic.go

// SemanticEngine 只负责「一句话对一条规则有多像」，不感知链路与阻断。
type SemanticEngine struct {

	embdID   string

	Text string
	Vec  []float32 // 已 L2 归一化
}

// Score 返回该句对这条规则的最大相似度及其对应的样本句。
func (e *SemanticEngine) Score(ctx context.Context, rule *entity.QcRule, sentence string) (float64, string, error)

// ScoreBatch 一次请求给多句向量，句子多时用它摊薄往返开销。
func (e *SemanticEngine) ScoreBatch(ctx context.Context, rule *entity.QcRule, sentences []string) ([]SentenceScore, error)
```

```go
// internal/service/qc_matcher.go（现有结构上的最小增量）

type StreamMatcher struct {
	// ... 现有字段不动 ...

	// 语义分支状态（与关键词共享同一 goroutine，无需加锁）
	semantic      *SemanticEngine
	semanticRules []*semanticRule
	checkedRunes  int      // 已做过语义判定的字符位置
	pending       []rune   // 未到句末的尾巴
}
```

`Inspect` 的增量只有一段：

```go
// 关键词分支照旧在上面执行；本函数末尾追加语义分支。
func (m *StreamMatcher) inspectSemantic() []QcHitResult {
	if m.semantic == nil || m.semantic.Disabled() || len(m.semanticRules) == 0 {
		return nil
	}
	full := m.FullText()
	// 只取「上次检查点之后、且已出现句末标点」的完整句子。
	sentences := completedSentences(full, m.checkedRunes)
	if len(sentences) == 0 {
		return nil
	}
	m.checkedRunes = sentences[len(sentences)-1].End
	return m.matchSemantic(sentences)
}
```

### 6.3 `QcSession` 挂载

```go
// NewQcSession 内，只有存在语义规则时才构造引擎。
// 模型不可用 → 引擎为 nil → 语义规则整体降级（§9），关键词质检不受影响。
if hasSemanticRules(rules) {
	if engine, err := NewSemanticEngine(ctx, tenantID, rules); err == nil {
		s.semantic = engine
	} else {
		common.Warn("qc semantic disabled: embedding model unavailable", zap.Error(err))
	}
}
```

### 6.4 两条链路的改动量

**零改动。** `wrapQcChannel` 与 `wrapAgentQcChannel` 调的是 `qc.InspectAnswer(delta)`，语义分支在 `StreamMatcher` 内部完成，`QcHitResult` 结构不变（只是多填两个字段）。

这是本方案最重要的取舍：**把复杂度关在匹配层，不让它渗到链路层**。链路层的同步语义、帧替换、`qc_event` 回传、canvas 侧不阻断——全部照旧生效。

## 七、接口设计

### 7.1 规则 CRUD（在现有接口上扩字段）

```jsonc
POST /api/v1/qc/rules
{
  "app_type": "chat",
  "app_id": "d1f2...",
  "name": "暗示收益确定性",
  "match_type": "semantic",          // 新增
  "keywords": [],                     // 语义规则可为空
  "examples": [                       // 新增：同一违规的不同说法
    "稳赚不赔",
    "保本保收益，不会亏",
    "闭着眼睛买都能赚"
  ],
  "similarity_threshold": 0.62,       // 新增，0=模型建议值
  "scope": "ai_answer",
  "severity": "block",
  "action": "block_and_alert",
  "prompt_message": "该回答涉及收益承诺，已被质检拦截",
  "enabled": true
}
```

保存时同步做两件事：①校验每条样本句能 embed 成功（失败直接返回错误，不留「规则建了但向量是空」的半成品）；②写入 `qc_rule_example` 并缓存向量。

### 7.2 语义测试接口（阈值校准的关键）

```jsonc
POST /api/v1/qc/rules/test-semantic
{
  "text": "这个产品稳赚不赔，本金绝对安全。",
  "examples": ["稳赚不赔", "保本保收益，不会亏", "闭着眼睛买都能赚"],
  "similarity_threshold": 0.62
}

// 200
{
  "code": 0,
  "data": {
    "threshold": 0.62,
    "sentences": [
      { "text": "这个产品稳赚不赔，本金绝对安全。", "score": 0.83,
        "best_example": "稳赚不赔", "hit": true },
      { "text": "本金绝对安全。", "score": 0.71,
        "best_example": "保本保收益，不会亏", "hit": true }
    ],
    "hit_count": 2
  }
}
```

前端把它渲染成「逐句分数条 + 阈值滑块」，运营拖动滑块就能看到命中边界在哪一句话上。**没有这个面板，语义规则上线就是黑盒**。

### 7.3 命中记录

`GET /api/v1/qc/hits` 的返回项增加 `match_type` / `score` / `matched_example`，前端命中列表显示「语义 0.83 · 最像『稳赚不赔』」。

## 八、前端实现

### 8.1 规则抽屉（`web/src/pages/qc/`）

- 「判定方式」单选：关键词 / 语义 / 两者
- 选语义时，把原来的「关键词」输入区换成「示例说法」多行编辑（一条一行），并出现阈值滑块（默认值按模型给，显示「建议 0.62」）

## 九、性能、容量与降级

### 9.1 延迟预算（一次回答）

| 环节 | 量级（估算，待实测） |
|---|---|
| 单句 embed（TEI CPU，bge-m3） | 15–40 ms |
| 一句对 5 条语义规则比较 | < 0.1 ms（纯内存） |
| 一条 400 字回答 ≈ 12 句，按 2–3 句一批 | 5–8 次 embed，合计 60–200 ms |
| 对整条回答的**额外墙钟时间** | ≤ 300 ms（超时上限），且摊在流式过程中 |

关键：这些时间**分散在生成过程中**，不叠加到首 token 延迟上。

### 9.2 容量

- 样本向量常驻内存：1000 条规则 × 10 句 × 1024 维 × 4B ≈ 40 MB。可接受。
- 每租户并发 embed 请求加信号量（默认 4），防止高峰期打爆 TEI。

### 9.3 降级策略（必须实现，否则质检会变成随机失效）

| 故障 | 行为 |
|---|---|
| 无 embedding 模型配置 | 语义规则不参与判定；规则列表标「未生效：未配置向量模型」；**关键词规则照常工作** |
| embed 请求超时（>300ms） | 该句跳过语义判定，本次回答标记 `degraded`，不阻断 |
| embed 连续失败 10 次 | 引擎熔断 60 秒，期间全跳过；恢复后自动半开重试 |
| 模型换了（`embd_id` 变更） | 样本向量标记待重算，重算完成前该规则不参与语义判定 |

降级的共同原则：**宁可漏检，不可卡死主流程**。质检是旁路，不能因为它让用户等不到回答。

### 9.4 安全

TEI 是本地容器，答案不出内网。如果后续接外部 embedding API（如云端 bge），等于把用户答案原文发出去，这必须在系统设置的开关上写明用途，并由租户显式勾选。**默认只允许本地模型做语义质检**。

## 十、分阶段落地

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** | 数据模型 + 样本句 CRUD + 语义测试接口 | 建一条语义规则，测试接口能返回逐句分数；改阈值命中条数随之变化 |
| **P1** | `SemanticEngine` + `StreamMatcher` 句边界触发（chat 链路） | 讨论域问答里说「稳赚不赔」被 `block` 规则拦截，`qc_hit` 有 score 与 matched_example |
| **P2** | canvas 链路（`wrapAgentQcChannel` 零改动，仅验证）+ 前端规则抽屉与测试面板 | 对话流里同样能拦住；运营可自助调阈值 |
| **P3**（可选） | LLM 复核：语义分数落在 `[threshold-0.1, threshold+0.1]` 灰区时，才调 chat 模型复核 | 灰区误判率下降，且调用量与成本可度量 |

P1 完成即可上线，P3 是准确率优化，不阻塞交付。

### 10.1 部署前置（P1 上线必须做）

1. **准备模型数据并自建镜像。** 仓库 `Dockerfile_tei` 是 `COPY tei_data /data`，所以镜像里有什么模型取决于本地先下载了什么：

   ```bash
   uv tool install huggingface_hub
   hf download --local-dir tei_data/Qwen/Qwen3-Embedding-0.6B Qwen/Qwen3-Embedding-0.6B
   docker build -f Dockerfile_tei -t ragflow-tei:qwen3-0.6b .
   ```

2. **⚠️ compose 的 `tei-cpu` 没有挂载模型卷。** `docker/docker-compose-base.yml` 里 `tei-cpu` 服务只有 `image / hostname / ports / env_file / networks / command`，没有 `volumes`——而它的启动参数是 `--model-id /data/${TEI_MODEL}`。用官方镜像直接起，`/data` 是空的，服务会在加载模型时失败。所以 `.env` 的 `TEI_IMAGE_CPU` 必须指向**第 1 步自建的镜像**（而不是 `infiniflow/text-embeddings-inference:cpu-1.8`），或自行给该服务补一条 `volumes: tei_data:/data` 并先把模型放进这个卷。

3. **起服务**（`tei-cpu` 在 profile 里，不显式启用不会启动）：

   ```bash
   cd docker
   # TEI_IMAGE_CPU=ragflow-tei:qwen3-0.6b
   # TEI_MODEL=Qwen/Qwen3-Embedding-0.6B
   docker compose --profile tei-cpu up -d tei-cpu
   curl -s -X POST http://127.0.0.1:6380/v1/embeddings \
     -H 'Content-Type: application/json' \
     -d '{"input":"测试","model":"Qwen/Qwen3-Embedding-0.6B"}' | head -c 200
   ```

   端口取 `.env` 的 `TEI_PORT`（默认 6380）。

4. **注册模型**：模型管理里新增 `OpenAI-API-Compatible` 工厂，base_url 指向 `http://tei:80/v1`（容器内网）或 `http://127.0.0.1:6380/v1`（宿主机调试），模型名与 `TEI_MODEL` 一致，类型选 embedding，设为租户默认。

5. **顺序不能反**：先自建镜像 → 起 TEI → 注册模型 → 最后开 `qc.semantic.enabled`。顺序反了会有一段时间语义规则全部降级（关键词质检不受影响）。

## 十一、常见坑（按踩到的概率排序）

1. **阈值照搬别人的 0.8**。不同 embedding 模型的余弦分布尺度差异很大，bge-m3 的 0.62 在 bge-large 上可能是 0.78。阈值必须用测试面板在本租户的真实语料上校准。
2. **整段答案做 embedding**。长文本向量会被主题稀释，一段 400 字里只有一句违规，整段相似度可能低到 0.4。必须分句。
3. **样本句写成规则描述**。「不得暗示收益确定性」是给人看的规则说明，不是语义样本；embedding 比的是「说法长得像不像」，样本必须是**真实会出现的违规说法**。
4. **样本句向量不缓存**。每次质检都重新 embed 十几条样本句，延迟和成本都会翻倍，而样本句几乎不变。
5. **换模型不重算向量**。维度不同直接算错，维度相同算出的分数也毫无意义（语义空间不同）。`embd_id` 必须参与缓存键。
6. **在 `Final` 帧之后才判定**。前端已经消费了 `final`，拦截等于无效。判定必须发生在 `Final` 之前。
7. **把语义当确定性命中做合规拦截**。语义是概率判定，法务要求的「必须拦」只能配关键词；语义只做兜底，且 `severity=block` 的语义规则要配人工复核流程。
