# 同义词（词表）导致检索分数反降 —— 排查与修复报告

- 日期：2026-10-29
- 环境：内网 `172.30.20.51`，引擎 Infinity（`DOC_ENGINE=infinity`），知识库「华夏基金FAQ库」`6995fa4b2ad24d5f9270fcfe18d12d1d`（qa，9 chunk / 3 doc）
- 触发人反馈：「我加了相似词之后，为什么分数反而变低了…我测过好几次，感觉没有生效」
- 结论：**确认是两个 bug，都已修复并提交**（`54ed13179`、`d1b626582`、`378b60ed5`）。另有一个**基础标定问题**（影响所有口语化问句，比同义词问题更大）未改，需要发版实测，见第 7.2 节。

---

## 1. 一句话结论

`minimum_should_match`（词命中率门槛）的分母被**同义词扩写**撑大了。

系统把一个用户词展开成「1 个原词 + N 个别名词」写进查询串，而门槛仍是「命中查询串 30% 的词」。只含原词的 chunk 因此被判不达标，**整条关键词召回归零**，融合分退化成 `vector_similarity_weight × 向量分`（默认 0.3 时约 0.21）。

扩写本身对分数是**完全中性**的（实测 ±0.002）。掉分 100% 来自这个门槛。

第二件事是「感觉没生效」：词条按你输入的原文存库，而查询侧拿**分词后的段**去查字典（问「基金怎么买」查的是 `基金买`），所以「基金是怎么买」这条词条在线上永远命中不了。变更集对比工具自己会分词，于是它演出了效果、线上却没有——两个口径不一致。这一条也修了（第 7.1 节）。

## 3. 实验设计（四组对照）

线上没法直接「关掉门槛同时保持权重 0.3」，所以用融合公式做四点对照：

```
fused(vsm) = (1 - vsm) × term + vsm × vector        // Infinity weighted_sum
minMatch(vsm) = 0.0  (vsm >= 0.8)                   // 代码里的既有开关
minMatch(vsm) = 0.3  (vsm <  0.8)
```

| 组 | 配置 | vsm | 门槛 | 作用 |
|---|---|---|---|---|
| A | 原配置（不含新词） | 0.30 | 0.3 | 你今天看到的基线分 |
| B | 新配置（含 pending 词条） | 0.30 | 0.3 | 你今天看到的「掉分」 |
| D | 原配置 | 0.80 | **0** | 门槛关闭时的基线 |
| C | 新配置 | 0.80 | **0** | 门槛关闭时的新配置 |

**判据**：`C − D ≈ 0` 说明扩写本身不掉分，那么掉分只可能来自门槛；此时把门槛修好（rebase 到 ~2%，等价于关闭），B 就会回到 A。

## 4. 门槛突变实验（定位到 `vsm>=0.8` 这个分界）

权重只动 1%（0.79 → 0.80），门槛从 0.3 跳到 0：

| 问句 | 是否扩写 | vsm=0.79 | vsm=0.80 | Δ |
|---|---|---|---|---|
| 买基金 | 是 | 0.5512 | 0.7581 | **+0.2069** |
| 申购费率是多少 | 是 | 0.5619 | 0.7689 | **+0.2071** |
| 基金怎么买 | 否 | 0.7701 | 0.7672 | −0.0028 |
| 开户需要准备什么 | 否 | 0.7714 | 0.7685 | −0.0029 |

扩写组跳变 0.207，不扩写组只抖动 0.003 —— 跳变点正是 `minMatch()` 返回 0 的分界，证据闭合。

**通路拆分**（`vsm` 分别取 0 / 0.3 / 1.0）：

| 问句 | vsm=0（纯关键词） | vsm=0.3 | vsm=1（纯向量） |
|---|---|---|---|
| 基金怎么买（不扩写） | **0.9948** | 0.9095 | 0.7103 |
| 买基金（扩写） | **0.0000** | 0.2093 | 0.6977 |
| 申购费率是多少（扩写） | **0.0000** | 0.2134 | 0.7112 |

关键词通道 **0.9948 → 0.0000**，向量通道几乎不动。0.2093 ≈ 0.3 × 0.6977，正好是「只剩向量腿」。

## 5. 根因与修复

### 5.1 代码位置

`internal/service/nlp/query_builder.go`，中文分支构造查询串时：

```go
// 一个用户词 -> (原词组)^5 OR ("别名1" OR "别名2" ...)^5
tmsStr = fmt.Sprintf("(%s)^5 OR (%s)^5", tmsStr, strings.Join(synParts, " OR "))
...
ExtraOptions: map[string]interface{}{"minimum_should_match": minMatch}  // 仍是 0.3
```

引擎把 `minimum_should_match: "30%"` 理解成「查询串里 30% 的 clause 必须命中」。扩写让 clause 数从 1 变成 7~13，于是门槛从「命中 1 个词」变成「命中 3~4 个词」——而 chunk 里只有你原本打的那些字。

### 5.2 修法

按 `原词 clause 数 / (原词 + 别名 clause 数)` 缩放这个比例，让门槛继续衡量**用户输入的那几个词**：

```go
func rebaseMinMatchForSynonyms(minMatch float64, literalClauses, synonymClauses int) float64 {
	if minMatch <= 0 || synonymClauses <= 0 {
		return minMatch          // 没扩写：原值透传，逐字节不变
	}
	return minMatch * float64(literalClauses) / float64(literalClauses+synonymClauses)
}
```

特性：
- **只在真的发生字典扩写时生效**。不含同义词的查询、以及无关问句，行为与修复前完全一致（回归表第 6.2 节 8/9 条零变化可证）。
- **别名词独占命中的 chunk 依旧能过门槛**，所以扩写带来的召回不受损。
- 门槛只会变小、不会变大，所以「加同义词导致掉分」在数学上不可能再发生（单测 `TestRebaseMinMatchForSynonymsNeverRaises` 穷举 13×41 组合锁死）。

实测缩放效果（单测日志，真实分词器）：

```
baseline gate=0.3  expanded gate=0.1125
query = (((费率)^0.657 (我的)^0.343 ("我的 费率"~2)^1.5)^5
         OR ("申购 费" OR "申购 费率" OR "手续费" OR "认购 费" OR "买入 费率")^5)
```

3 个原词 clause + 5 个别名 clause → `0.3 × 3/8 = 0.1125`。

## 7. 另外两条同源问题

### 7.1 「感觉没有生效」的根因：线上按**逐字 key** 匹配，对比工具按**分词后**匹配（已修，走方案甲）

- 生产侧 `GetDictionaryByDataset` 的 key 是词条的**原样字符串**（只折小写）。你加的「基金是怎么买」存成 key `基金是怎么买`，而中文问句进来后被分词成 `基金买` —— 两者永不相等，**这条词条在线上永远不会生效**。
- 对比工具侧 `buildInjections` 判断的是「token 是否等于某个词条分词后的结果」，口径更宽。所以你加的「基金是怎么买」在**对比界面**里被当成 key `基金买` 注入了（`synonym_override_keys: ['基金买']`），显示出了一次扩写；发布之后线上不会发生这件事。

后果有两个，方向相反，都很迷惑人：
1. 对比界面告诉你「有效果（而且掉分）」，实际发布后**毫无变化**；
2. 你反复确认「没生效」，确实没生效——**因为对比工具只在对比里补偿了这个差距**。

**已修（方案甲）**：加载词表时，用与查询侧完全相同的归一化再算一个 key，与逐字 key 并存，成员取并集去重。服务器真实分词器下的实测折算：

| 词条（客户怎么填） | 去停用词后 | `Split` 结果 | 是否新增 key |
|---|---|---|---|
| 基金是怎么买 | 基金买 | `[基金买]` | ✅ 新增，正好是问句的 token |
| 买基金 | 买基金 | `[买基金]` | ❌ 与逐字 key 相同 |
| 想买基金 | 想买基金 | `[想买基金]` | ❌ |
| 申购费率 | 申购费率 | `[申购费率]` | ❌ |
| 基金是怎么买的？ | 基金买的 | `[基金买的]` | ❌ 与问句 token `基金买` 不同，仍不生效（符合预期：填词条要与问法一致，多一个「的」就不算同一句） |

两道闸：只有「折完跟原文不一样」才新增 key（所以老词条零影响）；折出来只有 1 个字的丢弃（否则「怎么买」→「买」会把整个组挂到通用字上）。

### 7.2 门槛的**基础标定**偏严：影响的不只是同义词，是所有口语化问句（未改，需发版实测）

这一条比同义词问题大得多。抽测 8 个口语化问句（都不是 chunk 标题），**关键词腿全部是死的**：

| 问句 | 今天 | 反解 term | 反解 vector | 闸门放开后应得 |
|---|---|---|---|---|
| 我想买基金 | 0.2096 | 0.9925 | 0.6986 | 0.9044 |
| 买基金要多少钱 | 0.2103 | 0.9908 | 0.7011 | 0.9039 |
| 基金亏了怎么办 | 0.2100 | 0.9630 | 0.7000 | 0.8841 |
| 赎回要多久到账 | 0.2154 | 0.9986 | 0.7180 | 0.9144 |
| 开户流程 | 0.2092 | 0.9952 | 0.6973 | 0.9058 |
| 怎么查净值 | 0.2098 | 0.9979 | 0.6993 | 0.9083 |

也就是说：**今天只有「问题和某条 chunk 标题逐字相同」的问句能拿到 0.9 档，其它一律被压到 0.2 档。**

但**不能直接把闸门拆掉**。同一批数据里，放开闸门后域内但**未覆盖**的问句也会跳到 0.88~0.89：

| 问句 | 今天 | 闸门放开后 | 问题 |
|---|---|---|---|
| ETF和场外基金的区别 | 0.1964 | **0.8908** | 库里没有这条内容，分数却和已覆盖问句一样高 |
| 基金的夏普比率怎么算 | 0.1986 | 0.8784 | 同上 |
| 今天中午吃什么 | 0.8752 | 0.8752 | 本来就高（与闸门无关，预存在） |

完全无关的问句（明天会下雨吗 0.3554 / 如何种植多肉植物 0.3724 / 帮我写一首诗 0.3331）不受影响——它们没有任何 term 命中。

结论：闸门是当下唯一在区分「覆盖了」和「没覆盖」的东西，但它同时把口语化问句一起误杀。**正确做法是重新标定阈值（0.3 → 更小的值），不是拆掉**，而标定只能靠「发版 → 实测 → 再调」的循环，我没有线上开关可以扫。建议单独发一版做这件事。

> **注意这条对 7.1/第 5 节修复的连带影响**：修完之后，「命中词表组」的问句闸门被 rebase 到很低 → 拿到 0.9 档；「没命中词表组」的问句闸门仍是 0.3 → 仍是 0.2 档。于是会出现「加过同义词的问句 0.90、没加过的 0.21」这种看起来很别扭的对比。方向是对的（加词不再惩罚），但根子上的不对称要靠 7.2 的基础标定才能消掉。

## 8. 回归风险

| 项 | 结论 |
|---|---|
| 不含同义词的知识库 | 门槛路径完全不受影响（`synonymClauses == 0` 原值透传） |
| 含同义词的库 | 门槛变小 → 召回变多、分数变高。**上线后需要重新校准 `similarity_threshold`**：之前按「被压坏的分数」定的阈值（如 0.2）会一次性放进更多结果 |
| 词条别名（7.1） | 只给「折算后与原文不同」的词条加 key，现有词条基本不动；已发布词表里如果存在这类短语词条，它们会**第一次真正生效**，对应组的召回会变多——这是修复目标，但表现上是「同一个问句的结果变多了」 |
| 分数不对称（7.2 未修） | 命中词表组的问句会拿到 0.9 档，没命中的仍是 0.2 档。方向正确但看起来别扭，根治要等 7.2 的基础标定 |
| rerank 开关 | 未触碰。注意重排开关会整体改变分数量级（关 0.9 档 / 开 0.6 档），换开关仍需重定阈值 |
| 变更集对比 | 对比结果会从「0.213」变回 0.909 附近；且 7.1 修完后，对比工具的分词口径与线上一致，对比结果真正代表发布后的效果 |
