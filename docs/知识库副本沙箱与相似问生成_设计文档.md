## 一、背景与目标

### 1.1 现状问题

客户（客服中心）在维护知识库时遇到三个绕不开的痛点：

1. **改相似问不敢改**。相似问对检索结果影响极大（全文检索权重 `^20`、rerank 权重 `×6`），
   但改完无法评估效果，只能凭感觉，改坏了要等用户投诉才发现。
2. **生产数据没有安全网**。任何调整都直接落在生产库，出错即事故，没有回滚手段。
3. **知识点重复难发现**。知识库积累久了，相近甚至重复的知识点会互相「抢召回」，
   但没有任何工具能识别它们。

### 1.2 目标

| 功能 | 目标 |
|---|---|
| 功能一 | 提供「副本 → 调优 → 测试 → 审核 → 发布」闭环，让相似问/近义词调整可验证、可回退 |
| 功能二 | 降低相似问维护成本，并主动识别互相干扰的知识点 |

### 1.3 非目标（本期不做）

- **检索准确率**：系统无检索日志与评测打分，数据不存在，不做假指标
- **数据集内容副本**：仅复制配置类字段（相似问、近义词），不复制 chunk 正文与向量之外的解析产物
- **多租户环境隔离**：副本仅在租户内生效，不做跨租户沙箱

## 二、用户与场景

### 2.1 角色

| 角色 | 关注点 | 权限 |
|---|---|---|
| 知识库运营 | 相似问是否覆盖了用户的真实问法、调优是否有效 | 可创建副本、编辑、提交审核 |
| 审核人（主管） | 这次改动会影响生产什么、风险多大 | 可审核通过/驳回 |
| 系统管理员 | 谁改了什么、可追溯 | 只读全部副本与审核记录 |

### 2.2 核心场景

**场景 A：新增相似问并验证**

> 运营发现「新用户怎么申请退款」问不到对应知识点，怀疑是问法覆盖不足。
> 创建副本 → 用 LLM 批量生成相似问 → 人工挑选 → 在副本上实测 3 个问法 →
> 确认召回改善 → 提交审核 → 审核通过合并回生产。

**场景 B：干扰排查**

> 运营测试时发现某问法返回的第一条和第二条内容高度相似，怀疑知识库有重复知识点。
> 在「相近知识点检测」中扫描 → 看到 chunk A 与 chunk B 相似度 0.94 →
> 决定合并 → 在副本中调整 → 复测确认。

## 三、功能设计

### F1 副本管理

**副本生命周期**

```
生产库 KB
  │ 创建副本
  ▼
草稿态 pending ──提交审核──► 审核中（锁定编辑）
  │                          │
  │                     审核人决策
  │                      ├──通过──► 已发布 → 合并回生产
  │                      └──驳回──► 已驳回（保留，可继续改）
  │继续编辑
  ▼
丢弃 ──► 已丢弃（可删除）
```

**规则**

- 副本创建时快照生产库当前配置（`base_config`），作为对比基准
- 草稿态可反复编辑，不影响生产
- 审核中锁定编辑，避免「审核期间变更」导致 diff 失效
- 驳回后可继续编辑并重新提交
- 已丢弃副本保留 7 天后自动清理（可配置）

**关键交互**

| 操作 | 反馈 |
|---|---|
| 创建副本 | 弹窗：副本名称、备注、复制范围（相似问 / 近义词 / 检索参数）；提交后进入创建中状态（复用向量，通常秒级） |
| 编辑副本 | 顶部常驻提示条：「当前为草稿副本，生产库不受影响」+ [提交审核] |
| 提交审核 | 校验是否真有改动；无改动则禁用按钮并说明原因 |
| 审核通过 | 二次确认弹窗，列出将影响的生产 chunk 数量；确认后执行合并并跳转生产库 |

---

### F2 相似问编辑与 diff 审核

**编辑方式**

1. **单条编辑**：在 chunk 详情里编辑相似问（沿用现有 `EditTag` 控件）
2. **批量编辑**：按文档/状态筛选后批量追加或替换
3. **智能生成**（见 F4）

**diff 审核页**

审核人看到的核心是「**这次改动到底改变了什么**」：

- 顶部汇总：新增 N 条、修改 N 条、删除 N 条
- 列表按 chunk 展示三列：`chunk 内容（截断）` | `改动前相似问` | `改动后相似问`
- 新增行标绿、删除行标红、修改行标黄
- 支持按变更类型筛选、搜索
- 右侧固定「影响面预估」：预计影响的生产 chunk 数、与生产库的相似问差异条目数

**冲突处理**：若审核期间生产库对应 chunk 被他人修改，发布时逐条校验，
不一致的条目**拒绝合并并单独列出**，避免覆盖他人改动。

---

### F3 三层测试

用户在副本上可以直接验证效果，分三层递进：

| 层 | 页面 | 回答什么问题 |
|---|---|---|
| L1 检索层 | 检索测试（`/retrieval`） | 召回了哪些 chunk？三档打分如何？命中了哪条相似问？ |
| L2 对比层 | 双栏 A/B | 相比生产库，排序变化了多少？哪些是新增召回？ |
| L3 问答层 | 问答链路 | 最终回答质量如何？引用是否正确？ |

**L2 双栏对比**：现有检索测试页已预留双栏布局
（`web/src/pages/dataset/testing/index.tsx:62-91`，被 `count=1` 的 TODO 关着），
启用后左右分别检索生产库与副本，逐条对齐展示：

- 位置变化（`↑↑↑` 表示从第 8 名升到第 2 名）
- 分数变化（`0.61 → 0.84`）
- 新增/消失的召回条目高亮

**前置依赖**：检索结果必须返回 `question_kwd`，否则无法归因
「命中了哪条相似问」。这是 P0 必修项。

### F4 智能生成相似问

**现状**：解析阶段已能自动生成（`extractor.go:840-891` `runAutoQuestions`），
但只能对**新解析的文档**生效，已有 chunk 无法补生成。

**本期补充**：对已有 chunk 批量生成。

```
入口：知识库设置 → 相似问管理 → 「批量生成」
  1. 筛选范围：按文档 / 按解析状态 / 全库
  2. 展示 LLM 生成结果（每条 chunk 列出候选相似问，可勾选）
  3. 采纳的写入 —— 默认写入副本，与 F1 闭环
```

**工程约束**

- LLM 调用需限流与断点续跑（chunk 量可能上千）
- 批量操作异步执行，页面展示进度
- 生成结果必须人工确认，不自动写入生产

---

### F5 相近知识点检测

分两个时机，覆盖你要求的「两者都要」。

#### (a) 管理时批量扫描

入库后或手动触发，对全库做向量两两比对：

```
入口：知识库设置 → 相近知识点检测
  1. 点击「开始扫描」，展示进度
  2. 结果列表：chunk A | chunk B | 相似度 | 所属文档
  3. 操作：合并 / 改写其一 / 标记「允许共存」
```

**阈值**：默认 0.90，可在页面上调整后重扫。
需注意分块策略影响 —— 短 chunk 之间天然更易高相似。

**性能约束**：两两比对是 O(n²)，需分片 + 近似算法（LSH/Annoy），
不能直接暴力算。单次扫描建议异步任务 + 结果落库。

#### (b) 检索时实时提示

在检索测试页与问答链路中，若 top-k 结果内部高度相似，顶部提示：

> ⚠️ 此问题命中了 3 个高度相似的知识点（相似度 0.91~0.95），
> 可能是重复内容，建议合并后再上线。[查看详情]

**实现**：前端基于已返回的 `similarity` 做 top-k 内部两两比对，**无需新增后端接口**。
注意检索结果会 `delete vector`（`search.go:361`），所以只能用最终 `similarity`。

## 四、界面设计

### 4.1 信息架构

```
知识库详情
├── 概览
├── 文档
├── 分块
├── 检索测试
├── 相似问管理          ← F2 编辑入口
│   └── 批量生成         ← F4
├── 相近知识点检测       ← F5(a)
└── 副本                ← F1 列表
    ├── /副本/新建
    ├── /副本/:id/工作台   ← F2 编辑 + F3 测试
    ├── /副本/:id/审核     ← F2 diff
    └── /副本/:id/对比     ← F3(L2)
```

### 4.2 页面清单

|---|---|---|---|
| 1 | 副本列表 | `/datasets/:id/drafts` | 副本卡片列表、状态标签、创建入口 |
| 2 | 创建副本 | 弹窗 | 名称、备注、复制范围勾选 |
| 3 | 副本工作台 | `/datasets/:id/drafts/:did` | 草稿提示条、相似问编辑、右侧测试面板 |
| 4 | 审核页 | `/datasets/:id/drafts/:did/review` | diff 三列表、影响面、审核操作 |
| 5 | 检索对比 | `/datasets/:id/drafts/:did/compare` | 左右双栏、位置/分数变化 |

### 4.3 设计规范

沿用现有系统风格（参照 `style(web): 统一为中文企业后台视觉风格`）：

| 项 | 规范 |
|---|---|
| 主色 | `#065BC1`（品牌蓝） |
| 侧边栏 | 深底 `#1A2332` + 白色系文字，选中态白色色条 |
| 字体 | 中文优先系统字体栈（PingFang SC / 微软雅黑） |
| 表格 | 13px 正文，表头 40px 高 |
| 圆角 | 5px |
| 状态色 | 草稿=橙 `#F2994A`、审核中=蓝、已发布=绿、已驳回=红 |

**关键组件**

- `DraftBanner`：草稿态常驻提示条，必须出现在副本内所有页面顶部
- `DiffTable`：三列 diff 表格，虚拟滚动（chunk 可能上千条）
- `SimilarityBadge`：相似度徽标，≥0.9 标红、0.8~0.9 标橙、其余中性
- `ImpactSummary`：影响面预估卡片，审核页固定底部

## 五、数据模型

### 5.1 Knowledgebase 新增字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `source_kb_id` | varchar(64) | 来源生产库 ID，空表示正常库 |
| `is_draft` | bool | 是否草稿副本 |
| `draft_status` | enum | `pending` / `reviewing` / `published` / `rejected` / `discarded` |
| `base_config` | JSON | 创建时生产库检索配置快照 |
| `created_by` | varchar | 创建人 |
| `reviewed_by` | varchar | 审核人 |
| `reviewed_at` | datetime | 审核时间 |
| `review_comment` | text | 审核意见 |

### 5.2 相似问需从 chunk 提升为独立实体

**现状**：相似问寄生在 chunk 的 `question_kwd` 字段，只能逐条覆盖，
无法表达「本次副本改了什么」（`req.Questions` 是差异化整体覆盖语义）。

**建议**：新增 `chunk_question` 表，支持副本级 diff：

| 字段 | 说明 |
|---|---|
| `chunk_id` | 所属 chunk |
| `kb_id` | 知识库 |
| `content` | 相似问内容 |
| `origin` | `manual` / `llm` / `imported` |
| `is_deleted` | 软删除，便于 diff |
| `created_by` / `created_at` | 审计 |

**理由**：只有这样才能做到①增量 diff ②审核③溯源。
改造后应采用同义词模块的差异化更新范式
（`synonym.go:66-74` 的 `*[]T` 指针：nil=不修改、空数组=清空）。

### 5.3 相近知识点检测结果表

| 字段 | 说明 |
|---|---|
| `kb_id` | 知识库 |
| `chunk_a_id` / `chunk_b_id` | 两个 chunk |
| `similarity` | 向量余弦相似度 |
| `status` | `pending` / `resolved` |
| `resolution` | `merged` / `rewritten` / `allowed` |
| `scanned_at` | 扫描时间 |

## 七、权限与安全

| 规则 | 实现 |
|---|---|
| 越权与不存在不可区分 | 照抄 `handler/synonym.go:188-197`，防跨租户探测 |
| 租户归属强校验 | 照抄 `service/synonym.go:320-338` `resolveTenant` |
| 草稿库不进入生产选择器 | Agent 绑定、知识库选择等处过滤 `is_draft=true` |
| 审核中锁定 | `draft_status=reviewing` 时拒绝编辑请求 |
| 全量审计 | 副本创建/编辑/审核/发布/丢弃全部留痕 |

## 八、分期与验收

| 阶段 | 内容 | 预估 | 验收标准 |
|---|---|---|---|
| **P0** | 检索返回 `question_kwd`；同义词页注册路由 | 1~2 天 | 检索结果能看到命中的是哪条相似问；同义词页面可访问 |
| **P1** | 副本创建/编辑/审核/发布 | 1~2 周 | 副本可创建、可改相似问、可 diff、可发布回生产且生产数据无误 |
| **P2** | 双栏对比 + 问答层验证 | 3~5 天 | 能并排看到生产与副本的排序/分数差异 |
| **P3** | 批量生成相似问 | 3~5 天 | 1000 chunk 批量生成可断点续跑 |
| **P4** | 相近知识点扫描 + 实时提示 | 3~5 天 | 扫描出相似度 >0.9 的 pair；检索时给出干扰提示 |

**建议先做 P0**：成本最低，且「同义词页面可访问」本身就是用户可感知的交付；
同时 `question_kwd` 返回是后续所有归因分析的前提。

## 九、待确认事项

1. **发布冲突裁决策略**：副本创建后生产库被他人修改，是拒绝发布、
   还是允许覆盖？（当前方案：逐条校验，不一致的条目拒绝合并并单独列出）
2. **问答层会话是否隔离**：L3 验证走真实问答链路时，会话历史是否需要与生产隔离
3. **副本保留时长**：丢弃后保留 7 天是否合适
4. **近义词是否纳入副本**：当前设计包含，若仅相似问可简化 P1 范围
