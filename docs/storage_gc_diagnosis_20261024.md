# 存储诊断：我们是什么版本、有没有自动 GC、会不会炸盘

- 日期：2026-10-24
- 环境：ECS `42.121.119.90`（2 vCPU / 7GB 内存 / 40GB 系统盘）
- 触发：link 阶段耗时 55 分钟、`read_bytes` 累计 240GB，以及"社区版没有 GC、反复重建会炸盘"的判断

---

## 一、一句话结论

**我们不是 FAISS 后端，是 Infinity v0.7.4，原生带清理与段合并；实测 91 个存储块里 0 个孤儿。磁盘占用的大头是编译缓存（8.9GB），不是向量碎片（897MB）。**

---

## 二、我们是什么版本

| 项目 | 实测值 | 来源 |
|---|---|---|
| RAGFlow | **1.0.0-rc2**，main 分支，commit `0ef0ddf`（2026-10-24） | `pyproject.toml`、`git log` |
| API 运行时版本 | `0ef0ddf` | `GET /api/v1/system/version` |
| 文档引擎 | **Infinity v0.7.4** | 容器 `infiniflow/infinity:v0.7.4-x64-v3` |
| DOC_ENGINE | **`infinity`** | 运行态 `/proc/<pid>/environ` |
| Infinity 进程 | `/usr/bin/infinity`，RSS 3.6GB，端口 5432/23817/23820 | `ps`、`ss -lntp` |

**没有 FAISS。** 项目里既没有 FAISS 索引文件，也没有 `faiss` 相关依赖在运行路径上。所以"默认 FAISS + 老版本"这个前提对当前环境不成立。

## 三、我们有没有自动回收

有，而且是三层。

### 3.1 引擎层：Infinity 的定时清理与段合并

`/infinity_conf.toml` 实测配置：

```toml
[storage]
optimize_interval  = "10s"    # 优化调度
cleanup_interval   = "60s"    # 每 60 秒清理失效数据
compact_interval   = "120s"   # 每 120 秒做段合并
mem_index_capacity = 65536    # 内存索引容量（行）
```

这三项就是外部建议里说"Infinity 自带段合并、删除回收"的那套机制——我们正在用。

### 3.2 应用层：删除文档时主动删向量

`internal/service/document/document_crud.go:402-418`：

```go
// deleteDocEngineData removes chunks and metadata from the document engine.
_, delErr := s.docEngine.DeleteChunks(deleteCtx,
    map[string]interface{}{"doc_id": docID}, indexName, kbID)
```

Infinity 侧的实现在 `internal/engine/infinity/chunk.go:849`。也就是说删除文档不是只删 MySQL 行，会同步删除引擎里的 chunk 与向量，并在失败时返回错误而不是静默忽略。

### 3.3 日志层：轮转上限

```toml
log_file_max_size   = "100MB"
log_file_rotate_count = 10
```

上限 1GB。实测轮转出 3 个 100MB + 当前 41MB = 340MB，未超限（已清理历史 3 个，回收 310MB）。

### 3.4 回收是否真的在工作：实测验证

拿 persistence 下 91 个块的 UUID 逐个去 catalog 里比对引用：

```
blocks=91  referenced=91  orphan_count=0
```

**孤儿为 0。** 说明清理机制确实在跑，没有出现"删了文档但向量还留着"的情况。如果 GC 失效，这里应该能看到未引用的块。

## 四、那 897MB 到底是什么

不是垃圾，是**块粒度写放大**。

| 指标 | 实测值 |
|---|---:|
| persistence 总占用 | 897 MB |
| 块文件数 | 91 |
| 其中 >30MB 的块 | **21 个，占 882MB（98%）** |
| 剩余 70 个文件合计 | 15 MB |
| 单个大块大小 | 42–53 MB |
| 逻辑大小 vs 实际占用 | 完全相等（**不是稀疏文件，占多少就是多少**） |

而真实数据量：

| 指标 | 实测值 |
|---|---:|
| 知识库 | 12 个 |
| 文档 | 104 个 |
| chunk | 450 个 |
| token | 135,647 |
| 向量本体（450 × 1024 维 × 4B） | **1.84 MB** |

**1.84MB 的向量占了 897MB，约 488 倍。**

原因：`mem_index_capacity = 65536` 表示每个块按 65536 行容量分配，单块约 42MB。450 个 chunk 摊到 21 个大块上，每块实际只用了几十行，但文件按满容量写满。**块里的空间还要装全文索引（`ft_content` / `ft_docnm` / `ft_authors` 等），不全是向量。**

这属于引擎的存储粒度特性，**删块文件等于删数据**（已确认全部被引用）。要回收只能删表重建，而不是"清理碎片"。

## 五、逐条核对"社区版没有 GC"的判断

| 外部判断 | 对当前环境是否成立 | 依据 |
|---|---|---|
| 你大概率在用 0.26 之前的版本 | ❌ 不成立 | 我们是 1.0.0-rc2，main 最新提交 |
| 默认 FAISS，碎片万恶之源 | ❌ 不成立 | `DOC_ENGINE=infinity`，无 FAISS |
| FAISS 没有后台 GC、无段合并 | 对 FAISS 成立，与我们无关 | 我们不用 FAISS |
| Infinity 自带段合并、删除回收 | ✅ 成立，且我们已启用 | `compact_interval=120s` 等三项 |
| 删文档后残留索引垃圾 | ❌ 实测未发生 | 0 孤儿 |
| 反复重建会产生多套并行旧索引 | ⚠️ **部分成立，需监控** | 见下节 |
| 建议切到 Infinity/ES | 已完成 | 已在 Infinity 上 |
| 硬件要 NVMe SSD | ✅ 成立 | 见第七节 iowait |

**这份建议 90% 的篇幅建立在 FAISS 前提上，对我们不适用。**它给出的"路线 A 第一条：换掉 FAISS 切 Infinity"，我们已经做完了。

## 六、真实风险：反复重建会不会炸盘

观测到的现象：块数量会随写入次数累积（21 个大块，时间跨度 10-17 到 10-24），**没有观测到同一张表的多个块被合并回收**。这是需要监控的点，也是唯一值得做 GC 的地方。

但对"会不会炸盘"的判断要基于块复用而非线性外推：

- 单块容量 65536 行，21 个块约 137 万行容量
- 当前 450 个 chunk，容量利用率约 **0.03%**
- 也就是说：**在数据量涨到几十万 chunk 之前，块文件基本是固定成本，不会随文档数线性膨胀**
- 真正让块增长的是**写入次数**（每次解析新建块），不是文档体积

按当前 104 文档 / 897MB 的比例，外推到 100GB 原始文档既不现实也不必要——那时块会被真正填满，放大比会回落到接近 1。

**结论：短期内没有炸盘风险，但"反复重建导致块数单调增长"需要纳入巡检。**

## 七、磁盘真正被什么占着（34GB 已用）

| 路径 | 占用 | 性质 |
|---|---:|---|
| `/root/.cache/go-build` | **8.9 GB** | 编译缓存，占已用空间 26% |
| `/swapfile` | **8.1 GB** | swap 文件，实测用量 **0** |
| `/var/lib/docker` | 7.9 GB | 含 Infinity 1.4G / MySQL 2.4G / MinIO 333M |
| `/root/go/pkg/mod` | 2.1 GB | 模块缓存 |
| `/root/ragflow` | 1.1 GB | 代码 + 二进制 |
| `/root/ragflow_backup` | 746 MB | 历史二进制 |

**已执行清理（20:30）：**

| 项目 | 回收 |
|---|---:|
| Infinity 轮转日志 ×3 | 310 MB |
| `/tmp/go-link-*`、`/tmp/go-build*` 残留 | 493 MB |
| 旧前端打包 ×7 | 126 MB |

清理后：`34G → 33G`，`4.2G → 5.1G` 可用，`89% → 87%`。

**没有动 `go-build` 缓存（8.9GB）**：它是最大单项，但删了下次构建要从 1 分钟变成 25 分钟——那是在用"构建更慢"换"磁盘更空"，与当前诉求相反。留给你决定。

## 八、link 为什么慢（与碎片无关）

```
PID 74996  /usr/local/go/pkg/tool/linux_amd64/link -extld=gcc
ELAPSED 54:51   %CPU 9.9   RSS 918MB
read_bytes : 240,178,270,208   (240GB)
write_bytes:   2,059,640,832   (2GB)
```

- 240GB 是**累计物理读字节**，不是磁盘上的文件大小（整块盘才 40GB）
- 根因是内存不足：`available` 只剩 1GB，Infinity 3.6GB + MySQL 573MB + link 918MB 就吃满
- page cache 被反复回收，mmap 的静态库页被 evict，下次访问重新从磁盘搬 → 同一批几百 MB 的文件被读了上千遍
- `%CPU` 只有 9.9%，说明绝大部分时间在等 I/O，不是在算

**解法按性价比排序：**

1. **内存 7GB → 16GB**（最直接，根治）
2. **构建时临时停 Infinity**（释放 3.6GB，但会中断检索服务）
3. **系统盘 40GB → 100GB**（当前 87% 已经很紧，一次构建要写 2GB 二进制 + 临时文件）
4. 清 `go-build` 缓存只能腾空间，**不能让 link 变快**

## 九、要不要做碎片 GC 功能

**当前数据不支持做**：0 孤儿、897MB 且删了会丢数据、块是固定成本。为 897MB 写一套删除逻辑，风险和收益不匹配。

**值得做的是巡检，不是删除。**建议做一个只读巡检，把下面几项纳入定时任务，超阈值告警：

| 巡检项 | 阈值建议 | 对应风险 |
|---|---|---|
| Infinity 未引用块数 | > 0 | GC 失效 |
| 块数量增长趋势 | 周环比 > 50% | 反复重建失控 |
| `go-build` 缓存 | > 12GB | 磁盘将满 |
| MySQL `pipeline_operation_log` | > 500MB | 日志无 TTL |
| 磁盘使用率 | > 85% | 构建/写入失败 |
| Infinity 日志目录 | > 800MB | 轮转上限 1GB |

## 十、如果确实要回收那 897MB

唯一安全路径是**删表重建**（不是删块文件）：

1. 新建一个知识库，用相同切分配置重新导入
2. 校验检索效果一致
3. 删除旧知识库（会走 `DeleteChunks` 正常删除路径）
4. Infinity 在 `compact_interval` 周期内回收空间

代价：需要重新 embedding（消耗 token 配额），且期间知识库不可用。**为 897MB 做这件事，在 40GB 盘上收益约 2.2%，不建议现在做。**

真正该处理的是 `go-build` 缓存 8.9GB 和 `swapfile` 8.1GB（用量 0）——这两项加起来 17GB，是 897MB 的 19 倍。
