# 华夏基金「华小夏」智能客服 · RAGFlow 配置方案 v1

> 用途：基于客户 13 项功能清单，给出在 RAGFlow 上的落地场景、配置规则与缺口判定，供评审。
> 现状基础：租户 `8d5c79460d6c46efb58353c68d8bf729`，已上线「华小夏-客服」问答应用与 3 个知识库、1 个「夏管家推送」智能体。

---

## 一、配置场景

### 1.1 定位

把「华小夏」做成一个**多渠道共用一个知识底座**的智能客服：WEB / APP / IVR 三个渠道跑同一套知识与检索参数，只在「话术形态」和「输出方式」上分流；运营侧提供日志、报表、质检、追踪、测试的闭环。

一句话：**知识只维护一份，渠道只是出口**。

### 1.2 总体分层

```
渠道层    WEB 在线客服      APP 内嵌        IVR 语音        坐席辅助
             |                 |               |               |
应用层    华小夏-客服(生产)  华小夏-客服(生产)  华小夏-IVR    夏管家转人工(Agent)
             |                 |               |               |
检索层    同义词/别名归一 -> 向量+关键词混合检索 -> qwen3-rerank -> 阈值过滤 -> top_n
             |                 |               |               |
知识层    FAQ标准问库 | 寒暄库 | 业务知识库 | 渠道/网点库 | 转人工话术库 || 沙箱副本
             |                 |               |               |
治理层    参数基线 | 质检规则 | 审计日志 | 权限矩阵 | 变更集发布
```

### 1.3 应用与渠道的对应关系

| 应用 | 类型 | 承载渠道 | 绑定知识库 | 说明 |
|---|---|---|---|---|
| 华小夏-客服 | 问答应用（dialog） | WEB、APP | FAQ + 寒暄 + 业务 + 渠道 | 生产主力，一套配置两渠道复用 |
| 华小夏-IVR | 待建（问答应用） | IVR | FAQ + 寒暄 | 只取短答案，配合语音播报 |
| 夏管家推送 | 智能体（agent） | WEB、APP | 转人工话术 | 关键词/场景命中后转人工并推二维码 |
| 华小夏-沙箱 | 问答应用（副本） | 无（内部测试） | 各库的沙箱副本 | 模拟测试专用，与生产日志隔离 |

## 二、配置规则

### 2.1 知识库分层规则

| 层 | 库名 | 解析器 | 内容形态 | 是否入生产检索 |
|---|---|---|---|---|
| L1 寒暄 | 华夏基金寒暄库 | qa | 一问一答，一个 chunk 一个问题 | 是（全渠道） |
| L2 标准问 | 华夏基金FAQ话术 | qa | 标准问 + 相似问 + 答案 | 是 |
| L3 业务知识 | 华夏基金业务知识 | general | 长文本，按章节切 | 是（WEB/APP） |
| L4 结构化 | 服务渠道 / 线下网点 / 开户银行 | table | 表格长表 | 是（按问题命中） |
| L5 话术 | 转人工话术 | qa | 转人工引导语、二维码说明 | 是 |
| L0 测试 | 上述各库的 `_沙箱` 副本 | 与源库一致 | 生产内容副本 | 否（仅沙箱应用） |

规则：

1. **一个业务域一个库**，不把 FAQ 和长文本混在同一个库里，否则 chunk 粒度不一致、互相挤占 top_n。
2. 寒暄必须单独成库。寒暄的语义特征和业务问题差异大，混库会污染召回（现状已验证：混检时寒暄库进不了 top_n）。
3. 表格类保持一个文件一张表，沿用现有 `table` 解析器，保证 `positions` 可用（点击引用能定位到行）。

### 2.2 命名与元数据规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 知识库 | `华夏基金-<业务域>` | 华夏基金-FAQ话术 |
| 沙箱库 | `<正式库名>-沙箱` | 华夏基金-FAQ话术-沙箱 |
| 文档 | `<业务域>_<内容主题>_<版本>.md` | FAQ_基金交易_202611.md |
| 应用 | `华小夏-<渠道>` 或 `华小夏-<用途>` | 华小夏-IVR |
| 质检规则 | `QC-<场景>-<动作>` | QC-投诉-提示转人工 |

**渠道元数据（关键）**：每个 chunk 必须打 `channel` 元数据，取值 `web` / `app` / `ivr`，多选用逗号分隔。

- 应用侧通过 `meta_data_filter` 按渠道过滤，实现"同一份知识、不同渠道可见性"。
- 未打标签的 chunk 视为全渠道可见，但**不允许**长期缺省——新入库文档必须带。

### 2.3 解析器选择规则

| 内容特征 | 解析器 | 理由 |
|---|---|---|
| 一问一答、话术 | `qa` | 相似问参与检索，答案完整不被切断 |
| 制度/产品说明等长文 | `general` | 按语义段落切，保上下文 |
| 表格（渠道、网点、费率） | `table` | 保留行列位置，引用可定位 |
| 法规条文 | `laws` | 按章/条层级切 |

**语言必须为 Chinese**。这是硬性前置条件：`knowledgebase.language` 在入库时决定分词，设成 English 会让关键词检索整条失效（现状即此，已修但历史索引需重建才能完全恢复）。

### 2.4 相似问与同义词规则

**相似问**（对应需求 2）：

- 一个标准问 = 一个 chunk，挂 N 个相似问；相似问存在 `chunk_question` 表，并投影到 `question_kwd` 参与检索。
- 维护入口：知识库 → 文档 → chunk 编辑里的相似问面板（增/删/改），或走 `change-sets/similar-questions` 批量。
- 录入纪律：
  - 每条相似问 **6-30 字**，模拟真实客户口语，不要写书面标题；
  - 单条标准问的相似问 **5-15 条**为宜，超过 20 条说明该问题应拆成两个标准问；
  - 禁止跨业务复用语术（如"怎么操作"这种无主语短句，会命中多库）。

**同义词/别名表**（`synonym-management`，数据集级）：

- 只放**严格同义**，不放上下位、不放相关推荐。例：`华夏成长` = `华夏成长混合` = `华夏成长证券投资基金` = `000001`。
- 基金领域分两类维护：通用词（申购/认购、净值/单位净值）+ 华夏专属（产品全称/简称/代码、渠道名）。
- 反例（会污染召回）：不要配 `基金` = `理财`，不要配 `赎回` = `卖出`（语义相反方向不同）。

### 2.5 检索参数基线

以「华小夏-客服」为基准，新建应用一律继承：

| 参数 | 基线值 | 说明 |
|---|---|---|
| language | Chinese | 强制 |
| similarity_threshold | 0.35 | 低于 0.3 会放进无关内容 |
| vector_similarity_weight | 0.63 | 关键词权重 0.37 |
| top_n | 5 | 超过 8 条 prompt 变长、噪声增加 |
| top_k | 1024 | 召回池，不动 |
| rerank | qwen3-rerank，候选 30 | 现状 104 过大，无收益 |
| temperature | 0.2 | 客服场景要稳定 |
| top_p | 0.75 | 与 temperature 配合 |
| frequency/presence_penalty | 0 | 双开 0.5 会让模型刻意换词 |
| tts | WEB/APP 关闭，IVR 开启 | 按渠道区分 |
| 多轮改写 | 开启，但寒暄类短路 | 单轮寒暄不必改写 |

### 2.6 渠道隔离规则

- 知识的渠道可见性靠 `channel` 元数据 + 应用的 `meta_data_filter`，**不靠拆库**（拆库会让同一条知识维护多份）。
- 例外：IVR 需要独立的答案长度控制（短答案、口语化），可用单独的应用 + 单独的 system prompt 解决，知识仍是同一批。
- IVR 渠道默认**不召回**长文本业务库，只召回 FAQ + 寒暄，避免播报过长。

### 2.7 发布与环境隔离规则

```
知识变更 -> 变更集（change set）-> 沙箱库 -> 沙箱应用模拟测试 -> 通过 -> 发布到生产库 -> 生产应用生效
```

- 生产库任何变更前先落沙箱，沙箱跑通再发布；
- 应用配置（阈值、prompt）变更先在沙箱应用验证，再改生产；
- 每次发布记录：变更集编号、影响文档数、验证问题集、结果。

### 2.8 转人工与质检规则

**转人工（需求 5）** 命中顺序：

1. 关键词命中（转人工 / 人工客服 / 投诉 / 投诉电话）；
2. 情绪/场景命中（连续 2 轮未解决、明确表达不满）；
3. 检索为空且模型判定无答案（走兜底话术）。

命中后输出：引导语 + 夏管家二维码 + 服务时间说明，并打会话标记供报表统计。**开关**做成应用级参数（`transfer_enabled`），支持一键停用。

**实时质检（需求 8）** 规则编排：

- 规则命名 `QC-<场景>-<动作>`，如 `QC-投诉-提示转人工`；
- 每条规则绑定「关键词组 + 提示文案 + 触发动作（提示/标记/拦截）」；
- 规则只提示不拦截，避免误伤；命中记录进 `qc_hit`，供报表按日统计。

### 2.9 参数管理（需求 9，待业务梳理）

平台现有 `system_settings` 只管系统级配置，缺业务参数页。一期先建**参数登记表**，由运营在应用配置中维护，登记项：

| 参数 | 归属 | 当前值 | 可调范围 | 负责人 |
|---|---|---|---|---|
| similarity_threshold | 检索 | 0.35 | 0.25-0.5 | 知识运营 |
| top_n | 检索 | 5 | 3-8 | 知识运营 |
| 转人工开关 | 业务 | 开 | 开/关 | 客服主管 |
| 转人工关键词 | 业务 | 转人工/人工/投诉 | - | 客服主管 |
| 质检关键词 | 业务 | 见 QC 规则表 | - | 质检岗 |
| 兜底话术 | 业务 | 见 prompt | - | 客服主管 |

二期再做统一参数管理页。

### 缺口分析

**缺口 1：蓝凌知识点自动同步（需求 1）**

平台连接器目前支持 Google Drive / Box 等外部源，**没有蓝凌**。三条路径：

- A（推荐）：用 RAGFlow 开放 API 做定时增量同步——蓝凌侧导出或调用其接口，比对 `content_hash` 后调用文档上传/更新接口，成本最低；
- B：按蓝凌的开放接口定制一个 connector，进平台统一管理，工作量大；
- C：人工导出上传，作为兜底，不可持续。

**缺口 2：IVR（需求 11）**

平台无 IVR 引擎，也没有 SIP/话务对接。可落地的边界是：

- 能做：ASR 转写 → 调问答 API → 答案 TTS 播报（接口都在）；
- 不能做：IVR 按键流程画布、放音收号、话务路由、IVR 报表（需话务平台提供）。

建议分工：话务平台（如现有呼叫中心）负责 IVR 流程与放音收号，RAGFlow 作为其中的「智能问答节点」，通过 HTTP 接入；IVR 报表由话务侧出，平台侧补问答命中率。

**缺口 3：批量测试（需求 12）**

`evaluation_datasets / cases / runs / results` 四张表已存在但未对外开放。两条路径：

- A：补 REST 接口 + 测试集管理页面（工期较长，但可复用）；
- B：脚本化——测试集存 Excel，脚本批量调问答 API 并断言关键词/引用命中，产出通过率报表（1-2 天可交付，先解燃眉之急）。

建议一期走 B，二期补 A。

## 五、待确认（评审时定）

1. **蓝凌同步**走 A（API 定时同步）还是 B（定制连接器）？取决于蓝凌是否开放接口。
2. **IVR 本期是否要落地**？如果要，需确认现有话务平台型号与是否支持 HTTP 回调。
3. **批量测试**先脚本化（B）还是直接排期做页面（A）？
4. **渠道隔离**确认用 `channel` 元数据方案，还是业务上要求物理拆库（多份维护）？
5. **是否重建知识库**彻底恢复关键词检索（代价：chunk id 全变、历史引用失效）。
