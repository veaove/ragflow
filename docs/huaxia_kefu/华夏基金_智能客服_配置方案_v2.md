## 二、配置场景

**一句话：知识只维护一份，渠道只是出口。**

```
渠道层   WEB/APP 在线客服        IVR 电话语音        坐席辅助
应用层   华小夏-客服（生产）      按键菜单流程        夏管家推送（Agent）
         └ 绑 3 库               └ 16 节点放音树       └ 关键词命中→推二维码
                                  └ 末级按 1 进智能问答（复用生产应用）
测试层   华小夏-沙箱（模拟测试）  └ 绑 沙箱FAQ + 生产只读库
检索层   同义词归一 → 向量+关键词混合 → qwen3-rerank → 阈值 → top_n
知识层   FAQ话术 | 寒暄 | 服务渠道 || FAQ话术-沙箱
治理层   参数基线 | 质检规则 | 审计 | 报表
```

渠道差异靠**应用绑哪个库**解决，不靠给 chunk 打标 —— 三个渠道当前的真实差异只有一条：
「IVR 播不了长文本、也读不了表格」，所以电话侧先走**按键菜单把答案收敛到一句话**，
开放问法才落到智能问答（复用生产应用的短答案 prompt）。这个用绑定关系 + 一套菜单树就能表达，
不需要为 199 个 chunk 逐个打 `channel` 标签（见 3.4）。

### 3.1 参数基线（已固化到生产应用）

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| language | Chinese | 硬前置：决定入库分词，设 English 会让关键词检索整条失效 |
| similarity_threshold | 0.35 | 0.2 会放进无关内容（实测召回 13 条清一色不相关） |
| vector_similarity_weight | 0.63 | 关键词 0.37；当前 term_similarity 多为 0，实际生效主要是向量 |
| top_n | 5 | 13 条时 prefill 拖到 18 秒 |
| top_k | 1024 | 召回池，不动 |
| rerank_candidates_count | 104（未动） | v1 建议降到 30，但当前首字已 1.4s，动它收益不确定、风险确定，**维持不动** |
| temperature / top_p | 0.2 / 0.75 | 客服要稳定 |
| frequency/presence_penalty | 0 / 0 | 双开 0.5 会让模型刻意换词 |
| tts | 全部关闭 | 原 IVR 播报应用已删；语音改由话务平台对答案文本做 TTS |

**关于「不重建知识库」**：三个库的 `term_similarity` 仍普遍为 0，说明 Infinity 全文索引的
analyzer 在**建表时**就固定了，事后改 `knowledgebase.language` + 重解析回补不了。
但当前向量召回质量足够（实测 vec 0.83～0.97，11/11 用例命中正确 chunk），
而重建的代价是 chunk id 全变、历史引用链接失效、相似问与质检绑定要重做一遍。
**决策：不重建，记为已知限制**，等 P1 做知识分层重构时新建库一次性解决（那时本来就要重建）。

### 3.5 IVR 按键菜单流程（需求 11）—— 已按中国移动式重做

**为什么重做**：v1 交付的 `华小夏-IVR（语音播报）` 是「一问一答 + TTS 播报」形态，而客户要的是
「您好，欢迎致电…人工请按 1、咨询话费请按 9」这种**按键菜单**。两者形态不同，原应用已删除
（备份 `.workbuddy/backup/华小夏-IVR_删前.json`）。

**流程树（16 节点 / 48 条按键分支）**

```
welcome  您好，欢迎致电华夏基金客户服务中心。基金有风险，投资需谨慎。
         基金交易请按一，账户与净值查询请按二，产品与费率请按三，转人工请按九，重听请按零
├─ 1 trade   基金交易
│    ├ 1 trade_buy      买入 / 申购 / 认购   → 按 1 转智能客服
│    ├ 2 trade_sell     赎回 / 卖出          → 按 1 转智能客服
│    └ 3 trade_aip      定投                 → 按 1 转智能客服
├─ 2 account 账户与净值查询
│    ├ 1 acc_nav        净值查询             → 按 1 转智能客服
│    ├ 2 acc_share      份额 / 持仓          → 按 1 转智能客服
│    └ 3 acc_dividend   分红方式             → 按 1 转智能客服
├─ 3 product 产品与费率
│    ├ 1 prod_fee       申购 / 赎回费率      → 按 1 转智能客服
│    ├ 2 prod_type      产品类型             → 按 1 转智能客服
│    └ 3 prod_risk      风险等级             → 按 1 转智能客服
├─ 9 human   正在为您转接人工客服…（播完自动挂机）
└─ * / 0     * 返回上一级 ｜ 0 重听本级 ｜ 无效键 → 提示后回本级
```

每层通用规则：

- `*` 返回上一级（一级菜单的 `*` 回 `welcome`）
- `0` 重听本级播报
- 按了不存在的键 → 播「抱歉，您输入的按键无效，请重新选择。」→ **回本级**（不跳走、不挂机）
- 9 个具体业务节点都留了「按 1 转智能客服」——这是全流程唯一接 RAGFlow 的地方
- `human` 是终点（`keys={}`），播完自动挂机，避免「转人工后按键无效」的死循环

**三种交付物**

| 交付物 | 路径 | 说明 |

**边界（这条必须跟客户说清）**

平台**没有 IVR 引擎**：做不了放音收号（DTMF）、话务路由、IVR 报表。本期交付的是
**流程设计 + 语音素材 + 可点击模拟器**；模拟器是本地产物，**不是线上可拨打的号码**。
正式落地由话务平台跑这棵树、放这 16 段音、收 DTMF，只在「末级按 1 转智能客服」那一跳调
RAGFlow —— 问答用 `POST /api/v1/chats/{chat_id}/completions`（SSE），
或 OpenAI 兼容的 `POST /api/v1/openai/{chat_id}/chat/completions` 更好接；
把返回文本交给话务平台 TTS 播报即可。这也正是原来那个播报型应用唯一有价值的部分。

### 3.7 转人工 / 夏管家推广（需求 5）

现状：`夏管家推送` 智能体拓扑为
`begin → Switch(命中"人工") → 推二维码` / `→ 查询改写 → 检索 → 生成回答`，

**发布状态：保持未上架（`release=false`），这是有意为之，不是遗漏。**
`Message:FamousBananasWalk` 里的二维码地址仍是占位符 `![夏管家客服二维码](xxxx)`，
上架后客户点开是破图。客户提供真实二维码后：

1. 改 `Message:FamousBananasWalk` 的 content，把 `xxxx` 换成真实图片地址；
2. `python scripts/huaxia_configure.py transfer --publish` 上架。

脚本带守卫：二维码还是占位符时 `--publish` 会被拒绝执行，避免误上架。

> 注意 `release=false` 只影响「对外发布」，不影响内部预览与测试 —— 实测未上架状态下
> `POST /agents/{id}/run` 两条分支都能跑，所以流程验证不受阻。

**关于「一键停用转人工」：用平台的发布开关，不改 DSL。** 原因是我实测发现
Begin 组件的 inputs 在 conversational 模式下**会被用户输入覆盖**
（`begin.outputs = {"query":"我要人工","zuoxi_02":"我要人工"}`，配置的 `zuoxi_02=1` 不生效），
没法把开关塞进 Begin 再到 Switch 里判断。停用转人工 = 下架该智能体，入口即消失，零风险。

## 五、已知缺口（诚实清单）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1 | `term_similarity` 普遍为 0 | 关键词检索基本失效，只靠向量 | P1 重建库时解决；精确串（产品代码）暂时靠相似问兜 |
| 2 | 沙箱记录进生产报表 | 考核数据需按 app_id 排除 | 报表口径加排除项 |
| 3 | `response_ms` 无埋点 | 响应速度指标为空 | 开发项，需求 4 若考核则必须做 |
| 4 | 二维码占位符 `xxxx` | 已保持未上架，不影响客户；但也意味着推广入口还没对外开 | 客户提供素材 → 替换 URL → `transfer --publish` |
| 5 | 无 chunk 级 `channel` 元数据 | 当前靠应用绑定已够用；将来若要同一库内按渠道裁剪内容则不满足 | 随 P1 入库规范一起做，不事后刷 199 个 chunk |
| 6 | IVR 无引擎 | 菜单流程只能本地演示，不是可拨号码 | 话务平台跑树放音收号，末级按 1 调 RAGFlow 问答（见 3.5 边界） |
| 7 | 批量测试未做 | 无自动化回归 | 现成替代：`scripts/huaxia_configure.py eval` 已能跑 11 条断言 |

## 六、运维手册（给接手的人）

配置全部脚本化：`scripts/huaxia_configure.py`，幂等，可重跑。

```bash
export RF_BASE_URL=http://172.30.20.51
export RF_SECRET_KEY=<kvrocks ragflow:system:secret_key>
export RF_ACCESS_TOKEN=<user.access_token>
export RF_S3_AK=<minio_user> RF_S3_SK=<minio_password>   # 见 docker/.env 的 MINIO_USER / MINIO_PASSWORD，仅 sandbox 子命令需要

python scripts/huaxia_configure.py status    # 现状快照：库/应用/智能体/质检/同义词
python scripts/huaxia_configure.py synonym   # 建同义词组（13 组，幂等）
python scripts/huaxia_configure.py similar   # 补相似问（15 个标准问，幂等）
python scripts/huaxia_configure.py qc        # 建质检规则 + 绑应用（幂等）
python scripts/huaxia_configure.py sandbox   # 建沙箱库 + 沙箱应用（幂等）
python scripts/build_ivr_demo.py         # IVR：按 NODES 重合成语音 + 重出模拟器 + 自检
python scripts/huaxia_configure.py ivr    # ⚠️ 旧的播报型 IVR 应用，本次已弃用（会重建一个播报应用）
python scripts/huaxia_configure.py transfer  # 检查转人工链路 + 素材缺口（只检查不发布）
python scripts/huaxia_configure.py transfer --publish  # 素材齐了才上架
python scripts/huaxia_configure.py test      # 冒烟：三条链路各跑一遍
python scripts/huaxia_configure.py eval      # 检索回归：11 个用例断言
```

日常三条纪律：
1. 改 FAQ 先改沙箱库，沙箱应用验证过再动生产；
2. 新增标准问必须带 5–15 条口语化相似问，否则口语问法召不回；
3. 改完跑一次 `eval`，掉到 9/11 以下说明改坏了。
