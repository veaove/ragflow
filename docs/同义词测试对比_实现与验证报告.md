## 一、实现了什么

把原来的降级方案（只展示原配置 + 一句「发布后可能变」）换成**真对比**：同一问题跑两遍，两侧使用完全相同的 TopK / 阈值 / 权重 / 过滤，差异只来自待生效的变更集。

### 核心判断（都有代码依据，不是推测）

| 变更 | 注入点 | 依据 |
|---|---|---|
| 同义词 / 专有词 | query 字符串构造时展开 | `query_builder.go:389` —— 同义词在 query 侧生效，**与引擎无关** |
| 相似问 | chunk 的 token 列表（`insTw`） | `reranker.go:146` —— 经 `question_tks` 进 `tsim`，**不进** reranker 的 doc 文本 |

由此得到能力矩阵（与自评修正后一致）：

| 变更类型 | 有 rerank | 无 rerank |
|---|---|---|
| 同义词 | ✅ 精确 | ✅ **精确**（query 字符串与引擎无关） |
| 相似问 | ✅ 精确（应用层可注入 token） | ❌ 融合在引擎内，应用层改不了 |

### 后端

1. **两个注入 hook**，都用「新增变体 + 原函数委托」，**现有调用方零改动**：
   - `QueryBuilder.QuestionScopedWithOverride`：按 token 覆盖同义词列表，未命中的 token 仍查 live 字典（稀疏 overlay，不碰单例与缓存）
   - `RerankByModelWithExtra`：给指定 chunk 追加 token
2. `RetrievalRequest` / `RetrievalSearchRequest` 增加 `SynonymOverride`、`ExtraChunkTokens`，默认 `nil`
3. `internal/service/chunk/compare.go`：编排 + diff
4. `POST /datasets/:id/change-sets/:id/retrieval-compare` 端点

### 前端

`TestCompareDialog` 重写：变更摘要 + 参数行（问题/TopK/阈值/复制报告）+ **能力提示条** + 六张指标卡 + 双栏同序结果 + 可折叠差异明细 + 发布（二次确认）。

## 二、几个刻意的设计取舍

### 1. diff 的口径（按自评修正）

| 项 | 做法 | 为什么 |
|---|---|---|
| 平均分变化 | **只算交集** | 5 条 vs 6 条的均值是两个不同总体，不可比 |
| 位次变化 | 拆成 `reordered`（自身得分也变了）与 `displaced`（只是被挤动） | 否则「一条插队」会被记成 N 个回归 |
| `removed.reason` | 只保留 `pushed_out_of_topk` / `not_recalled` | 被阈值滤掉时拿不到分数，`below_threshold` 无法判定，去掉 |

`removed.reason` 的判定方式：candidate 的 `total > 返回条数` 说明还有结果被截断 → `pushed_out_of_topk`；否则 `not_recalled`。这是 TopK 对比能给出的诚实上限（看不到窗口外的分数）。

### 2. 不静默降级

任一侧检索失败 → **直接报错并显示原因**，不退回「只看原配置」。因为那会让人以为在做对比，而 candidate 根本没跑。

### 3. 无 rerank 时说清楚

不返回假 diff。`capability.similar_q_simulated=false` + `unsolved_reasons=["no_rerank_model"]`，前端显示黄色警告条：「相似问变更无法模拟」。

## 三、验证结果

### 3.1 服务器全量单元测试

```
通过: 126 个包   失败: 0
```

新增测试覆盖：
- 交集平均分不被异常值污染（用 9.99 的离群点验证）
- 结构性位移不重复计（一条插队导致 3 条位移 → displaced=3、reordered=0）
- 真实位次变化（得分和名次都动 → reordered=1）
- `removed.reason` 两种判定
- 全零状态返回空 slice 而非 nil
- 空结果集不除零
- epsilon 内的得分抖动不报变化
- **overlap 判定**（见下）

### 3.2 端到端（`scripts/e2e_compare_verify.mjs`）

```
✅ 20 项通过 · 0 失败
```

| 场景 | 结果 |
|---|---|
| A. 空变更集 | diff 全零；`synonym_simulated=true`、`similar_q_simulated=false`、`reasons=["no_rerank_model"]`；两侧耗时已记录（381ms / 163ms） |
| B. 新增同义词组 | 对比跑通，能力上报正确，两侧结构完整 |
| C. 新增相似问 | `affected_chunk_count=1`；`skipped_similar_count=1`；明确告知相似问不可模拟 |
| D. 无重叠相似问 | 被正确跳过（「火星探测器的燃料配方」） |

### 3.3 e2e 抓出并修复的缺陷

**相似问重叠判定过严，会导致漏报。**

给 query「华夏基金 申购费率是多少」加相似问「华夏的申购费率说明」，人一眼看出相关，却被判定为**无重叠并被跳过** → 这条变更的影响被静默隐藏。

根因：只用分词后的词项交集判定。分词器切分粒度不一致（「华夏基金」vs「华夏」），词项列表因此不相交。

**为什么必须修**：漏报的代价远大于多注入。多注入一个 token 顶多让某条相似问不产生差异；误跳过会让用户以为「这次变更没影响」——而这正是本功能要防的事。

修复：两级判定 —— 词项交集命中即算重叠，否则退回**字符 bigram** 兜底（对中文尤其可靠）。

修复后实测：`skipped` 从 **2 → 1**，只有真正无关的那条被跳过。已补单测锁住。

## 四、没验证到的部分（必须说清楚）

| 项 | 为什么没做 | 影响 |
|---|---|---|
| **有 rerank 时相似问的精确性** | 服务器 `tenant_llm` 无 rerank 模型，配一个需要真实 API key | 「相似问注入能让某 chunk 的名次真的上升」这一条**未经实测**，只有代码依据（`insTw` 拼接点） |
| **技术详设 8.3 的发布前后等价性验证** | 同上，且需要「发布 → 用同一问题跑线上检索 → 与 candidate 预测对照」的完整链路 | 这是方案可信度的基石，**未验证** |
| 同义词产生实际召回差异 | 库中无与测试同义词对应的内容（加了「认购费率」，库里只有「申购费率」） | 只验证了「同义词对比能跑通、能力上报正确」，未验证「同义词确实改变了召回」 |

前两项建议在有 rerank 环境后补测——技术详设明确写着「这一步不过，不给上线」。

## 六、使用方式

1. 知识库 → 变更中心 → 有待生效变更时点「测试对比」
2. 输入真实用户问题，调 TopK / 阈值，点「测试」
3. 看六张指标卡定结论，展开明细看具体哪些 chunk 变了
4. 需要评审就点「复制报告」拿 Markdown
5. 确认后可直接在弹窗里发布（二次确认）

**注意**：对比结果只用于发布前评估，不影响线上检索；未配置 rerank 时相似问变更无法模拟，界面会明确提示。
