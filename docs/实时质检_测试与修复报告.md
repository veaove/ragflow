## 二、本轮修复的缺陷（11 项）

### 后端

1. **正则规则恒不命中**（`internal/service/qc_matcher.go`）
   `CompileRules` 的正则分支没有收集首字符，`firstRunes` 为空 →
   `maybeHit` 恒返回 `false` → 正则规则在运行期和规则测试接口里都永远不命中。
   修复：新增 `hasRegex` 标志，存在正则规则时短路快速路径。

2. **阻断后前端永不结束**（`internal/service/chat_pipeline.go`）
   阻断时把 final chunk 整块丢弃，客户端收不到结束信号、也丢了 `reference`。
   修复：改为下发一个 `Answer` 为空的终止 chunk，保留 `Reference` / `Final` / `QcEvent`。

3. **整段回答绕过质检**（同上）
   原逻辑只检查非 final chunk，而 SQL 检索等路径把整段回答只放在 final chunk 里。
   修复：所有带 `Answer` 的 chunk（含 final）都送检。

4. **规则抽屉「实时测试」命中数恒为 1**（`internal/service/qc_highlight.go`）
   `QcTestMatch` 把所有关键词塞进**一条**合成规则，而 `CompiledRules.Match`
   对每条规则只返回首个命中的关键词 → 「保本」「稳赚」同时出现也只报 1 处。
   修复：每个关键词一条合成规则；`hit_count` 改为按**出现次数**统计；
   新增 `ranges` 字段供前端逐处高亮。

5. **相邻命中被合并少计**（同上）
   `mergeSpans` 用 `s.start <= last.end` 合并，「保本保本」被判成一整段。
   修复：改为严格重叠才合并，相邻算两处。

6. **非法 `app_type` 返回 500**（`internal/handler/qc.go`）
   `resolveAppOwner` 的通用错误被映射成服务端错误。
   修复：`ListRules` 先行校验，返回参数错误（101）。

7. **新增 3 个回归用例**（`internal/service/qc_matcher_test.go`）
   `TestQcTestMatchCountsEveryKeyword` / `...CountsRepeatedOccurrences` / `...Regex`。

### 前端

8. **完全不消费 `qc_event`**（`web/src/pages/next-chats/chat-stream/run-stream.ts`）
   后端把 `answer` 换成替代话术并带 `qc_event.blocked=true` 下发，前端却当成普通
   增量 append → 命中发生在已有正常文本之后时渲染成「半截原文 + 替代话术」。
   修复：`blocked` 时 REPLACE 累积文本；`warn` 级按规则去重后弹一次提示；
   助手气泡上方按技术详设 6.4 增加「该回答已被质检拦截」条
   （`components/message-item/index.tsx`，含三语 i18n）。

9. **实时测试只在 blur 触发**（`web/src/pages/qc/rule-panel.tsx`）
   与「输入后自动预览」的提示不符，且直接点保存会漏掉最后一次编辑。
   修复：改为 350ms 防抖。

10. **正则关键词被逗号拆分**（同上）
    `{2,3}` 这类量词会被撕碎。修复：正则模式只按换行拆分，并同步调整输入框提示。

11. **分页/请求风暴 + WebSocket 重连泄漏**
    - 切换应用不重置分页（`rule-panel.tsx`）；
    - 命中记录页每敲一个字符发一次请求（`pages/qc/index.tsx`，改为回车/点查询生效）；
    - `useQcRealtime` 在 `onclose` 里递归 `connect`，卸载只能清掉第一个定时器，
      关掉页面后仍每 3 秒无限重连（`hooks/use-qc-request.ts`）。

## 四、必须在服务器侧解决的两件事

### 1. nginx 没有转发 WebSocket 升级头（阻塞「实时质检」页签）

现状（`/etc/nginx/nginx.conf`）：

```nginx
location ~ ^/api/v1 {
    proxy_pass http://127.0.0.1:9380;
    proxy_http_version 1.1;
    proxy_set_header Connection "";     # ← 直接把升级头清掉了
    ...
}
```

实测对照：

- 直连 `ws://47.99.241.190:9380/api/v1/qc/stream?token=...` → **握手成功**
- 经 nginx `ws://47.99.241.190/api/v1/qc/stream?token=...` → **非 101，失败**

修复（`http { }` 内、`include mime.types;` 之后加 map）：

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';
}
```

然后把 `/api/v1` location 里的 `proxy_set_header Connection "";` 换成：

```nginx
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
```

生效：`nginx -t && kill -HUP $(pgrep -o nginx)`（`nginx -s reload` 在本机因 pid
文件为空会失败）。

> 顺带收益：同一段配置也是 SSE / 其他长连接的公共前置条件，
> 改完 bot、音频等 WS 场景一并受益。

### 2. 整套部署没有任何可用 LLM

`llm` 表、`tenant_llm` 表均为空；`tenant.llm_id` 只有 `123456789@qq.com`
那个租户有值（`qwen-flash@tongyi@Tongyi-Qianwen`），但该模型对其他租户
不可见（创建聊天应用时提示 `llm_id ... doesn't exist`）。

后果：任何 `/chat/completions` 直接返回 `no default chat model for tenant`，
**在进入 `AsyncChat` 之前就失败**，所以：

- 「AI 回答命中 → 阻断 → 替换话术」这条链路**无法做真实 e2e**；
- 连「用户输入命中落库」也测不到（同样进不到 `AsyncChat`）。

要验证这两段，需要先给测试租户配一个模型 key。在此之前，
这两块的正确性只由单元测试保证（`TestStreamMatcherBlockAndNoBlock`、
`TestRegexMatch`、`TestQcTestMatch*` 等）。
