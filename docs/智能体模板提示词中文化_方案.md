| 项 | 内容 |

| 版本 | v1.0 |

| 需求来源 | 内置智能体模板的提示词全为英文，日常使用以中文为主，希望能改成中文且不破坏现有功能 |

---

## 一、先纠正一个前提：问题范围比看上去小

从截图看，画布上到处是英文，容易判断成"模板全是英文"。实际查代码后，结论是：

| 位置 | 现状 | 说明 |
|---|---|---|
| 模板名称 | ✅ **已有多语言** | `title` 存为 `{"en": "SEO article writer", "zh": "SEO 博客写手", "de": ...}`，列表里显示的中文就来自这里 |
| 模板描述 | ✅ **已有多语言** | 同上，`description` 也是 JSONMap |
| **DSL 内部所有文本** | ❌ **单语英文** | `sys_prompt`（系统提示词）、`prompts[].content`（用户提示词）、节点 `description`（画布说明框）、`prologue`（开场白） |

**所以真正要改的只有一样东西：模板 `dsl` 字段里的文本。**

这一点很重要——它决定了方案不必动多语言框架（框架已经有了），只需要解决"dsl 怎么支持两份语言"。

## 二、规模与技术特征（决定工作量和风险）

对 19 个内置模板做了统计：

| 指标 | 数值 | 含义 |
|---|---|---|
| 模板数 | 19 | 其中 5 个无提示词（纯流程编排：切片、编译、入库流水线等） |
| 含提示词的节点 | 38 | 真正要翻的单位 |
| **提示词总字符** | **55,826** | 约等于 3~4 篇长文的体量 |
| 含 JSON 输出格式 | **0 / 19** | **好消息**：没有结构化输出契约，翻译不会让下游解析失败 |
| 含 `{变量}` 引用 | 14 / 19 | **最大风险点**，见下 |

### 最大的技术风险：变量引用不能碰

提示词里有大量运行时插值，例如：

```
The parse and keyword agent output is {Agent:ClearRabbitsScream@content}
The user query is {sys.query}
```

这类 `{...}` 是**运行时变量占位符**，由 DSL 引擎解析后替换成上游节点的输出。一旦翻译时改动、加空格、换全角括号，变量会解析失败，**智能体直接跑不起来**。

所以这次"翻译"不是纯文本替换，而是**受约束的改写**：只能改自然语言，必须原样保留变量、工具名、代码标识符。

## 三、方案对比

前提约束：**不能影响英文用户，也不能影响已克隆的实例**。

| 方案 | 做法 | 英文用户 | 工作量 | 侵入性 | 结论 |
|---|---|---|---|---|---|
| **A 双记录（推荐）** | 每个模板额外生成一条中文记录（id 加 `_zh` 后缀），列表按语言过滤 | 不受影响 | 中 | 低（seed 逻辑 + 列表过滤） | ✅ 推荐 |
| B dsl 加语言副本 | `canvas_template` 加 `dsl_zh` 字段，克隆时按语言选 | 不受影响 | 中 | 中（改实体 + 克隆链路） | 备选 |
| C 只翻展示层 | 仅翻节点 `description` + `prologue`，`sys_prompt` 保持英文 | 不受影响 | 小 | 极低 | 可作为第一批 |
| D 直接改英文为中文 | 把 dsl 里的英文全换成中文 | **失去英文版** | 中 | 低 | ❌ 违背"保障现有功能" |

### 为什么推荐 A

1. **dsl 结构完全不变** —— 智能体运行时读到什么就执行什么，不需要在运行时做语言判断，零性能开销、零链路风险
2. **英文版原样保留** —— 同一个模板中英各一条，互不干扰
3. **失败可回退** —— 中文版有问题，删掉中文记录即可，英文版毫发无损
4. **seed 机制天然支持** —— 现有 `SeedCanvasTemplates` 按 id upsert，只要文件名/字段能区分语言即可

**代价**：模板列表会从 19 条变 38 条（中英各半），需要列表接口按当前语言过滤，否则用户会看到重复项。这是方案 A 唯一需要新增的代码。

## 四、推荐方案的分层实施

不建议一次性翻译 5.6 万字符——风险集中、验证困难。建议分三批：

### 第一批：展示层中文化（P0，约 1 人日）

只翻**用户直接看到、且不参与 LLM 推理**的文本：

- 各节点的 `description`（画布上的说明框，截图红框里那些）
- Begin 节点的 `prologue`（开场白："Hi! I'm your SEO blog assistant..."）

**收益**：打开模板，画布说明和开场白全是中文，第一眼体验立刻改善。
**风险**：几乎为零——这些文本不进模型上下文。

### 第二批：提示词中文化（P1，约 3~4 人日）

翻 `sys_prompt` 与 `prompts[].content`，按方案 A 生成中文模板记录。

**分批建议**（按使用频率）：

| 批次 | 模板 | 字符量 |
|---|---|---|
| 2-1 | market_seo_article_writer、smart_customer_service_specialist、web_search_assistant、trip_planner | 约 1.3 万 |
| 2-2 | deep_research、stock_market_research_assistant、data_analysis_beginner_assistant | 约 2.8 万 |
| 2-3 | 其余（学术论文、text2sql、翻译、用户交互等） | 约 1.5 万 |

### 第三批：已有实例的同步能力（P2，可选）

**重要事实**：已克隆的智能体存在 `user_canvas` 表，是**独立副本**。本次改动**不会**影响它们——这正好满足"保障现有功能"。

如果后续希望老实例也能用上中文模板，需要一个"从模板重新同步"的入口。但这属于新功能，且会覆盖用户的修改，风险高，**建议本期不做**。

## 五、必须遵守的翻译规范

这是方案能否"不破坏功能"的关键，交付时必须作为验收项逐条检查：

| # | 规则 | 原因 |
|---|---|---|
| 1 | `{变量名}`、`{Agent:xxx@content}` 原样保留，**不加空格、不换全角括号** | 运行时插值，改动即失效 |
| 2 | 工具名不译：`Tavily Search`、`TavilySearch` | 与实际注册的工具名对应 |
| 3 | 代码标识符、字段名、URL 不译 | 同上 |
| 4 | 保留 `H2` / `H3` / `SEO` / `JSON` / `API` 等术语 | 行业惯例，译了反而难懂 |
| 5 | Markdown 结构保留：`# Role` / `# Goals` 等段落标题可译，但层级符号 `#` 不能动 | 提示词按 markdown 组织，删了层级会影响模型理解 |
| 6 | 示例数据（如示例输入输出）保留原文或同步译，不能一半英文一半中文 | 混排会让模型困惑 |
| 7 | 不新增、不删除任何指令 | 只做语言转换，不改变智能体行为 |

**验收方式**：翻译前后各跑一次同一个样例输入，对比输出结构与内容是否等价。这是唯一能证明"没破坏功能"的方法。

## 六、一个需要先说清楚的预期

**翻译提示词，主要收益是"可读、可改"，不是"效果变好"。**

现在主流模型（Qwen、DeepSeek、GPT 系列）用**英文提示词处理中文输入**是稳定可用的，英文提示词在角色设定、步骤约束这类任务上并不吃亏。所以：

- 如果你希望的是**用户打开模板能看懂、能自己改** → 这个方案正中目标
- 如果你期待的是**中文提示词让回答质量明显提升** → 收益可能不明显，不要抱这个预期

这点建议在实施前和业务方对齐，避免上线后"翻了但没感觉变好"的落差。

## 七、风险

| # | 风险 | 概率 | 影响 | 等级 | 应对 |
|---|---|---|---|---|---|
| R1 | 翻译误伤 `{变量}` 导致智能体运行失败 | 3 | 5 | **15 高** | 逐条规范校验 + 每个模板跑样例回归 + 中文记录可整条删除回退 |
| R2 | 中文提示词让个别模板行为偏移（输出变短/格式变松） | 3 | 3 | 9 中 | 每个模板保留英文版，可随时切换对比 |
| R3 | 模板列表出现中英重复项 | 4 | 2 | 8 中 | 列表接口必须按语言过滤，前端不显示另一语言记录 |
| R4 | 术语译得不准反而难懂 | 3 | 2 | 6 低 | 术语表统一（见第五节），交由业务方确认用词 |
| R5 | 后续新增模板又退回英文 | 3 | 2 | 6 低 | 把"模板需提供 zh"写进模板提交检查清单 |
